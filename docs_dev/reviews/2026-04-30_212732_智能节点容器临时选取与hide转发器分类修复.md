## 2. 关键数据结构和算法性能分析

新增的核心数据结构是容器快照里的 `temporarySelectedSlotIndex`。它只是一个 `int`，序列化成本很低，对现有 `54` 槽容器布局没有结构性放大。候选槽位解析采用线性扫描当前 contents，时间复杂度 `O(n)`，而 `n` 固定为 `54`，因此在滚轮切换和放置时都属于常数级开销。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L243) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L253)

`cycleTemporarySelectedSlot(...)` 通过先收集当前类型的真实槽位，再做一个小列表上的环形索引切换，没有引入额外排序；因此自动排序开启时复用已有顺序，关闭时尊重玩家当前库存顺序，避免重复排序和序号映射抖动。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L253)

hide 物品模型接入只改 json 引用，不增加运行时纹理处理逻辑；模型解析仍由原有资源系统完成，不会引入额外帧时开销。[hide_pulse_emitter.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/resources/assets/redstonelink/models/item/hide_pulse_emitter.json#L1) [hide_repeater.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/resources/assets/redstonelink/models/item/hide_repeater.json#L1)

## 3. 数据流或调用链

容器临时选取的数据流是：
客户端滚轮 hook 识别 `Ctrl + 智能节点容器` -> 本地读取容器 NBT contents 和当前 `selectedType` -> 计算下一个临时槽位 -> 本地写回 `temporarySelectedSlotIndex` 保证滚轮连续性 -> 发送 `SelectSmartNodeContainerSlotPayload` -> 服务端校验主手物品与槽位归属 -> 服务端写回主手容器物品 NBT。[RedstoneLinkClient.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/RedstoneLinkClient.java#L428) [SmartNodeContainerNetwork.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/SmartNodeContainerNetwork.java#L64) [SmartNodeContainerNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/SmartNodeContainerNetworkServerHandlerSupport.java#L59)

放置链路是：
`SmartNodeContainerItem.useOn(...)` 读取快照与库存 -> `resolvePreferredSlotForType(...)` 决定本次使用的槽位 -> 封装 `BlockPlaceContext` 调用内部 `BlockItem.place(...)` -> 放置成功后按消费规则回写 contents，并显式把 `temporarySelectedSlotIndex` 清成 `-1`。这样成功一次后就回到原默认顺序；失败时不会清空，便于继续尝试同一个临时选项。[SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L84) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L121)

菜单持久化链路仍然沿用原入口 `persistToHeldItem()`，只是把当前主手容器物品上的临时槽位状态一并保留写回，避免菜单内整理 contents 时丢失控制态字段。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L276)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全方面，这轮新增的网络包只传一个 `slotIndex`，服务端再次基于当前主手物品和当前 `selectedType` 做候选槽位校验，不直接信任客户端声明的类型或物品，风险较低。[SmartNodeContainerNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/SmartNodeContainerNetworkServerHandlerSupport.java#L59)

兼容性方面，旧容器没有 `temporarySelectedSlotIndex` 字段时会回退为 `-1`，仍按原本“当前类型首槽位”运行，因此属于典型“读旧写新”。转发器分类修复只扩大了 `REPEATER` 识别范围，不会改变非 `hide repeater` 物品的旧行为。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L427) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L198)

扩展性方面，这套模型后续可以继续支持“当前类型内更复杂的序列循环/筛选规则”，因为临时选取状态已经从“放置类型”里解耦成独立槽位。但目前仍是槽位级而不是“稳定 serial 级”绑定，所以如果未来允许菜单内异步重排 contents，建议再考虑是否切换为按 serial 跟踪一次性选择。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L253) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L277)

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

共享状态主要是主手智能节点容器物品栈上的 `CustomData`。客户端滚轮会先本地改一份，再发送包给服务端落主状态；这本质上是典型的“客户端乐观显示 + 服务端最终权威”模型。由于 payload 只在主手容器且无 screen 的短窗口触发，且服务端会再次校验槽位合法性，重入风险较低。[RedstoneLinkClient.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/RedstoneLinkClient.java#L428) [SmartNodeContainerNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/SmartNodeContainerNetworkServerHandlerSupport.java#L59)

读改写覆盖风险点在于：菜单持久化、客户端滚轮选择、以及放置成功后的清理都可能写同一个容器栈。当前实现通过以下方式收口：
菜单侧持久化保留当前主手物品上的临时槽位；放置成功后明确把临时槽位清为 `-1`；类型切换时也同步清空，避免跨类型遗留旧槽位。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L276) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L121) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L137)

线程边界方面，所有服务端容器写入都仍在主线程网络执行器里完成，没有引入新的异步任务。综合评估并发风险等级为“低”；后续若把这套滚轮选择扩到副手或多容器同步场景，再需要重新审视客户端本地预写与服务端最终回写的覆盖顺序。[SmartNodeContainerNetworkRegistrationSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/SmartNodeContainerNetworkRegistrationSupport.java#L45)
