# 补充双过滤器组合测试并跑通新增用例

## 1. 功能与语义、架构设计

本轮新增了三条双过滤器 functional case：`x29 1s1r`、`x30 2r`、`x31 2s`。三条 case 都用同一组判别信号矩阵 `7 / 12 / 3`，分别验证“同时放行”“仅 upper_bound 过滤器拦截”“仅 lower_bound 过滤器拦截”，从而证明跨侧 `send && receive` 与同侧“所有命中过滤器都必须通过”的叠加语义。关键入口见 [dual_filter_1s1r_signal_matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L2)、[dual_receive_filters_signal_matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L2)、[dual_send_filters_signal_matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L2)。

三条 case 的实现路径保持 bench 现有模板组合，没有新增 bench 内部命令。`x29` 用一个 send 与一个 receive 串到同一路径，`x30` 用两个 receive 覆盖同一 core，`x31` 用两个 send 覆盖同一 triggerSource，对应相位入口分别见 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L36)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L36)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L36)。

## 2. 关键数据结构和算法性能分析

本轮仍然只在测试资产层扩展 JSON case，运行成本主要来自 phase 数量线性增长，没有引入新的脚本复杂度或额外解析分支。三条 case 都是单 source、单 target 的最小布局，降低了 trace 数据量和调试成本，典型布局可见 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L10)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L10)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L10)。

为保证 `data merge block` 后运行态稳定，本轮仍采用“配置后补邻居掉电/复电刷新”的低成本模板动作。这样把不稳定性收敛在常数级附加 phase，而不是引入新的 bench 辅助命令。对应刷新相位见 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L94)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L94)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L94)。

## 3. 数据流或调用链

接入链路保持为 `functional-matrix -> regression-core suite entry -> RunFunctionalCase`。新增 case 注册点见 [functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L59) 与 [regression-core.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/regression-core.json#L80)。

每条 case 内部的数据流都是：放置过滤器和支撑块，配置 `upper_bound` / `lower_bound`，补邻居刷新，然后依次注入 `7 / 12 / 3` 三种强度并读取 core 最新样本断言。`x29` 的关键断言见 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L123)、[x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L156)、[x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L189)；`x30` 见 [x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L123)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L156)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L189)；`x31` 见 [x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L123)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L156)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L189)。

## 4. 安全、性能、兼容性、扩展性风险分析与建议

本轮仍然只改 bench 测试资产和 suite 接线，没有改业务实现、持久化结构、网络协议，也没有引入 `com.makomi.api.v1.*` 依赖。语义继续保持 `triggerSource/core` 单向路径。接线影响范围见 [functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L59) 与 [regression-core.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/regression-core.json#L80)。

主要风险仍是测试口径而非业务逻辑。第一，双过滤器 case 当前使用固定阈值矩阵来验证叠加语义，这能稳定证明组合规则，但没有覆盖“双过滤器同时处于 neighbor_max_input”这种更动态的组合。第二，配置切换后的邻居刷新动作如果在后续复用时被遗漏，仍可能导致运行态与 NBT 配置不一致的假失败。当前三条 case 的刷新模板都可直接复用，参考 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L94)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L94)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L94)。

## 5. 并发冲突审查

本轮没有新增共享状态或线程边界改动，主要并发风险仍是 dedicated suite 中多 world、多进程串行执行的时序隔离。三条新增 case 都通过独立 world 名和单 case 单进程运行避免互相污染，suite 顺序入口见 [regression-core.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/regression-core.json#L80)。

风险等级评估为低。需要关注的不是线程竞争，而是“同一 case 内两台过滤器的配置切换与观测顺序竞争”。本轮已通过显式 `wait_ticks` 和“先配置、再刷新、后注入”的相位顺序规避，见 [x29](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x29/dual_filter_1s1r_signal_matrix.json#L82)、[x30](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x30/dual_receive_filters_signal_matrix.json#L82)、[x31](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x31/dual_send_filters_signal_matrix.json#L82)。
