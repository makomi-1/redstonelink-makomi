# 固定延迟批窗口语义收紧

## 1. 功能与语义、架构设计

本轮将 `core` 目标级批提交调度器从“单目标单窗口”改成“单目标多 `dueTick` 小桶”模型：`window=0` 继续保留当前 tick 对齐与 late-arrival 补 flush，`window>=1` 则按 `enqueueTick + windowTicks` 计算固定到期时刻。这样 `triggerSource -> core` 路径在非零窗口下不再共享首条窗口起点，语义从“首条开窗、后续借窗”收紧为“每条已入 scheduler dispatch 都严格固定延迟”。关键入口与语义边界集中在 enqueue、flush 与 late-arrival 判定三处。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L23) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L108) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L150) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L202) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L228)

语义对齐方面，本轮未改动 `triggerSource/core` 的方向定义与 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射，仅调整 scheduler 内部时序收敛方式；新注释与文档也未引入旧术语回流。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L31) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L349)

## 2. 关键数据结构和算法性能分析

核心数据结构从 `windowStartTick + entriesBySourceAndKind` 改成 `bucketsByDueTick`，每个 `dueTick` bucket 内仍保留 `sourceType + sourceSerial + deltaKind` 级别的去重与 invalidation 覆盖，因此状态增长主要变成“同一目标同时挂住的 future bucket 数量”，而不是全局事件队列膨胀。对当前实际使用场景 `window=0/1/2` 来说，这一额外状态通常只会在目标级多保留 1~2 个未来桶，复杂度与内存成本可控。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L352) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L373) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L462)

算法层面，flush 仍集中在 `END_SERVER_TICK`，只是从“整目标一次 flush”变成“到期 bucket 升序 flush”。这保留了集中 batch apply 的同时性和低碎片特点，但因为跨 tick 不再借窗，`window>=1` 的合并粒度会略小于旧实现，这是用可预测固定延迟换取潜在微小性能回退的明确取舍。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L240) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L416)

## 3. 数据流或调用链

运行时调用链现在是：loaded target dispatch 进入 scheduler 时先计算 `currentTick` 与 `dueTick`，再写入目标级 accumulator 的对应 bucket；到 `END_SERVER_TICK` 时，仅 flush `dueTick <= currentTick` 的 bucket，并把结果统一落到 `core.applyDispatchBatch(...)`。这条链路在 `window=0` 下仍可通过 `flushLateArrivalsIfCurrentTickEndAlreadyPassed` 对齐 same-tick late-arrival，而 `window>=1` 则完全依赖固定 `dueTick`，不再做额外补偿。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L127) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L160) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L184) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L202) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L522)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全与兼容性方面，本轮未引入 `com.makomi.api.v1.*` 依赖，也未改变 `triggerSource -> core` 的数据方向；兼容风险主要集中在“旧实现允许 `window>=1` 借窗”的灰度行为现在被收紧，若未来某些 bench 或人工观察曾默认依赖旧借窗特性，需要重新按“严格固定延迟”口径解读结果。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L214) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L265)

性能与扩展性方面，风险是 `window>=1` 下 bucket 数量与批次碎片会略增，但在当前主要窗口仅 `0/1/2` 的前提下，目标级小桶模型已经足够轻量。若后续需要继续向更大固定延迟窗口扩展，再考虑引入 bucket 池或 flush budget 更合适；当前阶段不建议把 flush 时机迁到首 tick 或中间 tick，以免破坏 `window=0` 的 same-tick 语义边界并增加维护复杂度。残余风险：无新的术语泄漏风险；性能回退风险存在但可控，建议后续用现有 bench 对 `window=1/2` 再做一次 spark 对比确认幅度。[CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L31) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L352) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L552)
