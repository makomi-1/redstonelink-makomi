## 2. 关键数据结构和算法性能分析
- 队列真值仍基于 `LinkedHashMap<DispatchKey, PendingDispatchEntry>` 存储 pending，新增容量判断只增加 `containsKey + size` 这两个 O(1) 操作，不引入新的全表扫描。 [CrossChunkDispatchQueueSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSavedData.java#L61) [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L46)
- 批量路径仍先构建 `lastValidIndexByKey` 和 `resultByKey` 做去重与结果回填；本轮把容量判定插在 `buildPendingEntry(...)` 之前，因此对被拒绝的新 key 不会再分配版本号，也不会污染 `maxIssuedVersionByKey`。 [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L89) [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L136)

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- 安全/稳定性：总量硬上限补上后，跨区块 pending 不再能无限堆积；默认值设为 `100000`，能先提供保护，再通过配置做服主级调优。 [RedstoneLinkConfigTemplate.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/config/RedstoneLinkConfigTemplate.java#L344) [RedstoneLinkConfigInteractionAndCrossChunkParseTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/config/RedstoneLinkConfigInteractionAndCrossChunkParseTest.java#L204)
- 兼容性：本轮没有改 `triggerSource/core` 方向语义，也没有引入 `com.makomi.api.v1.*` 依赖；现有调用方仍只观察 `accepted/rejected`，因此协议与业务入口兼容。 [CrossChunkDispatchQueueSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSavedData.java#L110) [CrossChunkDispatchQueueSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSupport.java#L253)
- 残余风险：当前拒绝语义仍是“统一 rejected”，不会区分“队列满”“配置关闭”“参数非法”等原因；如果后续需要更好的运维可观测性，可再扩展拒绝原因枚举或诊断日志，但这不属于本轮最小改动范围。 [CrossChunkDispatchQueueSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSupport.java#L253) [CrossChunkDispatchQueueSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSupport.java#L369)

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）
- 共享状态主要仍是 `pendingByKey`、`lastAcceptedVersionByKey`、`maxIssuedVersionByKey` 和快照/过期堆缓存；本轮没有引入新的跨线程容器，只是在原有主线程写入路径上新增 `containsKey/size` 判断。 [CrossChunkDispatchQueueSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSavedData.java#L61) [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L46)
- 当前实现依旧隐含“队列写入发生在服务端主线程”这一线程边界；在该前提下，本轮新增逻辑不会造成新的读改写覆盖。风险等级：低。 [CrossChunkDispatchQueueSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueSavedData.java#L99) [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L306)
- 若未来引入异步入队或并行回调，`canAcceptPendingUpsert(...) -> upsertPendingEntry(...)` 仍属于典型的 check-then-act 模式，到时需要把队列写入收口到单线程执行器，或在数据层增加显式同步/原子保留机制。建议继续维持“主线程唯一写入”约束，避免把当前低风险残余升级为真实竞态。 [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L46) [CrossChunkDispatchQueueStateSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchQueueStateSupport.java#L136)
