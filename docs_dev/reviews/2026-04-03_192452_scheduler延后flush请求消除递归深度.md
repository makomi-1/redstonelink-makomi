# scheduler延后flush请求消除递归深度

生成时间：2026-04-03 19:24:52

## 1. 功能与语义、架构设计（关键方法和入口）
本次修复保持 `window=0` late-arrival 补 flush 的现有设计入口不变，仍由 loaded direct 批派发在 END 之后触发一次补 flush；真正的变化是把 `flushServerBatches(...)` 内的重入处理从递归调用改成了 scheduler 内部的延后请求与外层循环 drain。这样既不改变 `triggerSource -> core` 的批调度语义，也不引入新的 direct dispatch 旁路。关键入口和实现点如下：

- late-arrival 入口仍由 [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L266) 调用 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L206)。
- `flushServerBatches(...)` 现在先判断 apply phase 是否进行中，若是则只登记 deferred request，否则进入外层循环 drain [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L232)。
- apply phase 保护与 deferred request 状态收敛在 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L621)。

## 2. 关键数据结构和算法性能分析
核心数据结构没有扩大到新的 map/queue 层级，只是在 `SchedulerState` 上增加了三个布尔状态：`flushApplyInProgress`、`deferredFlushRequested`、`deferredForceFlushRequested`，用于表达“当前正在 apply”和“apply 后还要不要再 drain 一轮” [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L621)。

- `collectFlushPlans(...)` 仍然只对 `pendingByTarget` 做一次线性遍历并摘取到期 bucket，时间复杂度保持为与待 flush 目标数线性相关 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L274)。
- `TargetFlushPlan.apply()` 与 `DueTickBucket.flush(...)` 保持原有 bucket 级 flush 逻辑，新增逻辑没有改变 bucket 内 merge/flush 的复杂度 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L512) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L578)。
- 与旧实现相比，新增的循环 drain 可能在单次 flush 中多跑几轮，但它替代的是递归重入；空间上只增加常量级布尔状态，换来的是递归栈深度风险被消除 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L664)。

## 3. 数据流或调用链
本次修复后的关键调用链如下：

1. loaded direct 批派发完成整批入队后，在 END 之后通过 [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L266) 调用 late-arrival 补 flush 入口 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L206)。
2. `flushServerBatches(...)` 先用 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L274) 摘出本轮 `TargetFlushPlan`，再统一执行 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L512)。
3. `TargetFlushPlan.apply()` 最终进入 bucket flush，并调用 `core.applyDispatchBatch(...)` [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L578)。
4. 若下游在 apply 期间再次请求 late-arrival flush，新请求不会递归进入下一层 `flushServerBatches(...)`，而是落到 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L664) 的 deferred 标记，待当前 apply 结束后由外层循环继续 drain [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L232)。
5. 链式 late-arrival 场景由新增测试 [CoreDispatchBatchSchedulerTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/CoreDispatchBatchSchedulerTest.java#L404) 与测试桩 [CoreDispatchBatchSchedulerTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/CoreDispatchBatchSchedulerTest.java#L699) 固定下来。

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- 安全性：本次改动只涉及服务端内部 scheduler 状态机，没有引入新的外部命令、权限边界或 `com.makomi.api.v1.*` 依赖；late-arrival 的对外行为入口保持不变 [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L266)。
- 性能：递归栈风险已收口，但如果下游逻辑持续无限地产生新的 same-tick late-arrival，请求会表现为单次 drain 轮次增长，而不是栈增长；当前实现是更安全的退化方式 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L232) [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L664)。
- 兼容性：内部存储与输出语义未改，仍保持 `triggerSource/core` 基线；旧术语兼容层、本地持久化键名和 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射均未变更 [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L206)。
- 扩展性：当前 deferred 机制已经兼容 `forceFlush` 聚合，后续如果出现其它 apply phase 内的 flush 触发点，可以直接复用同一保护逻辑，不必再为每个入口单独补 guard [CoreDispatchBatchScheduler.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java#L664)。
