# 频道模式off逐tick与非压测回归

## 1. 功能与语义、架构设计
- 新增 dedicated functional case `x43`，先通过 OCC 把单个 `core` 与三类 `triggerSource` 切到同一频道，再复用 mixed 逐 tick 断言模板验证频道模式在 `directBatching=off` 下的行为入口。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L52)
- 专项 suite 明确把验证口径收敛为“关闭批打包”即 `crosschunk.directBatching=off` 且 `dispatchBatchWindowTicks=0`；全窗口验证不在该 suite 内重复，而是交给既有 `1024 -> 1024` 延迟覆盖率专项承担。[functional-mixed-combinations-channel-off-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-combinations-channel-off-debug.json#L1)
- 新 case 已注册进 functional matrix，保证 suite 解析、dedicated 执行与结果落盘链路可达。[functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L15)

## 2. 关键数据结构和算法性能分析
- `x43` case 只使用 `1 core + 3 triggerSource` 的同区块最小拓扑，避免把频道模式验证与大规模性能因素混在一起；trace 挂载容量固定为 `512`，足以覆盖本用例的逐 tick 采样窗口。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L54)
- OCC 配置阶段使用 snapshot + submit 的四次写入，成本为常数级；真正的性能压力测试仍由现有 `x20/x21` 和非压测 suite 负责，本轮没有改动生产算法或扩大运行时复杂度。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L74)
- suite 只保留 `window0`，避免把 `direct off` 的功能验证和 `dispatch window` 的延迟覆盖率验证重复叠加，减少 dedicated 执行时间与误报面。[functional-mixed-combinations-channel-off-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-combinations-channel-off-debug.json#L13)

## 3. 数据流或调用链
- 调用链为：suite 入口选择 `x43` case -> functional matrix 解析出 case 文件 -> phase 先挂 trace -> 通过 OCC snapshot/submit 建频道映射 -> 等待频道边展开 -> 依次执行 input start 与 `trace_read_tick_assert`。[functional-mixed-combinations-channel-off-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-combinations-channel-off-debug.json#L13)
- `x43` 的关键数据流是 `triggerSource input` 进入已展开的普通边，再由既有 core trace 读取最终仲裁结果；这保证测试验证的是“频道模式改边后其余服务自然生效”的路径，而不是额外旁路逻辑。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L168)
- functional matrix 注册点是该调用链的前置入口；缺少这一步时 suite 会在真正启动 server 前就被配置阶段拦下。[functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L50)

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- 风险 1：`directBatching=off` 下的 `window1/2` 行为并不等价于既有 `all_direct` 断言模板；首轮 dedicated 实测已证明两者口径不同。因此本轮 suite 明确只覆盖 `window0`，把全窗口验证交给既有 `x20/x21`，避免把未定义的行为误写成固定正确语义。[functional-mixed-combinations-channel-off-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-combinations-channel-off-debug.json#L3)
- 风险 2：新增 case 若忘记写入 functional matrix，会在 suite 配置阶段直接失败。这一问题已通过本轮经验文档留痕，后续新增 functional case 时应按“case 文件 + matrix 注册 + suite 引用”三点闭环检查。[functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L15)
- 风险 3：`server-basic-permission` 依赖真实玩家上下文，本轮通过同步同一构建产物到 Prism 实例并自动拉起 bench client 才跑通；后续如果更换机器或清理本地实例，需要重新准备客户端环境，否则权限专项会因环境而非逻辑失败。该风险不来自代码实现，但属于回归环境前提。

## 5. 并发冲突审查
- 本轮新增内容均为 bench case/suite/matrix 描述文件，没有引入新的 Java 共享状态、线程边界或读改写覆盖逻辑；对生产并发模型的直接影响为无，风险等级为低。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L1)
- `x43` 中的 OCC phase 仍通过现有服务器命令入口串行落到主线程执行，没有新增跨线程访问或重入入口；因此不会改变当前 `triggerSource -> core` 写入路径的线程安全边界。[mixed_samechunk_channel_off_combinations_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x43/mixed_samechunk_channel_off_combinations_tick_assert.json#L74)
- matrix 注册与 suite 编排只影响测试发现和执行顺序，不影响运行时共享状态；剩余并发风险仍来自既有生产实现，而非本轮测试资产本身。[functional-matrix.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/functional-matrix.json#L15)
