# 转发器自定义正整数延迟

生成时间：2026-04-30 09:19:05

## 1. 功能与语义、架构设计（关键方法和入口）

- 本轮把转发器延迟从“`1/2 tick` 枚举档位”提升为“仅允许大于 `0` 的正整数 tick 值对象”，同时保留 `1tick/2tick` 旧 token 的兼容读取；核心入口在 [RepeaterDelay.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/RepeaterDelay.java#L15)。
- 客户端编辑入口从两个固定按钮改成数字输入框，并在保存前做正整数校验；非法值不会写入服务端，只会在界面底部给出错误提示，相关入口在 [RepeaterEditorScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/RepeaterEditorScreen.java#L243)、[RepeaterEditorScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/RepeaterEditorScreen.java#L301)。
- 输入框 tooltip 明确了三条规则：只能输入大于 `0` 的正整数、`>2 tick` 为实验性、延迟期间新输入会覆盖旧 pending；渲染入口在 [RepeaterEditorScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/RepeaterEditorScreen.java#L378)、[RepeaterEditorScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/RepeaterEditorScreen.java#L393)。
- 运行时调度语义没有重写，仍复用现有“新输入覆盖旧 pending”的派发链：编辑态快照写入方块实体后，由 `onActiveChanged -> armDelayedDispatch -> onDelayTick` 完成延迟派发，这条链在 [LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L161)、[LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L225)、[LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L315)、[LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L182)。

## 2. 关键数据结构和算法性能分析

- `RepeaterDelay` 现在只按 `delayTicks` 建模，`token()` 和显示翻译键都由 tick 数推导，不再维护分支枚举表，数据结构更简单；见 [RepeaterDelay.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/RepeaterDelay.java#L15)。
- token 解析使用单个正则 `([1-9]\\d*)tick`，复杂度是 `O(n)` 字符扫描；对当前极短 token 来说成本可以忽略，解析实现见 [RepeaterDelay.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/RepeaterDelay.java#L78)。
- 物品与方块实体持久化仍然只写一个延迟 token 字符串，不引入额外结构体字段，存储开销与旧实现同级；写入路径见 [RepeaterItemData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/RepeaterItemData.java#L45)、[LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L262)。
- 调度算法仍是“每次输入变化覆盖一个 pending 派发槽位”，不会因为支持更大的 tick 数而引入队列或历史窗口，因此时间复杂度仍是单次 `O(1)`；覆盖逻辑见 [LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L315)。

## 4. 安全、性能、兼容性、扩展性风险分析与建议

- 安全性：本轮没有引入 `com.makomi.api.v1.*` 依赖，也没有开放新的命令入口，风险低。客户端先行校验正整数，服务端侧依旧通过 snapshot/token 结构兜底读取；见 [RepeaterEditorScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/RepeaterEditorScreen.java#L301)、[RepeaterDelay.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/RepeaterDelay.java#L97)。
- 兼容性：旧世界和旧物品里的 `1tick/2tick` token 仍可直接读取，新值统一写成 `Ntick`，属于“读旧写新”；验证覆盖见 [RepeaterDelayTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/RepeaterDelayTest.java#L19)、[RepeaterNetworkPayloadTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/network/RepeaterNetworkPayloadTest.java#L82)。
- 性能：更大的延迟值不会放大每 tick 算法复杂度，但 `>2 tick` 仍缺少 bench 与游戏内专项验证，这一保留问题已记录到 `docs_dev/保留问题.md`。当前仅有单测和全标签自动化回归，没有新增 `3+ tick` 性能门禁。
- 扩展性：如果后续要支持 `0 tick` 或更复杂的时间单位，当前值对象已经比枚举更容易扩展；但 `0 tick` 会直接触碰运行时调度语义，不建议在本轮实现上继续内联拓展，应单独开设计。

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

- 共享状态：`LinkRepeaterBlockEntity` 的 `pendingDispatchArmed/pendingDispatchTick/pendingDispatchPower` 仍是转发器唯一的延迟派发共享状态，写入点集中在 [LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L315)，读取与清空点在 [LinkRepeaterBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkRepeaterBlockEntity.java#L182)。
- 读改写覆盖：本轮设计明确依赖“新输入覆盖旧 pending”，因此覆盖不是竞态缺陷，而是目标语义；`armDelayedDispatch(...)` 每次都会直接覆写 pending 槽位并重新调度，风险等级为“低且可接受”。
- 线程边界：保存请求仍通过服务端网络线程切回主线程后执行，编辑器和物品读写都在主线程世界上下文里完成，本轮没有新增异步任务；服务端入口见 [RepeaterNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/RepeaterNetworkServerHandlerSupport.java#L36)。
- 建议：后续若真的扩展到 `0 tick`、批量 waveform bench 或更复杂的重复输入场景，建议补 dedicated server/bench functional 的逐 tick 断言，专门守住“覆盖旧 pending”与“重新计时”的边界行为。
