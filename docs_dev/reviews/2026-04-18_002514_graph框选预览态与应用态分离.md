# graph框选预览态与应用态分离

## 1. 功能与语义、架构设计（关键方法和入口）

本轮修复只作用于 graph 前端视图层的框选交互，不改 `triggerSource/core` 真值、snapshot、draft 和服务端保存语义。核心设计是把 ReactFlow 拖框过程中的“预览选区”与右侧批量编辑使用的“正式选区”拆开：预览阶段只缓存候选节点集合，不立即写入批量编辑数组；拖框结束后再一次性提交最终节点集合到画布选中态和批量编辑集合。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2043) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2066) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2153)

入口仍然集中在 `GraphViewer`：`handleCanvasNodesChange` 在预览阶段拦住 `select` 变更，`onSelectionChange` 只更新候选缓存，`onSelectionEnd` 再把最终结果正式提交，这样既保留了框选矩形本身的预览能力，又避免未最终命中的节点进入业务高亮逻辑。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2110) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2161) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2613)

## 2. 关键数据结构和算法性能分析

这次没有引入新的复杂状态机，只增加了三个 `ref`：是否处于框选预览中、当前候选节点集合、以及“框选结束后提交最终结果”的帧句柄。它们都不触发渲染，适合承接拖框过程中高频变化的临时状态，避免把预览过程不断刷进 React 状态树。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L1571) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L1573)

`resolveSelectableActualNodeKeys` 和 `applyCanvasSelectedNodeKeys` 将最终提交阶段收敛为一次线性遍历：先过滤出真实可选节点，再统一回写 `selected`。这样复杂度仍然保持在 O(n)，不会比现有节点重建链路更差。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2052) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2066)

## 3. 数据流或调用链

修复后的框选链路是：用户开始拖框时，`onSelectionStart` 进入预览阶段；此时 `handleCanvasNodesChange` 过滤 `select` 变更，`onSelectionChange` 只把当前候选节点写入 `pendingSelectionNodeKeysRef`；用户松开鼠标后，`onSelectionEnd` 在下一帧读取最终候选集合，并一次性调用 `applyCanvasSelectedNodeKeys` 与 `applyBatchSelectionFromNodeKeys` 提交正式结果。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2110) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2153) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2161) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2613) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2626)

非框选场景下，现有行为保持不变：普通点击仍通过 `onSelectionChange` 即时写入批量编辑集合；切回 `view` 模式和“清空选择”仍会先清掉预览缓存，再走既有的程序化清选逻辑，因此不会与上一轮清选修复冲突。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2241) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2257)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全与语义层面，本轮仅调整前端交互提交时机，没有新增 API 依赖，也没有更改 `triggerSource -> core` 的真实保存边界，符合当前项目语义约束。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2125)

兼容性层面，当前实现依赖 ReactFlow 的 `onSelectionStart/onSelectionEnd` 与 `onSelectionChange` 的相对时序，因此在未来升级 ReactFlow 时，应该优先复核这三者的触发顺序是否仍与当前版本一致。当前通过在 `onSelectionEnd` 使用下一帧提交，已经为末帧选区变化留出缓冲，降低了时序风险。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2168)

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

前端仍运行在 React 单线程事件循环内，没有新增跨线程共享状态。本轮主要解决的是“同一时间窗口内，预览选区和正式业务选区同时读改写同一批节点”的冲突。通过 `selectionPreviewActiveRef` 和最终提交帧的分段处理，读改写关系被明确切成“预览缓存”和“正式提交”两个阶段，风险等级从“中”下降到“低”。[GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L1571) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2110) [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L2161)
