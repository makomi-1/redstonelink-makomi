# 区块激活器core补发入队与强加载计费优化

## 1. 功能与语义、架构设计

本轮把区块激活器新增 `force_load + core` 的即时效果，从“本地直接补 transient ticket”改成“按真实 `triggerSource -> core` 定向补发一次 `sync`”，让未加载 `core` 自然进入现有跨区块队列与强制加载服务。入口仍然挂在区块激活器保存后的 `applyAfterUpsert(...)`，没有改变 `LinkChunkActivatorBlockEntity` 的调用边界，只收敛了 `core` 分支的即时语义。[LinkChunkActivatorBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkChunkActivatorBlockEntity.java#L249) [ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L26)

新的计划拆分仍保持 `resident` 和 `replay` 两类副作用分离：`resident` 继续直接补常驻票，`core + force_load` 则进入 `replayCores` 集合，再按 `core -> triggerSource` 反查来源并逐个触发单目标 `publishTriggerSourceCurrentOrPersistedSyncReplay(...)`；这保证了内部方向仍固定为 `triggerSource -> core`，没有引入反向写入语义。[ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L56) [ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L124) [LinkSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkSavedData.java#L345) [InternalDispatchDeltaRuleSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/InternalDispatchDeltaRuleSupport.java#L731)

## 2. 关键数据结构和算法性能分析

`ImmediateEffectPlan` 现在把原来的 `forceLoadCores` 收敛为 `replayCores`，构建阶段仍只对“本次新增进入当前生效集合”的 serial 做一次集合差分，复杂度保持在 `O(新增集合大小)`，没有额外引入全量扫描。[ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L163) [ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L185)

`replayCoreCurrentTruth(...)` 的代价是“新增 core 数 * 每个 core 的已链接来源数”。它不再直接对 chunk 做本地 bootstrap，而是依赖已有链接索引按需反查来源，避免了额外的世界级遍历。对于区块激活器当前每套节点集最多 `32` 个成员的约束，这个 fanout 仍处于可控范围内。[ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L124) [LinkSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkSavedData.java#L351)

强制加载计费方面，`tryForceLoad(...)` 现在先按 `ForcedChunkKey` 查 `forcedChunksUntilTick`。如果 chunk 已持票，仅续期，不再重复 `addTransientTicket(...)`，也不再重复消耗 `forceLoadCountThisTick / forceLoadCountBySource`。这把先前“按调用次数计费”的热点收缩成更接近“按首次拉起的新 chunk 计费”，能显著减少多来源或重复 replay 命中同一 chunk 的预算浪费。[CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L282) [CrossChunkDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchService.java#L678)

## 3. 数据流或调用链

保存后的调用链仍是：区块激活器更新持久化快照后，`LinkChunkActivatorBlockEntity.syncPlacedActivatorState()` 读取前后 entry，并把差异交给 `ChunkActivatorImmediateEffectService.applyAfterUpsert(...)`。新的 `core` 分支会进一步反查来源并发出标准 `SYNC_SIGNAL` delta，而不是自己直接碰 chunk 票据。[LinkChunkActivatorBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkChunkActivatorBlockEntity.java#L253) [ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L39)

补发后的投影链没有新增旁路：`publishTriggerSourceCurrentOrPersistedSyncReplay(...)` 继续按当前真值或持久化 replay 快照构造 `DispatchDeltaEvent`；`InternalDispatchDeltaProjector` 在目标未加载时统一转 `queueSyncSignal(...)`。因此这次 `core` 新增 replay 会自然复用现有队列、重试、强制加载判定与 TTL 策略，不会形成 activator 专用的第二条跨区块通道。[InternalDispatchDeltaRuleSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/InternalDispatchDeltaRuleSupport.java#L731) [InternalDispatchDeltaProjector.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/InternalDispatchDeltaProjector.java#L238)

自动化验证覆盖了两层：一层是计划语义，确认 `force_load + core` 新增成员进入 `replayCores` 而不是 resident；另一层是强制加载计费，确认已有持票 chunk 重复命中只续期、不重复扣预算。[ChunkActivatorImmediateEffectServiceTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/ChunkActivatorImmediateEffectServiceTest.java#L75) [CrossChunkDispatchServiceTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/CrossChunkDispatchServiceTest.java#L291)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全与语义边界上，这次设计明确依赖“补发的意义就是有来源”。因此如果新增 `core` 当前没有任何已链接 `triggerSource`，或所有来源都没有可恢复真值，本轮就不会再本地直接拉起 chunk。这是有意的语义收缩，但也意味着 `force_load core` 的即时生效前提更明确，需要后续玩法说明保持一致。[ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L124)

性能上，`tryForceLoad(...)` 的计费已经从“每次命中”优化到“首次新 chunk 命中”，但配置上限仍维持原来的硬夹紧。当前更合理的后续顺序仍是先观察新口径下的实际命中分布，再决定是否放宽 `forceLoad.maxPerTick / maxPerSourcePerTick` 的 parser 上限，而不是立即扩大上限掩盖重复计费问题。[CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L299) [CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L307)

兼容性方面，内部命名和方向仍完全使用 `triggerSource/core`，没有恢复旧术语输出，也没有改变 projector 的统一入队规则；因此现有 `sync`、target chunk load replay、source attach replay 仍共用同一套底层事件模型，扩展性保持稳定。[ChunkActivatorImmediateEffectService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/ChunkActivatorImmediateEffectService.java#L15) [InternalDispatchDeltaRuleSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/InternalDispatchDeltaRuleSupport.java#L777)

## 5. 并发冲突审查

本轮没有引入新的共享状态类型，仍然复用 `CrossChunkDispatchService.DispatchState` 中的 `forcedChunksUntilTick`、`forceLoadCountBySource` 与 `forceLoadCountThisTick`。关键变化是 `tryForceLoad(...)` 对这三个共享字段的写入顺序被收敛为“先看已有 chunk，再决定是否扣预算”，但读改写仍在既有服务端线程边界内执行，没有新增跨线程可见性问题。[CrossChunkDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchService.java#L678) [CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L282)

`resetForceLoadWindow(...)` 仍然只在 tick 边界清空预算计数；本轮改动故意让“已持票 chunk 的续期”跳过这个预算重置入口，因为它不应参与新 chunk 计费。这不会造成状态竞争，但会让预算值在仅有续期事件的 tick 内保持上一窗口值；这种行为是安全的，因为预算只在首次新 chunk 命中时才被消费。[CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L299) [CrossChunkDispatchTicketSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkDispatchTicketSupport.java#L493)

测试层已经专门加入“预置已有持票状态后再次命中”的用例，验证重复续期不会扩大预算计数或来源计数。这能直接防止后续并发语义或状态机重构时，把“已加载 chunk 的续期”误退回到“每次调用都扣费”的旧口径。风险等级评估为中低，主要风险来自未来若再引入新的 force-load 状态桶，需要同步维护这条去重判定。[CrossChunkDispatchServiceTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/CrossChunkDispatchServiceTest.java#L318)
