## 1. 功能与语义、架构设计

本次没有修改区块激活器业务实现，而是收紧 bench 用例的加载语义，让 `x44/x45` 的 dedicated 观测只反映“区块激活器对白名单/resident 的贡献”，不再混入 bench 默认整案 `forceload`。核心做法是给两条用例显式关闭 `autoLoadCaseChunks`，并改为只预加载最小 setup 区块；其中 `x45` 还在“重新加载激活器 -> 失活”之后补了一次 `self forceload remove`，避免为了让激活器重新附着而把相邻来源 chunk 一起带在线。[Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L349) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L1) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L1) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L117)

语义上保持 `triggerSource/core` 方向不变：`x44` 仍验证“激活态区块激活器让 3 个 `triggerSource` 具备 force-load 资格并驱动 3 个 `core` 自动上线”，`x45` 仍验证“激活态 resident 保持 3 个 `triggerSource` 在线，重新加载并失活后贡献撤销”。本轮只是修正验证口径，没有引入旧术语，也没有新增 API 依赖。[chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L71) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L129)

## 2. 关键数据结构和算法性能分析

这次改动落在 case 配置层，新增的数据结构只有 `benchForceLoadZones` 的常量矩形列表；runner 在 `Ensure-CaseChunksLoaded` 中按维度顺序线性遍历边界并发出 `forceload add`，复杂度仍是 `O(zones)`，对 dedicated 启动开销只增加固定常数，不改变功能执行期的 dispatch、resident ticket 或 link 解析复杂度。[Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L358) [Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L372) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L6) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L6)

`x45` 新增的 “unpower 后等待 4 tick 再移除 self forceload” 也是常数级时序步骤，主要是给方块态同步留出稳定窗口，避免把“激活器还没完成失活同步”与“resident 已撤销但 chunk 尚未脱离邻近加载影响”混在一起。性能影响仅是 dedicated case 增加 1 条命令和 4 tick 等待，量级可忽略。[chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L129) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L145)

## 3. 数据流或调用链

当前调用链是：bench runner 读取 case 配置后，先由 `Ensure-CaseChunksLoaded` 按 `benchForceLoadZones` 预加载 setup 区块，再进入 phase 时间线；`x44` 通过移除目标 chunk 与激活器自身 chunk 的 setup forceload，先证明目标 `core` 离线，再通过 3 个 `triggerSource` 的输入方波验证 force-load 生效并让 3 个 `core` 上线激活。[Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L349) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L88) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L113)

`x45` 的链路则是：先移除 source/self 的 setup forceload，验证 resident 激活态能保持 3 个 `triggerSource` 在线；随后仅重新加载激活器自身 chunk，让区块激活器重新附着并接收失活输入；等待 4 tick 完成失活同步后，再移除 self forceload，最后观测 3 个 `triggerSource` 全部转为 `online=false`。这个链路把“重新附着触发同步”与“最终离线观测”拆成了两个阶段，能更准确地定位 resident 贡献是否撤销。[chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L73) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L117) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L150)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

主要风险不在业务实现，而在 bench 观测口径。第一，凡是需要验证 unload/reload 语义的 case，只要忘记关闭 `autoLoadCaseChunks`，runner 就会重新把整案范围 `forceload add`，导致 dedicated 结果被 bench 自己污染；后续新增类似用例时应默认先评估是否改成显式 `benchForceLoadZones`。[Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L358) [Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L364)

第二，像 `x45` 这种需要“重新加载激活器自身 chunk 才能验证失活同步”的场景，如果 offline 断言对象与激活器 chunk 过近，就会被激活器 self reload 的邻近加载副作用干扰；因此建议保留“同步后再 remove self forceload”的双阶段结构，不要把 `unpower` 与最终离线断言直接贴在一起。[chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L119) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L141)

第三，`x44` 现在也显式收敛到最小 setup 区块，避免 future 里 runner 默认行为变化后出现“用例通过但其实没真正验证 force-load”的伪通过；这对后续继续扩展“多激活器/更大节点集”场景是正向的兼容性收紧，而不是破坏性变更。[chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L6) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L95)

## 5. 并发冲突审查

本轮没有改动 Java 运行时共享状态，也没有触碰 `PlacedChunkActivatorSavedData`、dispatch service 或 resident ticket 的并发边界；变更仅发生在 bench case 配置与单线程 RCON phase 时间线，线程级并发风险为低。[Bench.World.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.World.ps1#L349) [chunk_activator_force_load_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x44/chunk_activator_force_load_three_sources.json#L88)

需要注意的“冲突”主要是时序冲突而非线程冲突：如果在同一 dedicated case 中既依赖 self reload 完成状态同步，又立即拿邻近 chunk 做 offline 断言，就会出现观测重叠，表现为结果看起来像 resident/force-load 没撤销。`x45` 通过把 `unpower -> wait 4 tick -> remove self forceload -> wait 40 tick -> offline assert` 串行化，把这类时序覆盖风险降到了低级别；后续保持这种串行模板即可。[chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L129) [chunk_activator_resident_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x45/chunk_activator_resident_three_sources.json#L150)
