## 2. 关键数据结构和算法性能分析

参数层的核心数据结构是有序参数表。`Convert-BenchParametersToOrderedMap`、`Resolve-BenchParameterizedString`、`Expand-CaseConfigWithParameters` 把参数解析限定在 bench 配置装配期，避免为每个 case 再维护多份近似 JSON，同时保持输出顺序稳定，利于 summary 比对与脚本化处理。[Bench.Matrix.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.Matrix.ps1#L74) [Bench.Matrix.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.Matrix.ps1#L125) [Bench.Matrix.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.Matrix.ps1#L187)

延迟断言的关键算法从“仅覆盖率窗口判断”扩展成“覆盖率 + 精确延迟值断言”。`trace_sync_latency_collect` 现在会基于 `inputDelayTicks` 或 `referenceDelayTicks` 选择被评估的延迟数组，再计算最小/最大值与 `expectedDelayTicks` 比较；这避免了窗口检查只能证明“<= N tick”，却不能证明“恰好 N tick”的歧义。[Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L2656) [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L2838) [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L2878)

这段算法的复杂度仍然受原 trace 采样规模主导。本轮新增的成本主要是对已收集延迟数组做一次排序以取 `min/max`，相对 1024 规模样本是轻量级；而收益是专项断言可以直接区分 `window=1` 与 `window=2`，不再只能依赖 coverage ratio 推断。

最新游戏内结果表明，数据流已经可以稳定区分三个窗口：
- `window=1`：通过，source 延迟固定 `1` tick，core 相对 source 延迟固定 `1` tick。
- `window=2`：通过，source 延迟固定 `1` tick，core 相对 source 延迟固定 `2` tick。
- `window=0`：失败，source 仍为 `1` tick，但 core `matched=0`，失败集中在 `matched_ratio / delay_ticks / window_coverage`。

## 4. 安全、性能、兼容性、扩展性风险分析与建议

兼容性上，这轮改动没有改 bench matrix 中原始 case id，也没有改变 `triggerSource/core` 的内部语义，只是在 suite summary 层增加了逻辑 case id 与参数记录。对现有依赖 matrix case id 的调用方，仍可通过 `matrixCaseId` 回溯旧口径；风险主要在于若外部脚本历史上直接假定 `summary.caseIds` 等于 matrix case id，需要同步适配新字段。[BenchSuite.EntryPoint.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/BenchSuite.EntryPoint.ps1#L133) [BenchSuite.Results.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/BenchSuite.Results.ps1#L237)

验证风险当前集中在 `window=0`。`window=1/2` 已经通过，说明“参数化窗口验证 >0”成立；但 `window=0` 在 `all_sync` 条件下 core 完全未匹配，这提示它与旧专项“原本跑通”的测试口径并不完全等价，后续需要明确它究竟代表“即时生效基线”还是“同调度周期批提交但 referenceDelay=0”的新语义。

性能上，本轮新增的脚本逻辑只发生在功能专项 trace 分析阶段，不进入模组运行时主链路。bench 侧额外排序与参数展开的开销可接受，但 `delay_ticks` 输出中目前还保留了 `evaluatedMatched/delayCheckVersion` 诊断字段，后续如不再需要，建议在确认 `window=0` 语义后清理，避免长期污染结果格式。

建议顺序：
1. 先把 `window=0` 的目标语义写死，是“必须相对 source 0 tick”还是“允许 immediate 路径不用 batching”。
2. 如果目标是验证 `batchWindowTicks>=0` 的批提交语义，建议保留当前 `window=1/2` 断言结构，并单独为 `0` 设计更贴近运行时口径的专项。
3. 若确认不再需要诊断字段，再统一收口 `delay_ticks` 的结果结构，避免下游解析脚本对临时字段产生依赖。
