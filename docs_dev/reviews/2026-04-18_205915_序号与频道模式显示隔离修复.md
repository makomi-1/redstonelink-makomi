# 序号与频道模式显示隔离修复

## 1. 功能与语义、架构设计

- 本轮修复点集中在前端视图层，没有修改服务端真值、导出协议或 `triggerSource -> core` 的真实写入语义。serial 视图现在在入口处先切出 `connectionMode=serial` 的节点与边，再继续做聚合和可见性收敛，关键入口位于 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L584) 和 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L589)。
- 这样处理后，序号模式不再把纯频道节点和频道推导边混入主画布，也不会再把它们纳入序号模式的孤立节点池；对应孤立池收敛点在 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L911) 与 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L918)。
- 搜索口径也同步隔离，序号模式下只搜索 serial 节点，避免出现“主画布没有但搜索还能搜到频道节点”的不一致；对应实现位于 [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L221)。

## 2. 关键数据结构和算法性能分析

- serial 视图没有引入新的复杂数据结构，而是在现有 `GraphSnapshotBundle` 上构造了一份轻量的 `serialGraphBundle` 子集对象，再复用原有 `buildEdgeCountByNodeKey`、聚合收敛和布局逻辑，关键点在 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L598)。
- 该过滤步骤本质上是一次节点扫描加一次边扫描，复杂度约为 `O(N + E)`；后续聚合、布局的复杂度与原流程一致，因此本轮不会额外放大热路径复杂度。
- 相比去改服务端导出协议，这种前端消费层收敛的代价更小，且能同时覆盖“原始导出图”和“前端草稿预演图”两条来源路径，减少改动面。

## 3. 数据流或调用链

- serial 模式的数据流现在变成：`effectiveGraphBundle` -> 过滤出 serial 节点与边 -> 基于 serial 子图生成 actual node / aggregate / isolated pool -> ReactFlow 渲染，对应主链路在 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L584) 到 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L925)。
- 搜索链路则变成：`displayMode` 决定 `searchableNodes` 的节点口径 -> 应用搜索条件 -> 聚焦命中节点；本轮只改了口径源头，不改搜索应用与聚焦流程，关键点在 [GraphViewer.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/GraphViewer.tsx#L221)。
- 频道模式的数据流未改，仍然单独在 `buildChannelGraphCanvasView(...)` 里按 `connectionMode=channel` 与 `channel>0` 构建两级连接，因此两种模式的显示边界现已前端显式分离；频道视图入口在 [canvas.tsx](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/canvas.tsx#L924)。

## 4. 安全、性能、兼容性、扩展性风险分析与建议

- 安全风险低：本轮没有增加命令入口、保存协议或服务端状态写入点，属于纯前端显示层修复。
- 性能风险低：新增的是线性过滤，不会改变原有聚合与布局的数量级；同时因为序号模式不会再处理纯频道节点，某些场景下 serial 视图的实际计算量还会下降。
- 兼容性风险主要在“口径变化”：如果历史上有人把 serial 模式当作“显示所有节点但只看 serial 边”，这轮会把纯频道节点整体移出 serial 搜索与孤立池。但这与当前“序号和频道模式隔离”的需求一致。
- 建议后续若继续扩展其它显示模式，也沿用这种“先切模式口径子图，再做聚合/布局/搜索”的结构，避免把模式差异散落到后续各个阶段。

## 5. 并发冲突审查

- 前端共享状态没有新增复杂并发点。本轮只修改了 `useMemo` 数据来源和 serial 视图构建函数，没有新增异步写操作，也没有改变草稿保存时序。
- 由于没有改服务端真值链路，不存在新的读改写覆盖风险；当前修复只影响前端对已有 `effectiveGraphBundle` 的消费方式。
- React 渲染层面，serial 子图是纯派生数据，不会与现有 `graphDraft`、`savePhase` 或搜索应用状态形成新的重入链路。
- 风险等级：低。当前剩余风险主要是人工实测口径确认，而不是线程或并发一致性问题。
