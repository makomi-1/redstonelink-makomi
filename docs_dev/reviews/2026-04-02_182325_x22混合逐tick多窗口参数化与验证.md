# x22混合逐tick多窗口参数化与验证

## 1. 功能与语义、架构设计

- 本次改动将 mixed 逐 tick bench 从“仅 `window=0` 稳定”收敛为“单一参数化 case + suite entry 覆盖窗口值”的结构，核心入口在 [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1432) 和 [mixed_samechunk_direct_window0_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x22/mixed_samechunk_direct_window0_tick_assert.json#L1)。
- `Bench.FunctionalTrace.ps1` 新增 mixed `sync/pulse/toggle` 三段模板构造，并在 `Resolve-TraceTickExpectations` 中注册 `mixed_direct_sync/mixed_direct_pulse/mixed_direct_toggle` 三类模板，以便同一 case 通过窗口参数生成不同期望序列。[Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1432) [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1545)
- `x22` case 改为带 `dispatchBatchWindowTicks` 参数的单一 case，并保留 `sync/pulse/toggle` 三段 target 断言的分段锚定方式，避免后续 `pulse/toggle` 相对首个 `sync` 锚点漂移造成假失败。[mixed_samechunk_direct_window0_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x22/mixed_samechunk_direct_window0_tick_assert.json#L3) [mixed_samechunk_direct_window0_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x22/mixed_samechunk_direct_window0_tick_assert.json#L126)
- suite 已切换为三个 entry 统一指向参数化后的 `x22` case，并通过 `parameters.dispatchBatchWindowTicks` 与服务端配置 `crosschunk.dispatch.batchWindowTicks` 分别覆盖 `0/1/2`。这一点与 `x21` 的参数化编排方式保持一致。[functional-mixed-direct-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-direct-debug.json#L15)

## 2. 关键数据结构和算法性能分析

- mixed 期望构造采用“固定小段功率序列 -> 通用样本对象”方式，新增的 `Build-TraceExpectationsFromPowerSequence` 避免了三段模板分别重复拼装 `pscustomobject`，逻辑成本低且不会对 bench 主路径带来额外复杂度。[Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1432)
- `Resolve-MixedDirectWindowTicks` 将窗口值限制在 `0..2`，与运行时配置边界一致，避免模板侧产生运行时不支持的无意义窗口值。[Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1445)
- 三个 mixed 模板都只生成十几个 tick 以内的短序列，复杂度为 `O(n)` 且 `n` 极小，对 `trace_read_tick_assert` 的窗口搜索负担主要仍来自已有 trace 样本数量，而不是模板构造本身。[Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1454) [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1471) [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1493)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

- 风险一：当前 `x22` 参数化已完成，但 `window=1/2` 在 target 侧实测未表现出相对于 `jobStartTick` 的额外固定延迟，这比简单的 `x21` 一拍锚点偏移更强，至少在 `sync` 段上已经显示出“0/1/2 三窗口对 target 可见起点几乎一致”的现象。相关模板和入口代码见 [Bench.FunctionalTrace.ps1](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/lib/Bench.FunctionalTrace.ps1#L1454) 与 [mixed_samechunk_direct_window0_tick_assert.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x22/mixed_samechunk_direct_window0_tick_assert.json#L126)。
- 风险二：由于 `x22` 当前只对 target 做逐 tick 断言，没有同时记录 source 的逐 tick 命中窗口，因此还不能完全排除“`jobStartTick`/anchor 模型存在与 `x21` 同类偏移”这一可能。若要继续收敛，应优先补 source 侧逐 tick 参考窗口，或给 `trace_read_tick_assert` 增加类似 `x21` 的 reference-phase 对齐能力。相关结果入口见 [summary.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/run/profiles/bench-suite-results/20260402_181727/summary.json#L48) 和 [summary.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/run/profiles/bench-suite-results/20260402_182107/summary.json#L45)。
- 风险三：`x23/x24` 旧静态 case 仍留在仓库中但已不再被当前 suite 使用，短期不会影响运行；若后续确认参数化 `x22` 成为唯一入口，建议再做一次 bench 资产清理，避免重复 case 长期误导维护者。当前 suite 切换点见 [functional-mixed-direct-debug.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/functional-mixed-direct-debug.json#L15)。
