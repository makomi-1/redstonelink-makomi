# graph保存回包瘦身

## 1. 功能与语义、架构设计（关键方法和入口）

本轮把 graph save 成功响应改成“最小增量回包”而不是“全量受影响节点回包”。服务端入口仍然是 `GraphWriteService.submit(...)`，真实保存语义没有变化，仍只执行 `triggerSource -> core` 真值写入；变化点只在 save success 响应的序列化策略上。[GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L44) [GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L138)

服务端 JSON 协议层通过 `GraphWriteJsonSupport.buildAppliedResponse(...)` 和 `appendUpdatedNodes(...)` 区分 applied 响应与 conflict/rejected 响应：applied 只序列化 `nodeKey + sourceRevision + coreRevision`，其余响应仍保留完整节点信息，避免丢失冲突诊断能力。[GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L86) [GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L199)

前端入口仍是 `parseGraphWriteResponse(...)` 和 `applyUpdatedNodeStates(...)`，但现在把 `updatedNodes` 视为“可选字段补丁”，允许 save success 响应只带 revision，不再要求必须返回 alias/displayText/connectionMode/channel 全字段。[graphTypes.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/graphTypes.ts#L254) [draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L494)

## 2. 关键数据结构和算法性能分析

性能关键点在于 `updatedNodes` 的单节点载荷体积。之前每个节点都包含 `nodeType/serial/alias/displayText/connectionMode/channel/sourceRevision/coreRevision`，大批量频道保存时会快速逼近网络层 `GRAPH_SAVE_JSON_MAX_LENGTH`。现在 applied 响应按同样的去重集合输出，但单节点只保留 revision 所需最小字段，时间复杂度仍是 O(n)，常数项明显下降，响应体尺寸也显著减小。[GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L199)

服务端 `submit(...)` 仍然按受影响节点收集增量，但成功路径改为调用 `buildAppliedUpdatedNodeState(...)`，不再为 save success 额外做别名解析和完整展示态构造，进一步降低了大批量保存时的常数开销。[GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L68) [GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L659)

前端解析层新增了基于 `nodeKey` 反推 `nodeType/serial` 的兼容逻辑，因此即使服务端不再显式返回这些字段，补丁仍能稳定落到对应节点，不需要额外整图刷新。[graphTypes.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/graphTypes.ts#L134) [graphTypes.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/graphTypes.ts#L254)

## 3. 数据流或调用链

调用链仍然是：网页端 `submitGraphSave(...)` 发起 `/api/graph/save`，服务端进入 `GraphWriteService.submit(...)`，保存完成后走 `GraphWriteJsonSupport.buildAppliedResponse(...)` 生成最小 success JSON，再回到前端由 `parseGraphWriteResponse(...)` 解析、`applyUpdatedNodeStates(...)` 把 revision 合并进本地已应用草稿结果。[draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L564) [GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L44) [GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L86) [graphTypes.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/graphTypes.ts#L254) [draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L494)

这个调用链的重要语义是：“画布结构与显示字段以本地草稿应用结果为主，服务端 success 回包只负责补齐 OCC 所需 revision 和新的 `graphRevision`。”因此 save success 不再承担“整图回显”职责，从而规避大响应体问题。[GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L138) [draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L494)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全上，这轮没有放宽任何权限、限流或方向校验，仍保持 `triggerSource -> core` 单向写入和原有限流/OCC 约束；仅改变成功回包的字段裁剪策略，风险主要在兼容层而不在真值层。[GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L44)

兼容性上，旧前端如果仍假设 `updatedNodes` 一定包含完整字段，可能无法消费新的最小 success 回包；但当前仓库中的网页端已同步升级为“可选字段补丁”模型，因此同仓版本内兼容性成立。[graphTypes.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/graphTypes.ts#L254) [draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L494)

残余风险在于：如果单次保存影响节点规模极大，哪怕只回 `nodeKey + revision`，仍可能继续逼近 `16384` 网络上限。这一版已经把常见高开销字段去掉，但它不是理论上的无限扩展方案；若后续仍有极端超大保存场景，需要再评估 revision 分块或保存成功后的轻量重拉机制。[GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L199)

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

本轮没有新增共享可变状态。服务端仍在原有 `submit(...)` 线程边界内完成解析、写入和 JSON 序列化；前端仍在收到响应后一次性把补丁合并回本地 graph 基线，没有引入新的跨线程缓存或延迟提交对象。[GraphWriteService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteService.java#L44) [draft.ts](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/webapp/src/components/graphViewer/draft.ts#L494)

并发风险等级评估为“低”。原因是改动没有改变 OCC 判定本身，只是改变了成功后的回包体积和前端补丁合并策略；只要 `nodeKey -> node` 的映射稳定，补丁应用就是幂等的。同一节点多次出现在 `updatedNodes` 时仍由服务端 `dedupeUpdatedNodes(...)` 稳定收口，不存在前端多次覆盖顺序漂移的新风险。[GraphWriteJsonSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/GraphWriteJsonSupport.java#L310)
