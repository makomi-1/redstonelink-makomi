# 节点容器回收与创造放置策略第二轮

## 1. 功能与语义、架构设计

本轮把智能节点容器从“仅存放与放置节点”扩展为“放置 + 回收 + 创造模式放置策略”统一入口。核心语义分成两条：一条是容器持久化状态新增 `creativeAutoConsumeEnabled`，用于决定创造模式下是否真实消耗容器内节点；另一条是 `Shift+右键` 命中节点时触发受控回收，而不是走普通破坏拾取链。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L39) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L59) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L225)

受控回收被抽到独立 helper：先用真实掉落链解析节点物品，再优先写入容器，剩余部分回退为世界掉落，最后显式取消待退役任务。这样设计能复用既有节点掉落元数据继承逻辑，不需要再手搓序号/配置回填代码。[SmartNodeContainerRecoverySupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerRecoverySupport.java#L43) [LinkNodeRetireEvents.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkNodeRetireEvents.java#L178)

客户端层面只做最小扩展：容器菜单和界面新增“创造自动消耗”控制项，但不改变当前容器布局模型，也不把定向编辑推广到可见节点，保持第二轮边界清晰。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L24) [SmartNodeContainerScreen.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/screen/SmartNodeContainerScreen.java#L21)

## 2. 关键数据结构和算法性能分析

关键数据结构仍然是节点容器的轻量快照与 54 格库存，只是快照从“三元组”扩展成了“四元组”：`selectedType + autoSort + creativeAutoConsume + itemCount`。所有控制状态仍然写在单个 `ItemStack` 的 `CUSTOM_DATA` 中，读写成本是常量级，不引入新的世界级持久化对象。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L39) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L68) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L349)

回收算法是纯局部常量/线性小规模处理：先对单个方块解析掉落，再把结果尝试插入首个空槽位，复杂度约为 `O(dropCount * slotCount)`，在本模组节点掉落通常只有 1 个物品的前提下，成本可控。辅助方法 `findFirstEmptySlot/tryInsertNodeItem` 也为后续容器协作扩展提供了复用入口。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L248) [SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L266) [SmartNodeContainerRecoverySupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerRecoverySupport.java#L63)

放置算法在原有逻辑上新增了一个分支判断：若创造玩家关闭自动消耗，则放置时保留容器内节点，仅复制出一个临时放置栈参与 `BlockItem.place(...)`；否则继续沿用原有消耗式放置链。这个判断是常量级，不增加额外世界扫描。[SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L94) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L280)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

安全层面，本轮没有新增外部接口或高危命令路径，主要风险是“回收后误退役”。当前通过显式 `cancelPendingRetire(...)` 把受控回收与待退役系统打通，已经覆盖了这个核心缺口。建议后续若增加更多受控保留路径，统一复用这一入口而不是再写一套匹配逻辑。[LinkNodeRetireEvents.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkNodeRetireEvents.java#L178) [SmartNodeContainerRecoverySupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerRecoverySupport.java#L85)

性能层面，回收只处理单个命中节点，没有跨区块扫描；容器状态写回仍是单物品 NBT 更新。唯一需要关注的是自动排序开启时每次回收/放置都会做一次 54 格排序，不过在当前容器规模下这属于低成本操作。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L181) [SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L266)

兼容性方面，本轮不改节点序号模型、不改 `triggerSource/core` 方向语义、不引入 `Mixin`，对既有节点掉落链的复用也降低了行为偏差风险。扩展性方面，`tryInsertNodeItem`、`RecoveryResult` 和新增容器控制状态都可以继续支撑后续香草编辑工具或红石场发生器的“自动回收/再部署”需求。残余风险在于：当前回收对象仍限定为容器允许的节点类型，没有扩展到过滤器、区块激活器等更复杂配置块。[SmartNodeContainerData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerData.java#L266) [SmartNodeContainerRecoverySupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/SmartNodeContainerRecoverySupport.java#L29)

## 5. 并发冲突审查

风险等级评估为“低”。本轮所有状态修改仍发生在主线程的玩家交互链上：容器按钮点击、右键放置、潜行回收都在服务器主线程完成，没有引入新的异步任务或后台共享状态。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L137) [SmartNodeContainerItem.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/item/SmartNodeContainerItem.java#L225)

共享状态主要是容器 `ItemStack` 的 `CUSTOM_DATA` 与待退役内存表。前者通过 `persistToHeldItem()` 串行写回，后者通过 `cancelPendingRetire(...)` 在同一服务器实例内同步删除，不存在新的并发写入入口。真正需要持续注意的是：如果未来增加客户端预测或异步容器同步，`container.copyContents()` 和待退役状态表都需要继续保持服务端主线程唯一写入约束。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L276) [LinkNodeRetireEvents.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkNodeRetireEvents.java#L178)

重入风险主要在容器菜单回调链：自动排序开启时，`replaceContents(...)` 会再次触发 `setChanged()`。当前通过 `sortingContents` 与 `suppressCallback` 双层保护避免了重复回写和递归排序，风险可控。[SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L230) [SmartNodeContainerMenu.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/menu/SmartNodeContainerMenu.java#L318)
