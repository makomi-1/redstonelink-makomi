## 2. 关键数据结构和算法性能分析
- resident 去重统计采用 `LinkedHashSet<ResidentEntryKey>`，核心构造位于 [CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L157) 、[CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L167) 与 [CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L186)；时间复杂度与当前 resident 总量线性相关，仅在命令保存/GUI 保存等低频写路径执行，不进入 tick 热路径。
- 区块激活器覆盖预估通过遍历 `entriesSnapshot()` 并跳过目标条目实现，自引用定位依赖 [PlacedChunkActivatorSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/PlacedChunkActivatorSavedData.java#L476) 与 [PlacedChunkActivatorSavedData.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/PlacedChunkActivatorSavedData.java#L483) 暴露的只读位置访问器，避免把私有 key 类型泄露到外部服务。
- 区块激活器 resident 节点集仍复用 `SerialParseUtil.parseTargetsOrdered(...)` 做一次性规范化去重，入口在 [CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L333)；单次解析上限由现有 `MAX_NODE_SET_SIZE=32` 约束，因此额外成本可控。
- 命令侧 `withSerial(...)` 只在 resident add 路径创建一个小型去重集合，位置见 [CrossChunkCommandRegistry.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/command/crosschunk/CrossChunkCommandRegistry.java#L808)；不会影响批量 dispatch、resident ticket 同步等主流程性能。

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- 兼容性：`syncTargetChunkLoadReplay.enabled` 已从配置层彻底移除，旧配置文件中的该键会被忽略；模板与使用说明已同步，但外部脚本若仍依赖该键，需要按新语义改为仅使用 `crosschunk.syncTargetChunkLoadReplay.immediateAttemptFirst`。相关变更点见 [RedstoneLinkConfigTemplate.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/config/RedstoneLinkConfigTemplate.java#L442)。
- 语义风险：本轮 resident 上限拦截覆盖了“命令 resident 写入”和“已放置区块激活器保存”两类主写入口，但对历史已保存配置、手持物品预配置后再落地激活等运行时路径仍属于残余观察项；建议后续若要绝对封死绕行路径，再评估是否把上限下沉到激活器运行时激活流程。当前相关入口见 [ChunkActivatorNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/ChunkActivatorNetworkServerHandlerSupport.java#L148)。
- 性能：resident 去重统计是写时线性扫描，不在 tick 热路径；在当前 resident 总量较低、激活器节点集上限 32 的前提下风险低。若后续 resident 配额继续上调或扩展到更多实体来源，建议考虑维护增量快照而不是每次重建集合。现实现集中在 [CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L157)。
- 扩展性：resident 统计服务已拆出“当前计数 / 手动覆盖后 / 激活器覆盖后”三类入口，未来若再加入第三类 resident 贡献源，可继续在同一服务内追加聚合源，避免命令、GUI、票据同步各自复制逻辑。

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）
- 共享状态：本轮新增逻辑只读取 `CrossChunkWhitelistSavedData`、`PlacedChunkActivatorSavedData` 与配置快照，不新增后台线程或异步共享容器；关键读路径在 [CrossChunkEffectiveWhitelistService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/CrossChunkEffectiveWhitelistService.java#L157)。
- 读改写覆盖：resident 上限校验是“先读当前有效集合，再写单一目标”的典型检查后写入模型。当前命令入口与区块激活器网络保存都运行在服务端主线程上下文，默认不存在多线程并发写入同一世界数据的竞争；相关入口见 [CrossChunkCommandRegistry.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/command/crosschunk/CrossChunkCommandRegistry.java#L777) 与 [ChunkActivatorNetworkServerHandlerSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/ChunkActivatorNetworkServerHandlerSupport.java#L148)。
- 重入/线程边界：`LinkNodeLifecycleDispatchEvents` 的改动仅删除一个配置分支，不引入新的回调重入；区块激活器主题色改动纯客户端渲染常量替换，也不影响线程边界。对应位置见 [LinkNodeLifecycleDispatchEvents.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkNodeLifecycleDispatchEvents.java#L218) 与 [LinkSerialOverlayRenderCommon.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/client/java/com/makomi/client/render/LinkSerialOverlayRenderCommon.java#L64)。
- 风险等级：低。当前实现没有引入新的跨线程状态同步点；主要残余风险仍是“未经过本轮主写入口的历史或外部路径”可能绕过 resident 上限，这属于语义覆盖范围问题，不是线程安全问题。
