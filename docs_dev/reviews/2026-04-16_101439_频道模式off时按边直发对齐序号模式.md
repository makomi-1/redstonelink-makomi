## 1. 功能与语义、架构设计（关键方法和入口）
- 本次改动只收紧频道模式 loaded direct 进入中间层的条件：`crosschunk.directBatching=off` 时，不再进入 `ChannelDispatchScheduler`，直接按边派发，与序号模式对齐；其余模式保持现状。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L273) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L311) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L315)
- 为避免条件散落在方法内部，新增了包级 helper `shouldStageLoadedTargetsIntoChannelBucket(...)`，把“仅 `triggerSource -> core`、来源是频道模式、频道合法、且 `directBatching!=OFF`”的判定集中到一个入口，便于复用和测试。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L602)
- 语义对齐检查结果：内部和测试仍统一使用 `triggerSource/core`，方向仍是 `triggerSource -> core`；未引入旧术语持久化或 API 依赖，兼容边界不变。相关入口仍复用原有 `dispatchInternal(...)` 主流程。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L273)

## 2. 关键数据结构和算法性能分析
- 性能上没有新增持久状态或运行时桶，只是提前剪掉 `OFF` 场景的频道中间层，因此 `directBatching=off` 时少了一次“同频道收口 -> 再分发”的中间步骤，直接回落到已有按边派发分支。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L370)
- 该判定是常量级布尔计算，不改变原有目标遍历复杂度；`ALL_DIRECT/QUEUED_ONLY` 下的频道中间层与 `core` 批调度行为都未被触碰，因此没有引入新的时间窗或额外合并成本。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L313) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L315) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L794)
- 新增测试直接覆盖 helper 判定，避免为了验证一个布尔分支去构造高成本的世界/频道拓扑集成场景，回归成本低且稳定。[LinkedTargetDispatchServiceTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkedTargetDispatchServiceTest.java#L264)

## 3. 数据流或调用链
- 调用链仍然是：触发入口调用 `dispatchInternal(...)` -> 解析来源模式和批打包模式 -> 对每个 loaded 目标决定“进频道中间层”还是“直接按边派发”。这次改动仅影响这一处分流，不改 pending queue、跨区块队列、过滤器和后续通知逻辑。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L273) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L370) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L401)

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- 安全与兼容性风险较低：本次不改存档结构、不改配置键、不改频道图或普通边的持久化模型，也未变更用户可见命令或 UI 行为。核心影响仅在运行时 loaded direct 分流条件。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L602)
- 需要注意的边界是：`dispatch.batchWindowTicks>0` 时，频道模式的延迟仍然属于后续 `core` 批层，而不是频道层自身。这是本轮明确保留的现状，不是遗漏；如果未来要把窗口迁到频道层，需要单独设计，不能在现有分流条件上继续叠加。[LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L313) [LinkedTargetDispatchService.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkedTargetDispatchService.java#L315)
- 建议后续若继续演进频道模式，优先保持“一个模式只在一层持有窗口/收口职责”的原则，避免频道层和 `core` 层同时承担同类批处理语义。
