# 1. 功能与语义、架构设计（关键方法和入口）

## 2. 关键数据结构和算法性能分析
本次不改运行时算法复杂度，主要是测试侧口径收紧。之所以弃用原来的短 `trace_read_tick_assert`，是因为该 phase 会在锚点后的可搜索窗口中寻找任意一段匹配序列；当期望只包含 2 个样本时，表达能力过弱，无法稳定代表 handoff 边界。改成若干 `trace_latest_assert_core` 稳态点后，bench 扫描负担更小，语义也更直接。

## 3. 数据流或调用链
运行时语义仍由 `core` 端结构真值与仲裁优先级决定：`SYNC > PULSE > TOGGLE`。读档后，目标端会从持久化的并发桶中恢复 `sync/pulse/toggle` 贡献，并据此重建 authority 与派生态；因此 `r05` 应验证的是“重启后的恢复仲裁链”，而不是把 `pulse/toggle` 描述成生命周期 replay。

## 4. 安全、性能、兼容性、扩展性风险分析与建议
风险主要在测试语义层，而不在运行时兼容性。本次已去掉容易把“观测到过两拍 `pulse`”误当成“设计上正确 handoff”的弱断言，但 `r05` 仍以稳态检查点为主，尚未精确建模“移除 `sync` 时 pulse 剩余有效期”的逐 tick 全窗口真值。若后续要进一步收紧，应优先补 bench 对剩余 `pulse` 生命周期的参考相位，而不是重新回到短样本拟合。
