# core OCC参数位序修复

## 1. 功能与语义、架构设计（关键方法和入口）

- 本轮修复点集中在 `core` OCC 的薄包装入口：`PairingOccSubmissionSupport.submitCore(...)` 仍通过 [PairingOccSubmissionSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/PairingOccSubmissionSupport.java#L132) 调用 `LinkOccSupport.resolveCoreConflict(...)`，但该入口此前把 `expectedCoreRevision` 与占位 `0L` 传反，导致 `core` 冲突总是按 `0` 比较。现已在 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L59) 修正为“真实 `expectedCoreRevision` 进入 `expectedCoreRevision` 槽位，未使用的 `expectedSourceRevision` 仍用 `0L` 占位”。
- 通用比较语义保持不变：`resolveTargetConflictWithCurrentBaseline(...)` 仍在 `CORE` 分支只比较 `expectedCoreRevision` 与 `currentBaseline.coreRevision()`，未改动 `triggerSource/core` 语义，也未改动真实写入方向 `triggerSource -> core`，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L93) 与 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L123)。
- 为避免同类薄适配层错误再次漏过，本轮新增了直接覆盖 `resolveCoreConflict(...)` 的回归测试，分别验证“匹配 revision 不应冲突”和“冲突结果保留真实 `expectedCoreRevision`”，见 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L19) 与 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L33)。

## 2. 关键数据结构和算法性能分析

- 本轮没有引入新的数据结构，也没有改变 `RevisionBaseline`、`OccConflict` 或 `LinkSavedData` 的读写复杂度；修复只是在现有 O(1) 的包装调用里交换两个 `long` 参数的顺序，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L59)。
- 新增测试使用已有的 `LinkSavedData.addTriggerSourceCoreLink(...)` 推进一次 `coreRevision`，再直接调用 OCC helper 断言结果，不引入额外高成本依赖或集成环境，见 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L20) 与 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L34)。

## 3. 数据流或调用链

- `core pairing` 提交链仍是“客户端提交 `expectedCoreRevision` -> `PairingOccSubmissionSupport.submitCore(...)` -> `LinkOccSupport.resolveCoreConflict(...)` -> `resolveTargetConflictWithCurrentBaseline(...)` 的 `CORE` 分支比较”，本轮只修正其中 `resolveCoreConflict(...)` 的参数映射，不改变调用链层级，见 [PairingOccSubmissionSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/network/PairingOccSubmissionSupport.java#L132)、[LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L59)、[LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L123)。
- 回归链路则直接打在 helper 层，避免再次被 GUI、网络包或其他 `core` 事件混淆；这使问题能够在最小范围内复现并锁定，见 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L19)。

## 4. 安全、性能、兼容性、扩展性风险分析与建议

- 安全与语义边界：本轮未引入任何新的 API 依赖，也未放宽方向约束；`triggerSource/core` 命名与 `triggerSource -> core` 真实写入方向保持不变。风险等级：低，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L59)。
- 兼容性：修复仅影响此前错误的 `core pairing` OCC 比较值，不改变冲突消息 key、payload 结构和外部命令格式；已有的 `core_revision` 文案仍复用原 key。风险等级：低，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L130)。
- 扩展性建议：对同时承载多套语义的通用 helper，后续若继续保留连续同类型位置参数，必须维持“包装层直测”；否则编译器无法帮助发现错槽位问题。当前新增测试已对这一点建立门禁，见 [LinkOccSupportTest.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/test/java/com/makomi/data/LinkOccSupportTest.java#L33)。

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

- 共享状态：本轮没有新增共享状态，也没有改变 `LinkSavedData` 的 revision 推进路径；真正的共享状态仍是现有 `graphRevision/sourceRevision/coreRevision` 与链接集合。风险等级：低，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L123)。
- 读改写覆盖：修复后，`core pairing` 提交终于会把客户端上报的真实 `expectedCoreRevision` 送进 `CORE` 分支比较，避免把所有 `core` 提交都误判成“以 0 为基线”的伪冲突。风险等级：低，见 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L64) 与 [LinkOccSupport.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/data/LinkOccSupport.java#L124)。
- 重入与线程边界：修改仅发生在纯函数式 helper 内，没有新增异步回调或跨线程共享对象；测试也只做单线程内存态断言。残余风险：无新增线程边界风险。
