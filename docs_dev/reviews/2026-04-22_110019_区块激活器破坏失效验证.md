## 3. 数据流或调用链

当前验证链路是：bench 先根据 `benchForceLoadZones` 拉起最小 setup 区块，放置 3 个 `triggerSource` 与 1 个区块激活器；激活器配置为 `resident` 并通电后，先移除 source/self 手工 forceload，验证 resident 激活态仍让 3 个来源在线；再临时 readd self forceload 让激活器方块实体重新附着，随后执行 `setblock ... air` 触发真实物理移除；最后去掉这层临时 self forceload，观察来源离线。[chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L79) [chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L117) [chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L139)

调用层面，这条 case 对应区块激活器的“物理移除”分支，而不是普通失活分支；因此它验证的是 `onRemove -> markPhysicalRemovalInProgress -> setRemoved -> removePlacedActivatorState` 这条删除 persisted activator 条目的链路是否最终体现在 `triggerSource online=false` 上。虽然本轮未改 Java 代码，但 dedicated case 直接对这条调用链提供了回归覆盖。[LinkChunkActivatorBlock.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/LinkChunkActivatorBlock.java#L118) [LinkChunkActivatorBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkChunkActivatorBlockEntity.java#L168) [LinkChunkActivatorBlockEntity.java](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/src/main/java/com/makomi/block/entity/LinkChunkActivatorBlockEntity.java#L215)

## 4. 安全、性能、兼容性、扩展性风险分析与建议

本轮主要风险仍然是测试口径污染，而不是业务安全风险。第一，任何需要验证 unload/reload/physical remove 的 case，都必须像本案一样显式关闭 `autoLoadCaseChunks`；否则 bench 默认加载会导致“逻辑已失效但节点仍在线”的伪结果。[chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L6)

第二，物理破坏前必须先让激活器自身 chunk 重新附着，否则破坏动作根本不会命中真实方块实体生命周期；但这层 readd self forceload 只应短暂存在，之后必须移除，否则最终 offline 断言会再次被外部加载条件污染。[chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L117) [chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L139)

第三，当前只补了 `resident` 物理破坏用例，没有单独补 `force_load` 物理破坏口径；这符合本轮“最小粒度实现”的原则，但如果后续需要更完整覆盖，可以再补一条“物理破坏后 target 不再被 auto-load 拉起”的 `force_load` dedicated case。[regression-lifecycle.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/suites/regression-lifecycle.json#L100)

## 5. 并发冲突审查

本轮没有改动 Java 共享状态、ticket 缓存或持久化结构，因此线程级并发风险为低。新增内容只是在 bench 单线程 phase 时间线上顺序执行命令，不会与运行时并发写逻辑产生新的共享状态覆盖风险。[chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L48)

需要关注的是“时序冲突”而非线程冲突：如果把 readd self forceload、physical remove、最终 offline assert 压在同一瞬间，容易把“重附着同步”和“删除后卸载”混成一个不可判定结果。本用例通过 `reload -> physical remove -> wait 6 tick -> remove self forceload -> wait 40 tick -> offline assert` 的分段结构，把这类时序覆盖风险降到了低级别。[chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L123) [chunk_activator_resident_physical_remove_three_sources.json](/d:/OpenProjects/RedstoneLink/rl-release-no-mixin/tools/bench/cases/functional/x46/chunk_activator_resident_physical_remove_three_sources.json#L145)
