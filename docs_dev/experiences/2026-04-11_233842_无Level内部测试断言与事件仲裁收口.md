# 阻塞点

这轮“`sync` 来源状态 / `toggle,pulse` 目标事件结果”收口时，内部测试一度出现两类混淆：

- 纯内部测试没有 `Level`，直接断言 `active/resolvedOutputPower` 容易误判实现是否正确。
- 仲裁器里还残留了一条“活着的 `pulse` 永远压过 `toggle`”的隐藏规则，和“先比时间、同时间再比固定优先级”的设计不一致。

# 现象

- `ActivatableTargetBlockEntityInternalTest` 在大部分结构真值断言已经正确的情况下，仍有多条用例显示 `active=false` 或 `resolvedOutputPower=0`，看起来像回退失败。
- batch invalidation / later toggle 场景里，later `toggle` 明明时间更晚，`getEffectiveMode()` 仍停在 `PULSE`。

# 原因

- `ActivatableTargetObservationComponent.applyResolvedState(...)` 在 `level==null` 时会直接返回，因此纯内部测试里 `active/resolvedOutputPower` 不会随着结构真值一起刷新；这两个字段更适合在带 `Level` 的链路或 load/save 场景断言。
- `ActivatableTargetArbitrationComponent.pickWinner(...)` 旧实现把 `PULSE` 特判成“只要存在就直接赢过 `TOGGLE`”，没有真正执行全模式统一的时间优先比较。

# 解决方法

- 纯内部逻辑测试改为优先断言 `getEffectiveMode()`、`toggleState`、`pulseSnapshotRecorded`、`toggleSnapshotRecorded` 这类由结构真值直接驱动的字段；只有读档重建等路径再断言 `active`。
- 仲裁器改为统一使用 `pickMoreRecentCandidate(...)` 在 `SYNC/PULSE/TOGGLE` 三类候选之间做时间优先比较，同时间再按 `SYNC > PULSE > TOGGLE` 固定优先级裁决。

# 复用建议

- 以后写无 `Level` 的 block entity 内部测试时，先确认目标字段是否依赖 `applyResolvedState(...)` 或其它需要世界上下文的桥接逻辑；若依赖，就不要把它当结构真值断言主口径。
- 只要设计写的是“先比时间、同时间固定优先级”，就避免在候选挑选阶段再塞额外的模式特判；否则很容易留下隐藏例外，后续只有在跨模式回退/失效场景里才会暴露。
