# 转发器延迟 trace 观测修复经验

生成时间：2026-04-24 18:56:39
文件名：2026-04-24_185639_转发器延迟trace观测修复经验.md

## 阻塞点

- bench 已经能放置转发器，但 `repeater_block` 的虚拟 `triggerSource` 不支持 `node get` runtime / `node trace mount`，导致延迟用例无法直接观测转发器输出态。
- 即使补上 trace 入口，若把 `sync source` 的“可见 trace 起跳 tick”直接当作转发器延迟基线，也会得到错误的 0tick 结论。

## 解决方法

- 在 `NodeRuntimeProbe` 中为 `LinkRepeaterBlockEntity` 单独补 `SYNC_TRIGGER_SOURCE` 分支，并用转发器的 `replaySyncSnapshot()/dispatchedOutputPower` 构造 trace 快照，确保观测的是已延迟派发后的真实输出。
- bench 用例把“转发器延迟”改为相对输入启动 tick 直接断言 `1tick/2tick`，再把“目标 core 不额外加 tick”单独做成“相对转发器输出为 0tick”的二层断言。

## 可复用结论

- 遇到“单方块承载双身份”的虚拟节点时，先补 runtime probe，再写 bench trace；否则很容易出现“可放置、可配对、不可观测”的假完成状态。
- 写延迟类 trace 用例时，必须先核对“真实派发 tick”和“来源可见输出 tick”是不是同一个层次；如果不是，不能默认把来源可见 trace 当作传播延迟基线。
