# quick-link核心侧顺序稳定与反馈映射

## 阻塞点

1. quick-link 复用 `LinkSetExecutionService.prepareConfirmedReplace(...)` 与 `CoreLinkEditingService.prepareConfirmedReplace(...)` 后，失败反馈类型变成了命令层 `OperationFeedback`，不能直接塞回 `QuickLinkOperationFeedback`。
2. `core` 视角的一跳修改在构造“当前来源集合 + 缓存来源集合”的目标列表时，如果直接从 `Set<Long>` 保留迭代顺序，会让 append/remove 结果顺序不稳定，测试容易抖动，后续文档示例也难保持一致。

## 解决方法

1. 在 `QuickLinkApplyService` 增加统一转换入口 `toQuickLinkFeedback(...)`，把命令层结构化反馈显式映射回 quick-link 自己的反馈类型，再继续走 HUD / OCC summary / network 回执链路。
2. `core` 视角构造目标来源列表时，不直接复用 `Set` 迭代顺序，而是先把当前来源集合归一化成升序列表，再叠加缓存来源集合的编辑模式逻辑：
   - `replace`：直接使用缓存顺序
   - `append`：当前集合升序在前，缓存新增项按缓存顺序补到后面
   - `remove`：从当前集合升序列表里删掉缓存命中的项

## 可复用结论

1. 只要 quick-link 开始复用命令层/编辑层准备结果，就不要假设两边的反馈类型天然兼容，最好在边界层做一次显式转换。
2. 任何“从图索引 `Set` 投影成用户可见列表”的 quick-link/core 视角逻辑，都应先定义稳定顺序，否则测试、日志和文档示例都会出现不必要噪声。
