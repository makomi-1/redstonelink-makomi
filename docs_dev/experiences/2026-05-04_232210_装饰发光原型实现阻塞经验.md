# 装饰发光原型实现阻塞经验

## 阻塞点 1：同一工作区下并行运行 `compileJava` 与 `compileClientJava` 会产生伪编译失败

### 现象
- 单独执行 `.\gradlew.bat compileJava --no-daemon` 可以通过。
- 但与 `.\gradlew.bat compileClientJava --no-daemon` 并行触发时，会出现大量“找不到符号”报错。
- 报错范围并不集中在本轮新增文件，而是扩散到现有主源码的大量类型，看起来像整个主源码源集被破坏。

### 原因判断
- 这是 Gradle/Fabric Loom 在同一工作区下并行构建时的状态竞争问题，不是本轮业务代码本身的真实编译错误。
- 典型特征是：
  - 单独串行运行恢复正常。
  - 失败内容覆盖整个主源码包，而不是集中在刚修改的类。

### 解决方法
- 不要把 `compileJava` 与 `compileClientJava` 用并行工具同时跑。
- 改为严格串行：
  1. `compileJava`
  2. `compileClientJava`
  3. `test testIntegration testClient testSlow`

### 复用建议
- 后续只要是同一仓库的 Gradle 任务，尤其涉及 Fabric Loom 的 `compile*`、`processResources`、`clientClasses`，默认都按串行执行。
- 如果再次出现“本轮新增改动很小，但整个主源码都报 missing symbol”的异常，先怀疑并行构建污染，不要立刻按业务代码方向误修。

## 阻塞点 2：装饰发光原型不能只套统一基类，必须保留原版放置状态

### 现象
- 统一的 `WirelessDecorativeLightBlock` 适合“只有一个 `LIT` 状态”的普通装饰灯。
- 但直接拿它套 `末地烛`、`蛙明灯`、`南瓜灯` 时，会丢掉原版关键放置状态：
  - `末地烛` 的 `FACING`
  - `蛙明灯` 的 `AXIS`
  - `南瓜灯` 的 `FACING`

### 原因判断
- 这些方块不只是“一个普通立方体 + 是否发光”，它们依赖原版方块类自己的放置逻辑和状态定义。
- 如果只走统一基类，即使编译通过，游戏内也会出现：
  - 朝向错误
  - 轴向错误
  - `blockstate` 变体与真实状态不对齐

### 解决方法
- 把原型分成两类：
  - 简单 `LIT` 装饰灯：继续用 `WirelessDecorativeLightBlock`
  - 带原版关键放置状态的方块：单独建类，继承更贴近原版的方块类型
- 本轮最终落地为：
  - `WirelessDecorativeLightBlock`：通用简单灯基类
  - `WirelessLanternBlock`：保留 `HANGING/WATERLOGGED`
  - `WirelessEndRodBlock`：保留 `FACING`
  - `WirelessFroglightBlock`：保留 `AXIS`
  - `WirelessLitPumpkinBlock`：保留 `FACING`

### 复用建议
- 以后做“无线化原版方块”时，先判断原版语义是不是只有一个简单状态。
- 只要原版有独立的朝向、附着、双半块、轴向、墙面态、支撑面等状态，就不要偷懒全塞进同一个通用基类。
- 正确做法是：统一节点语义，分别保留原版放置语义。
