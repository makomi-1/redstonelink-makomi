# 跨区块队列总量上限与背压拒绝

## 问题
跨区块持久派发队列原先只有 `dispatch.maxPerTick` 这类“每 tick 处理预算”，但没有“队列最多允许积压多少条”的总量硬上限。  
这类设计在功能上可以跑通，但当目标长期离线、force-load 不命中或持续有新 key 入队时，队列规模缺少明确边界，消费预算本身并不能替代库存上限。

## 解决方法
1. 先把“消费预算”和“库存上限”拆成两个独立配置维度。
2. 在数据层而不是 service 层加硬限制，统一覆盖单条/批量入队。
3. 容量规则采用“新 key 占槽、旧 key 覆盖不占新槽”：
   - 已存在 key：允许继续覆盖更新，保持恢复语义稳定。
   - 新增 key：只有在 `pendingByKey.size() < maxPendingEntries` 时才允许写入。
4. 批量路径要在分配版本号前做容量判定，避免被拒绝的新 key 仍推进 issued/version 状态。
5. 调用方先不扩展拒绝原因协议，只复用现有 `accepted=false` 作为背压拒绝结果，保证改动面最小。

## 可复用结论
1. 对持久队列类问题，`maxPerTick` 只解决“多久消化一次”，不解决“最多堆多少”；两个维度必须分开建模。
2. 真正的容量保护应尽量收口在数据层，否则单条入口、批量入口、未来兼容入口很容易出现规则不一致。
3. 对带 upsert 语义的队列，容量统计应按“唯一 key 数”而不是“写入次数”计算，否则会误伤已有 key 的正常覆盖。
4. 如果暂时不想扩协议，最稳妥的最小实现就是“数据层拒绝 + 现有 accepted/rejected 透传 + 文档补充容量语义”。
5. 后续若继续做异步化或更强观测，优先补“拒绝原因细分”和“主线程唯一写入/原子预留”两项，而不是先把容量逻辑散落到上层入口。
