# PlayerAdvancements 进度查询前移副作用

## 阻塞点

- 这次原本准备把“已达成成就直接短路”也前移到所有条件型成就入口之前，但在落实现时发现，当前能直接使用的玩家进度查询路径依赖 `PlayerAdvancements.getOrStartProgress(...)`。
- 该 API 名称本身就带 `orStart`，进一步用 `javap` 检查后确认：当进度对象不存在时，它会先创建空 `AdvancementProgress` 再返回。
- 如果把这一步前移到所有条件型事件入口，就会把“初始化空进度”的副作用扩散到原本只是做条件匹配的路径上，得不偿失。

## 解决方法

- 本轮最终收口为“两段式优化”：
  1. 条件型成就先只前移 `isEligibleGameMode(player)`，确保创造模式完全不进入业务匹配。
  2. “已达成短路”统一收在 `awardIfEligible(...) -> resolveAwardableAdvancement(...)`，只在真正准备发奖时才查询玩家进度并阻断重复发奖。
- 这样既达成了“创造模式前置拦截”的目标，也避免把玩家进度初始化副作用提前到所有条件事件。
- 后续如果项目引入无副作用的“是否已完成成就”查询接口，再考虑把“已达成短路”继续前移到条件匹配之前。
