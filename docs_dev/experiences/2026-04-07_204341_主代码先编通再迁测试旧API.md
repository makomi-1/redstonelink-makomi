# 主代码先编通再迁测试旧API

## 阻塞点
- 这次语义收口同时移除了多组历史数据 API。共享服务落地后，`compileJava` 先被主代码里的旧审计字段卡住，随后 `compileTestJava` 又被测试层大面积旧 API 调用卡住，单看报错很难区分“实现缺陷”和“残留命名”。

## 解决方法
- 先单独跑 `compileJava`，把主代码中真正参与运行时链路的残留点收干净，确保 `LinkCommandRegistry`、`CoreLinkEditingService`、`PairingOccSubmissionSupport` 这条主链已经稳定。
- 再用 `rg` 扫描旧 API，把测试拆成两类处理：
  1. 机械替换：`toggleLink/getLinkedCores/getLinkedButtons/...` 直接迁到新的定向访问器。
  2. 语义重写：把“允许 core 作为底层 source 写入”的历史断言改成新的单向语义断言，例如 `getLinkedPeersByNodeType(...)` 和 `clearLinksForNode(...)`。

## 适用场景
- 数据层 API 一次性重命名或收口。
- 主代码与测试同时大量依赖旧方法名。
- 需要快速判断编译失败到底是行为问题还是迁移遗漏。

## 收益
- 能先把真实运行链路编通，减少“测试残留噪声”对实现判断的干扰。
- 机械替换和语义重写分开后，测试迁移节奏更稳定，也更容易看出哪些断言已经不再符合新设计。
