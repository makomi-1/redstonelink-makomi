# 客户端直发权限suite回归经验

生成时间：2026-04-03 17:37:14
文件名：2026-04-03_173714_客户端直发权限suite回归经验.md

## 背景

本次工作围绕游戏内服务器基本权限专项展开，目标是把 `C07`（读控/写控）与 `C08`（限流）跑成真实 dedicated server + Prism client 的自动化回归，并确认客户端命令桥确实走到了“玩家原生命令发送”路径，而不是只在 bench 侧做了伪装。

## 问题与解决

### 1. 误以为“客户端能拉起”就等于“客户端直发命令已经生效”

- **现象**：客户端可以被 Prism 正常拉起并自动进服，但 suite 失败时，不能证明命令已经通过客户端原生命令链路发出。
- **根因**：旧链路虽然带了 bench client，但单 case 实际执行命令时仍可能走 RCON / 服务端代理路径，不能把“客户端在场”直接等同于“客户端直发”。
- **解决方法**：
  - 在 bench client 桥中显式支持 `client_direct_command`
  - 让 suite 向单 case 透传玩家桥接上下文与 dispatch mode
  - 实跑时强制带 `RL_BENCH_CLIENT_COMMAND_BRIDGE_DISPATCH_MODE=client_direct_command`
  - 用日志验证切换证据，而不是只看 case 结果
- **复用结论**：以后凡是要证明“客户端直发命令”成立，必须同时满足三点：
  1. 参数里明确指定 `client_direct_command`
  2. 日志出现 `Player command bridge context ... mode=client_direct_command`
  3. `Player context ready` 之后命令前缀从 `[Bench/RCON]` 切到 `[Bench/PLAYER]`

### 2. 玩家 ready 前桥接时序不稳定，导致直发超时

- **现象**：客户端已经启动，但玩家实体还没完全进入世界时，桥接直发容易超时或拿不到稳定上下文。
- **根因**：bench 的世界准备、`reload/prepare/reset` 与客户端入服、玩家实体 ready 之间存在时序差；如果太早切到玩家直发，命令接收端还没准备好。
- **解决方法**：
  - `Player context ready` 之前继续走旧 RCON 路径
  - `Player context ready` 之后再切到 `[Bench/PLAYER]` 直发
  - 直发模式的验证重点放在 ready 之后的命令，而不是全链路都强制玩家直发
- **复用结论**：对需要玩家上下文的 bench 命令，不要把“客户端进程已启动”当作“玩家上下文已可用”；必须以 ready 探针为切换点。

### 3. 中文失败消息没有被 bench 识别为失败响应

- **现象**：
  - `C07` 的低权限写入返回 `[RedstoneLink] 没有足够权限。`，但被判成 `expected_failure_missing`
  - `C08` 的限流返回 `[RedstoneLink] 操作过于频繁，请稍后再试。`，也被判成 `expected_failure_missing`
- **根因**：`Test-BenchResponseLooksLikeFailure` / `Test-FunctionalCommandAssertHardFailure` 只覆盖了英文失败词，没把中文权限/限流提示纳入 failure pattern。
- **解决方法**：
  - 在 bench 失败判定里补齐 `没有足够权限`
  - 在 bench 失败判定里补齐 `操作过于频繁`
  - 同步补齐 `Test-NodeTraceReadRateLimited` 的中文限流识别
- **复用结论**：只要 bench 允许中英文双语输出，所有 `expectFailureResponse=true` 的 case 都要检查失败判定词典是否双语对齐，否则 case 设计正确也会被口径误杀。

### 4. hard failure 的宽匹配误伤了正常 `node get` 响应

- **现象**：`C07` 的 `node get` 响应语义明明正确，仍被判成 `failure_response`。
- **根因**：
  - `(?i)\\bmax\\b` 会误命中正常字段 `maxSources=-`
  - `已退役` 会误命中正常字段 `已退役=false`
- **解决方法**：
  - 删除过宽的 `max` 失败模式
  - 把 `已退役` 收紧成真实失败句式，例如：
    - `源序号 X 已退役`
    - `目标序号 X 已退役`
    - `以下目标序号已退役`
- **复用结论**：bench 的 failure pattern 不能直接用“业务文案中的裸关键词”，必须优先匹配“失败句式”，否则很容易和正常审计字段冲突。

### 5. `C07` 的 `rejectRegexes` 过宽，把合法字段也判成泄露目标

- **现象**：`low_permission_link_get_masked` 的实际响应是“目标数=0，目标列表=-”，已经是正确的 masked 行为，但 case 仍失败。
- **根因**：旧断言直接用 `(?<!\\d){{targets[0]}}(?!\\d)` 检查整条响应，导致目标 `1` 和正常字段 `源序号=1` 发生冲突。
- **解决方法**：
  - 不再对整条响应做裸数字 reject
  - 改成只在 `target_list/目标列表` 字段上做 expected / reject
  - 对 masked 场景显式补充 `target_list=-|目标列表=-`
- **复用结论**：只要响应里同时存在“源序号/目标序号/统计字段/列表字段”，就不能对整条文本做裸数字断言，必须锚定到语义字段。

## 实跑验证要点

- 构建与同步必须遵守：
  1. 先构建当前工作区运行 jar
  2. 先同步 server jar
  3. 再按需同步 client jar
  4. server/client 复用同一次构建产物

  - 运行 jar：`build/libs/redstonelink-makomi-fabric-1.21.1-0.9.7-alpha.jar`

## 后续执行建议

1. 后续新增权限/限流类 case 时，优先先写“业务期望”，再检查 bench 的中英文 failure pattern 是否覆盖到位。
2. 凡是包含列表展示的命令响应，断言都优先绑定到 `target_list/目标列表`、`target_count/目标数` 这类字段，不要直接匹配整条文本里的数字。
3. 再次验证客户端直发链路时，不要只看客户端是否启动成功，必须抓 ready 前后 `[Bench/RCON] -> [Bench/PLAYER]` 的切换证据。
