# trace读取窗口溢出排障

## 阻塞点

- dedicated `x22_window2` 看起来像 mixed runtime 在 `batchWindowTicks=2` 下丢失了 pulse。
- 但同类 `x23 combo_p` 在 `window=2` 下通过，说明不能直接把失败归因到运行时。
- 真正卡点在于：`trace_mount` 已给到更大的 capacity，但 `trace_read_tick_assert` 的 `limit` 太小，长链路 case 会把真实目标窗口挤出 recent samples，形成假阴性。

## 解决方法

- 先对照结果文件里的 `startTickMin`、`searchTickMax`、`rawSampleCount`，判断真实窗口是否已经超出 trace read limit。
- 若 `searchTickMax - startTickMin` 已超过当前 `limit`，优先把 case 的 `trace_read_tick_assert.limit` 提升到与 mount capacity 对齐，而不是先改运行时。
- 修复后重新跑全标签自动化和 dedicated 专项；本次把 `x22` 的 6 个 `trace_read_tick_assert.limit` 从 `256` 提到 `512` 后，`functional-mixed-direct-debug` 重新回到 `3/3` 通过。

## 复用信号

- 当 dedicated trace 失败只出现在靠后的 phase，而前面 phase 通过时，优先怀疑 recent sample 截断。
- 对 debug / 逐 tick 专项，`trace_mount.capacity` 与 `trace_read_tick_assert.limit` 长期不一致时，后续很容易再次出现同类误判。
