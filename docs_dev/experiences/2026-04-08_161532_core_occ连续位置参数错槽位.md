# core OCC连续位置参数错槽位

## 问题

- `core pairing` 的客户端开屏、客户端提交和服务端收包都已经确认拿到了正确的 `expectedCoreRevision`，但最终冲突文案仍显示 `expected revision=0`。
- 这类现象很容易先把注意力带到网络层、本地开屏残留或重复提交上，实际根因却可能藏在最后一层薄适配包装里。

## 解决方法

- 回到最小包装层排查 `expectedCoreRevision/expectedSourceRevision` 的参数位序，而不是继续在更外层链路扩散怀疑范围。
- 最终定位到 `LinkOccSupport.resolveCoreConflict(...)` 调用通用 helper 时，把真实 `expectedCoreRevision` 塞进了 `expectedSourceRevision` 槽位，而真正参与 `core` 比较的 `expectedCoreRevision` 被写成了占位用的 `0L`。
- 修复时只交换参数顺序，不扩散重构；同时补一条直接覆盖该包装层的单元测试，确保“匹配 revision 不冲突”和“冲突结果保留真实 expectedCoreRevision”。

## 可复用结论

- 当运行时已经证明“开屏值正确、提交值正确、收包值正确，但最终比较值错误”时，优先回查最后一层 adapter 的参数映射，不要先怀疑更外围的网络或 UI 链路。
- 对同时承载多套语义的通用 helper，若使用连续的同类型位置参数（如两个相邻 `long`），薄包装层最容易出现“编译通过、运行错槽位”的静默错误。
- 这类适配层不要只依赖高层集成验证；必须补“直接打包装层”的最小回归测试，专门校验参数是否写入了正确字段。
