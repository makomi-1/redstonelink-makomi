# bench参数化与trace窗口假失败修复

## 阻塞点
- `functional-samechunk-latency-debug` 首次回跑时，没有进入业务断言，直接在 `Bench.Matrix.ps1` 给参数化 case 回写 `parameters` 时崩掉；根因是 PowerShell 5 下 `PSCustomObject` 不能按当前写法动态新增属性。
- `x20` 与 `x23` 后续失败也不是实现回归，而是观测口径问题：
  - `x20` 用了错误的 latency 锚点，导致整批样本全部错位；
  - `x23` 的 `trace_read_tick_assert.limit` 太小，长链组合跑到后半段时，前几拍样本已经被 trace 环形窗口挤掉。
- `server-basic-permission` 首跑失败同样是测试口径漂移，断言还在匹配旧字段 `target_list=`，而当前响应已统一为 `targets=`。

## 解决方法
- bench 参数化兼容：在 `Bench.Matrix.ps1` 增加统一属性写入 helper，改为通过 `Add-Member -Force` 回写 `id/parameters`，避免 PowerShell 5 动态属性赋值失败。
- latency/trace 口径修复：
  - `x20` 把 `anchorTickStrategy` 从 `end` 改为 `start`，与 `jobStartTick` 保持一致；
  - `x23` 把所有逐 tick 读取窗口从 `256` 提到 `512`，与 mount capacity 对齐。
- 权限专项断言修复：把 `c07` 的 `target_list=` 相关匹配统一更新为现行 `targets=`。

## 可复用结论
- bench suite 失败后，先区分“实现缺陷”与“测试/观测口径漂移”，不要直接根据首个失败结果怀疑业务实现。
- PowerShell 5 跑 bench 参数化配置时，`PSCustomObject` 新增字段要走显式补属性，不要依赖动态赋值。
- 长链 trace/逐 tick 断言设计时，读取窗口必须覆盖“挂载后累计执行时长 + 预期序列长度”；只看单阶段局部长度很容易出现假失败。
- 命令响应断言依赖字段名时，新增或重构输出文案后要同步核对实际响应，避免旧字段名把真实通过的权限行为误判成失败。
