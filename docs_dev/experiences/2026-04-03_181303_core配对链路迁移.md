# core配对链路迁移

## 问题
- `core` 配对界面已经不是最终语义里的真实“来源”，但旧实现仍把它当成 `link set core ...` 的命令来源使用。
- 如果直接把这条旧链路从“命令字符串”换成“结构化 payload”，只会把旧方向语义从命令层复制到协议层，后续更难清理。

## 解决方法
- 保留 `core` 配对界面这个用户视图入口，但把它重新定义为“以 core 为观察中心的编辑请求”。
- 客户端只提交 `coreSerial + triggerSourceExpression`。
- 服务端收到后，先根据当前 `core` 关联的 `triggerSource` 集合和用户输入做差异计算，再把每个变更来源拆成一条真正的 `triggerSource -> core` 正向覆盖写入。
- 真实写入继续复用共享服务 `LinkSetExecutionService`，不要再为兼容视图额外维护第二套写控、离线校验、delta 和快照同步逻辑。

## 可复用结论
- 当旧 UI 视图必须保留、但底层语义已经重定义时，不要把“旧视图 = 旧真实来源”直接搬进新协议。
- 更稳的做法是：保留视图入口，服务端把视图请求转换成当前标准语义下的真实写入，再统一复用现有执行闭环。
- 这类迁移的核心不是“把传输层换掉”，而是先把“视图语义”和“真实写入方向”拆开，再让新协议只承载视图输入，真实落地始终走标准方向。
