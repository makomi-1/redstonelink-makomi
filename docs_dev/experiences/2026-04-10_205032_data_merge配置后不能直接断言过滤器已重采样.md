# 阻塞点

过滤器 functional case 在 `data merge block ...` 改配置后，如果立即断言运行时效果，容易把“配置已写入方块 NBT”误判成“持久化过滤真值已经重采样并生效”。

# 现象

- 本轮 `x24/x26` 初版改动在 `configure_*_neighbor_upper_bound` 后直接等待 4 tick 并断言目标恢复高态。
- dedicated 实跑显示此时目标仍维持旧结果，但后续只要再触发一次邻居变化，新的过滤语义就会正确生效。

# 原因

- 当前过滤器运行期真值仍依赖邻居变化路径触发 `refreshFilterWithCurrentNeighborSignal(...)`。
- 单纯 `data merge` 只改了方块配置，并不会自动补一次邻居重采样。

# 解决方法

- 对需要验证“配置切换后新语义”的 functional case，若仍沿用 `data merge` 改配置，就必须追加一个明确的刷新触发动作。
- 本轮采用的刷新触发仍是邻居变化；因此 `x24/x26` 只保留“掉到 0 后总开关关闭”的断言，不再新增“data merge 后立即恢复”的中间断言。

# 复用建议

- 以后写过滤器 functional case 时，把“配置写入”和“运行时刷新触发”视为两个独立步骤。
- 若要断言“配置刚写完就生效”，应先确认实现层是否真的提供了无邻居变化的即时刷新路径，否则不要把 bench 观测口径误写成设计语义。
