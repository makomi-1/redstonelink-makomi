## 任务背景

需要为转发器补一组可在 bench / dedicated server 场景下长期复用的游戏内自动化测试，验证 `1tick` 与 `2tick` 两档延迟按设计成立，并要求最终在当前工作区 `D:\OpenProjects\RedstoneLink\rl-release-no-mixin` 上实际跑通。

设计依据不是实测拟合，而是转发器现有实现语义：
- `LinkRepeaterBlockEntity.onActiveChanged()` 在输入真值变化时登记 `pendingDispatchTick = now + delayTicks`
- `LinkRepeaterBlockEntity.onDelayTick()` 到点后调用 `applyDispatchedOutputPower()`
- `applyDispatchedOutputPower()` 以 `triggerSource` 身份向下游 `core` 派发同步信号

因此本轮修的是“bench 支撑层 + 测试层”，不是改转发器实现层。

## 方案详情

### 现状分析

- 现有 functional case 可以自动放置 `sync_emitter / pulse_emitter / toggle_emitter / core_block / core_dust`
- bench 的 `kind` 映射尚未支持转发器，导致 case 无法直接放置 `redstonelink:link_repeater`
- functional trace 已具备 `trace_sync_latency_collect` 能力，能按锚点与参考 phase 统计精确延迟 tick
- 转发器延迟档位持久化键为 `delay`，token 仅支持 `1tick / 2tick`
- `crosschunk.directBatching=off` 且 `crosschunk.dispatch.batchWindowTicks=0` 时，loaded direct 的 `triggerSource -> core` 不再额外进入目标级批提交，适合隔离转发器自身延迟

### 技术方案

1. 先在 bench 支撑层新增 `repeater_block`：
   - `Get-BlockIdByKind()` 映射到 `redstonelink:link_repeater`
   - `Get-NodeTypeNameByKind()` 映射到 `core`
2. 新增 1 个参数化 functional case：
   - 场景结构为 `sync_emitter -> repeater -> core`
   - 不使用自动 `links`，改为通过 OCC 命令分别提交：
     - 上游 `triggerSource -> repeater(core)`
     - repeater(`triggerSource`) -> 下游 `core`
   - 通过 `data merge block` 写入转发器 `delay`
3. 在 phase 中挂三组 trace：
   - 上游 source `triggerSource`
   - repeater 输出侧 `triggerSource`
   - 下游 target `core`
4. 使用 `trace_sync_latency_collect` 逐层验证：
   - source 相对输入命令锚点的延迟保持现有 `1 tick`
   - repeater 输出相对 source 的延迟严格等于参数化 `delayTicks`
   - 下游 core 相对 repeater 输出的额外延迟为 `0 tick`
5. 新增专用 suite，分别以 `1tick` 与 `2tick` 两个 entry 运行同一 case，并固定关闭命令限流与 direct batching 干扰项
