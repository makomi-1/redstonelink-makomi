# sync硬压制与跨tick共存方案

生成时间：2026-05-05 18:42:03
文件名：2026-05-05_184203_sync硬压制与跨tick共存方案.md

## 任务背景

当前 `core` 目标端对 `sync` 的处理仍带有“跨 tick 仅保留最新帧”的硬编码，同时 `sync`、`pulse`、`toggle` 三类信号仍共享按时间键选胜者的混合仲裁路径。  
本轮目标是在不引入连接模式隔离设计的前提下，完成两项语义收口：

1. 新增可配置项控制 `sync` 在内部是否跨 tick 覆盖，默认关闭；关闭时 `sync` 对 `sync` 跨 tick 共存，打开时保持现状。
2. 将类间语义收紧为“`sync` 对事件类硬压制”：
   - 只要存在有效 `sync` 真值，`pulse/toggle` 均无法生效；
   - `sync` 到来时清理事件域；
   - `pulse/toggle` 在存在有效 `sync` 时直接拒收，不保留候选；
   - `sync` 消失后不回露旧事件。

## 方案详情

### 现状分析

- `sync` 目标端真值由 `ActivatableTargetConcurrentBucketComponent` 维护，当前通过 `clearSyncTruthBefore(...)` 与“只读取最新帧”的重算逻辑实现跨 tick 覆盖。
- `pulse/toggle` 结果以目标端事件快照保存，并与 `sync` 共享 `ActivatableTargetArbitrationComponent` 的候选比较。
- 观测层 `shouldFanoutByResolvedOutput(...)` 当前会把 `SYNC` 的 `authorityTimeKey` 也作为去重条件，导致“功率不变但时间键变化”的 later `sync` 仍重复扇出。
- 持久化层已具备保存多帧 `SyncConcurrentEntries` 的结构，不需要新增 NBT 结构，只需调整重建口径。
- 当前代码中的 `32` 仅为对象池保留数，不是 `core` 并发桶容量上限，本轮不引入新的默认硬限制。

### 技术方案

1. 在跨区块配置中新增布尔开关，控制 `sync` 是否沿用现有跨 tick 覆盖语义，默认 `false`。
2. 将 `sync` 重算逻辑改为两种模式：
   - 覆盖模式：保持现状，只从最新 surviving `sync` 帧重建强度；
   - 共存模式：同一来源仍只保留最新一条，但最终强度对所有 surviving `sync` 来源做 `max` 聚合。
3. 将类间仲裁改为“两段式”：
   - 先判断是否存在有效 `sync` 真值，存在则直接生效 `SYNC`；
   - 仅在无有效 `sync` 时，才进入 `pulse/toggle` 的现有事件类仲裁。
4. 保留 `sync -> clear event truth`，但把 `sync -> clear older sync truth` 收口为受配置控制的行为。
5. 在存在有效 `sync` 时，`pulse/toggle` 直接拒收，不保留旧事件候选，确保硬压制成立。
6. `SYNC` 模式下的邻居扇出去重改为只看最终激活态与输出功率，不因单纯时间键变化重复扇出。
7. 更新内部测试、配置解析测试与持久化测试，锁定新语义。

## 预期结果

- 新增配置项后，`sync` 可在“跨 tick 覆盖”与“跨 tick 共存”之间切换，默认采用共存。
- `sync` 对 `pulse/toggle` 保持硬压制，不再存在 mixed 场景下旧事件回露的问题。
- `SYNC` 扇出去重更加贴合最终功率变化，不再因单纯时间键更新重复激发。
- 不引入新的连接模式隔离或默认容量硬限制，保持改动集中在目标端仲裁与配置层。
