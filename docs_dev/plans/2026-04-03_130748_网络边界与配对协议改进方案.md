# 网络边界与配对协议改进方案

生成时间：2026-04-03 13:07:48
文件名：2026-04-03_130748_网络边界与配对协议改进方案.md

## 任务背景
`docs_dev/更新计划草稿与索引.md` 第 12 项聚焦“服务器最小化发包收包，与客户端行为划清界限”。当前分析确认存在两类高优先级缺口：
- `QuickLink` 上行请求仍偏信任客户端，服务端只校验维度一致与区块已加载，缺少距离与节点身份边界。
- 配对界面写入仍走命令字符串，协议语义停留在命令文本层，不利于后续边界收口与结构化回执。

本方案目标是在不引入 `com.makomi.api.v1.*` 依赖、不扩大本轮需求范围的前提下，给出可分期落地的网络边界与配对协议改进路径，并明确语义约束与残余风险。

## 方案详情

### 现状分析
1. `QuickLinkNetworkServerHandlerSupport` 当前仅校验 `dimensionKey` 与 `blockPos` 对应区块已加载，随后直接交给 `QuickLinkCollectService` / `QuickLinkApplyService` 读取方块实体并执行逻辑，服务端尚未复用近外显已有的“距离 + 身份一致”校验模型。
2. `PairingNetworkServerHandlerSupport` 已经存在更严格的节点定位校验：维度一致、区块已加载、距离阈值、`PairableNodeBlockEntity` 类型匹配、`LinkNodeType/serial` 一致，这说明项目内已有可复用的服务端边界模型。
3. `AbstractMultiPairingScreen` 当前仍通过 `minecraft.player.connection.sendCommand(...)` 发送 `redstonelink link set ...`，因此复用了命令层权限、限流、写控与快照同步，但客户端与命令文本强耦合。
4. 当前 `CorePairingScreen` / `PairingNetwork.openCorePairing(...)` 仍沿用“`core` 作为 sourceType”的旧模型，而项目现行语义规范要求内部新增设计统一收口为 `triggerSource -> core` 单向写入。
5. 仓库中已存在两个直接参考：
   - `StatePanelNetwork`：结构化 `C2S/S2C payload + 服务端校验 + 反馈回执`
   - `BenchStructuredLinkApplySupport`：结构化建链执行与命令层副作用闭环复用

### 技术方案
1. 第一阶段先独立加固 `QuickLink` 上行边界：
   - 抽取统一的服务端节点定位校验能力。
   - `QuickLink` 采集/应用改为复用“维度一致、区块已加载、距离足够近、节点类型/序号一致”的服务端校验。
   - 视最终实现复杂度，可在上行中补充 `expectedType/expectedSerial`，进一步避免客户端伪造坐标命中错误节点。
2. 第二阶段将配对写入从“命令字符串协议”迁移到“结构化 `C2S` 协议”：
   - 先从 `LinkCommandRegistry.executeLinkSet(...)` 与相关复用点中抽出共享写入服务。
   - 共享写入服务统一承接：输入校验、限流、写入控制、替换写入、delta 事件、客户端快照同步、结构化反馈。
   - `PairingNetwork` 新增专用写入 payload 与反馈 payload，界面层改为发结构化请求，不再拼命令字符串。
3. 第三阶段单独处理 `core` 侧配对语义：
   - 不直接把当前 `core` 作为 source 的旧行为固化到新协议。
   - 先明确 `core` 侧入口是“兼容视图”还是“按新语义重设计的编辑入口”。
   - 只有在方向语义收敛后，才将 `core` 侧接入新的结构化写入协议。

### 技术取舍
1. 先做 `QuickLink` 边界加固，而不是先做配对协议重构：
   - 优势：安全收益最高，改动面相对集中。
   - 代价：短期内配对仍保留命令字符串实现。
2. 配对协议改造选择“先抽共享写入服务，再替换传输层”：
   - 优势：避免命令层与网络层各写一套写入逻辑，便于保持副作用一致。
   - 代价：前期需要梳理命令层已有校验与副作用链路。
3. `core` 侧单独分期处理：
   - 优势：避免把旧方向语义继续固化到网络协议。
   - 代价：短期内会保留一段“新旧模型并存”的过渡期。

### 语义对齐说明
- 命名是否仅使用 `triggerSource/core`：是。本方案正文统一使用 `triggerSource/core`，仅在分析现状时提及旧行为。
- 输入/输出结构是否保持方向一致：目标状态为是。最终新增写入协议只允许 `triggerSource -> core`，`core` 不直接作为新增写入来源。
- 文案与注释是否无旧术语泄漏：是。仅在现状问题描述中保留必要的旧实现说明。
- 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource=TRIGGER_SOURCE`，`core=CORE`。
- 兼容层是否仅“读旧写新”：目标状态为是。旧命令/旧界面仅保留兼容入口，新增内部写入路径与协议统一按新语义落地。
- 残余风险：当前 `core` 配对链路仍携带旧方向语义，在第三阶段完成前，该风险仍存在。

## 原子步骤清单

### 步骤 1：抽取统一节点定位校验能力
- **操作对象**：`QuickLinkNetworkServerHandlerSupport`、`PairingNetworkServerHandlerSupport` 或新增共享 support
- **具体动作**：梳理并抽取服务端节点定位校验逻辑，统一收口维度、区块加载、距离、节点身份一致性判断
- **预期结果**：服务端节点定位边界不再散落在各网络入口中
- **关键里程碑**：是

### 步骤 2：加固 QuickLink 采集与应用上行边界
- **操作对象**：`QuickLink` 网络入口与相关服务
- **具体动作**：让 `collect/apply` 复用统一节点定位校验，并补充必要的失败反馈与回归测试
- **预期结果**：恶意客户端无法仅凭伪造坐标对远处或错误节点执行 quick-link 逻辑
- **关键里程碑**：是

### 步骤 3：抽取配对共享写入服务
- **操作对象**：`LinkCommandRegistry`、`LinkCommandSupport` 及新增共享 service/support
- **具体动作**：把 `link set` 的解析、校验、限流、写控、写入、副作用同步抽成结构化服务
- **预期结果**：命令层与网络层复用同一套写入闭环
- **关键里程碑**：是

### 步骤 4：为 triggerSource 配对新增结构化 C2S 协议
- **操作对象**：`PairingNetwork`、payload support、客户端配对界面
- **具体动作**：新增写入 payload 与反馈回执，客户端由 `sendCommand` 切换为结构化发包，服务端调用共享写入服务
- **预期结果**：triggerSource 配对从命令文本协议迁移到结构化网络协议
- **关键里程碑**：是

### 步骤 5：重设 core 侧配对语义边界
- **操作对象**：`CorePairingScreen` 及相关打开/写入链路
- **具体动作**：明确 `core` 侧是兼容视图还是按新语义重设计的编辑入口，再决定是否接入结构化写入协议
- **预期结果**：不再把旧的反向来源语义继续固化到新协议
- **关键里程碑**：是

### 步骤 6：回归验证与审查归档
- **操作对象**：自动化测试、网络回归、`docs_dev/reviews/`
- **具体动作**：执行全标签自动化测试，并补充“超距离/伪造节点/权限不足/写控拒绝/成功同步”的专项回归；实际实施完成后生成五段式审查文档
- **预期结果**：网络边界与协议改造具备可追溯验证证据
- **关键里程碑**：是

## 预期结果
1. `QuickLink` 的服务端边界从“信任客户端坐标”提升为“服务端二次确认命中节点合法”。
2. 配对界面的新增写入路径不再依赖命令字符串，而是收口为结构化 `C2S` 协议。
3. `triggerSource/core` 语义在新增协议中保持单向一致，不继续扩大旧方向模型。
4. 命令层与网络层复用同一套写入闭环，避免副作用漂移与重复实现。
