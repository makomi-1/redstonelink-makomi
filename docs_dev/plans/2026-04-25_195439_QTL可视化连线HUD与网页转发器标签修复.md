# QTL可视化连线HUD与网页转发器标签修复

生成时间：2026-04-25 19:54:39
文件名：2026-04-25_195439_QTL可视化连线HUD与网页转发器标签修复.md

## 任务背景

本轮需要同时处理三个已确认问题：

1. QTL 第三形态 `visualize` 的可视化连线有时不能稳定穿墙显示。
2. 当准星对准一条 `visualize` 连线时，需要补充一个低优先级 HUD，显示该连线另一端对象的别名与序号；若当前已有节点、转发器、过滤器或区块激活器近外显，则仍以现有近外显优先。
3. 网页可视化编辑里，转发器在孤立节点池与主图中名称显示错误，当前会退化成 `core(#...)`，但用户已明确说明这只是名称显示问题，不需要调整转发器结构或语义。

本轮只修客户端显示与网页标签生成，不改图真值、节点连接语义、持久化结构，也不引入 `com.makomi.api.v1.*` 依赖。

## 方案详情

### 现状分析

- 客户端 `QuickLinkOutlineRenderer` 当前同时负责 quick-link 预览线框与第三形态显示对象连线。第三形态连线与预览线框共用 `AFTER_TRANSLUCENT` 阶段和同一套穿墙线渲染类型，虽然已有 `NO_DEPTH_TEST`，但实际表现仍不够稳定。
- `LinkSerialHudOverlayRenderer` 当前只依赖 `minecraft.hitResult` 的方块命中结果来决定是否绘制近外显，因此准星对准空中连线时没有任何 HUD 入口。
- 网页端 `buildGraphCanvasView` 在组装 `GraphCanvasRepeaterNode` 时，直接把 `pair.coreNode.displayText` 赋给了转发器节点自身的 `displayText`，导致只要核心侧显示名是 `core(#序号)`，主图、详情和孤立节点池都会一起错误显示。

### 技术方案

1. 在客户端将第三形态连线的绘制逻辑与普通 quick-link 预览线框逻辑拆分，保留现有方框预览路径不动，为 `visualize` 直连线建立更稳定的专用穿墙绘制路径。
2. 为第三形态显示对象补充“准星命中连线”的纯逻辑采样能力：基于玩家视线射线与各线段之间的距离，在合理阈值内识别当前命中的显示对象及其对侧目标。
3. 在近外显渲染入口中增加低优先级回退分支：先沿用原有方块近外显判定，只有当当前没有命中有效方块外显对象时，才尝试使用连线命中结果生成 HUD。
4. 网页端在转发器节点组装阶段统一按“序号 + 别名”生成转发器显示名，不再复用 `core` 成员节点的 `displayText`；这样孤立池、主图节点标题和详情区将自动恢复一致。
5. 为客户端命中采样与网页端转发器命名分别补充自动化测试，防止后续回归。

### 技术取舍

- 连线穿墙问题只处理第三形态直连线，不顺带改动现有 quick-link 方框预览与缓存边界提取逻辑，尽量降低渲染侧回归范围。
- 连线 HUD 直接复用第三形态快照里已有的显示对象类型、序号与 `displayText`，避免新增网络请求或服务端快照字段。
- 网页端不在多个展示点分别追加兜底字符串，而是在 `GraphCanvasRepeaterNode` 生成源头一次性修正，减少显示口径分叉。

## 原子步骤清单

### 步骤 1：拆分第三形态连线渲染与命中采样
- **操作对象**：`QuickLinkOutlineRenderer`
- **具体动作**：抽离第三形态直连线的绘制入口；补充基于视线射线的连线命中计算方法，并暴露给 HUD 层复用
- **预期结果**：`visualize` 连线显示更稳定，同时获得可测试的“线段命中 -> 对侧对象”解析能力
- **关键里程碑**：是

### 步骤 2：补充低优先级连线 HUD
- **操作对象**：`LinkSerialHudOverlayRenderer` 及其辅助类
- **具体动作**：保留现有方块近外显优先级，在无方块近外显命中时回退到 `visualize` 连线 HUD，显示另一端对象的别名+序号
- **预期结果**：对准节点/转发器时维持现状；对准连线时新增辅助 HUD
- **关键里程碑**：是

### 步骤 3：修正网页端转发器显示名
- **操作对象**：`webapp/src/components/graphViewer/canvas.tsx`，必要时同步 `GraphViewer.tsx`
- **具体动作**：在生成 `GraphCanvasRepeaterNode` 时按转发器统一序号与别名构造显示文本，不再继承 `core` 成员节点的 `displayText`
- **预期结果**：孤立节点池、主图及详情区中的转发器名称一致且正确
- **关键里程碑**：是

### 步骤 4：补充自动化测试与本地验证
- **操作对象**：客户端与网页端测试文件
- **具体动作**：补充连线命中采样测试与网页转发器命名回归测试；随后执行对应测试和全量 Gradle 回归
- **预期结果**：问题修复具备自动化兜底，验证结果可追溯
- **关键里程碑**：是

## 语义对齐说明

- 命名统一：本轮不新增业务字段，节点语义继续保持 `triggerSource/core`，与 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射不变。
- 方向一致：不修改任何来源到目标的图写入逻辑，仅调整客户端显示与网页标签生成。
- 文案与注释：新增内容仅使用 `triggerSource/core`，不引入旧术语。
- 兼容边界：无持久化结构调整，无“写旧术语”行为，属于纯显示层修复。
- 残余风险：客户端渲染阶段调整仍需通过本地测试与实机观察确认；除此之外无额外语义风险。

## 预期结果

- `QTL visualize` 连线可稳定穿墙显示。
- 准星命中 `visualize` 连线时，能以低于近外显 HUD 的优先级显示另一端对象的别名与序号。
- 网页端转发器在孤立节点池、主图和详情面板中的名称恢复一致，不再错误显示成 `core(#...)`。
- 对应客户端与网页端回归测试补齐，并完成本地验证。
