# crosschunk第8级动态窗口策略

生成时间：2026-04-01 14:42:08
文件名：2026-04-01_144208_crosschunk第8级动态窗口策略.md

## 任务背景

第 7 级已经先完成 crosschunk 内部缓存与容器收紧，并通过现有 `crosschunk-stress` 专项完成了 `P20-P25` 的多轮 spark 对比。现有结论表明：

- `P24` 的 force-load/preload burst 仍然是最重路径，MSPT、young GC 与 old gen 抬升都最明显。
- `P20` 的问题更像 queue release 的 ready 集中释放，而不是 resident 常驻底座。
- `P25` 更接近 replay/重放带来的 Eden 抖动。
- `P23` 主要是 resident 底座，对动态窗口帮助有限。

因此第 8 级不再继续改 target 真值计算，而是先给现有 `core` 目标级批提交调度器增加“可配置的 flush 窗口”，验证能否在不改语义口径的前提下，把 ready 流的自然分散进一步吃掉。

## 方案详情

### 现状分析

- `CoreDispatchBatchScheduler` 现在按“每目标一个 accumulator、tick 末统一 flush”的模型工作。
- 同一 `core` 在同一 tick 内会聚合为一个批次，但跨 tick 没有窗口概念，所有已进入 scheduler 的条目都会在当前 tick 末落到 `target.applyDispatchBatch(...)`。
- `crosschunk.directSyncBatching` 仅控制 loaded `SYNC` 是否进入 scheduler，本身没有配置 flush 窗口。
- target 端的批应用仍然会进入 `applyDispatchBatch -> applySyncDeltaMutation -> finalizeStructuredBatchMutation`，因此若 ready 流在同一 tick 集中进入 scheduler，窗口为 0 时仍会在该 tick 集中结算。

### 技术方案

本轮按“最小可验证骨架”推进：

1. 新增配置 `crosschunk.dispatch.batchWindowTicks`，默认 `0`。
2. `windowTicks=0` 时保持现状，即同调度周期 tick 末 flush，不改变当前功能语义。
3. `windowTicks=1` 时，仅延迟已经进入 scheduler 的目标级 batch flush，一个窗口内继续向同一个 accumulator merge，但不重置窗口起点。
4. `2+ tick` 允许作为配置值存在，但不作为默认档；本轮只保证机制正确，不额外做策略自动化。
5. 保持 `ACTIVATION / toggle / pulse` 仍不进入这条窗口逻辑，继续只覆盖当前 batchable `SYNC / invalidation`。

### 影响范围

- `src/main/java/com/makomi/config/RedstoneLinkCrossChunkConfig.java`
- `src/main/java/com/makomi/config/RedstoneLinkCrossChunkConfigParser.java`
- `src/main/java/com/makomi/config/RedstoneLinkConfigTemplate.java`
- `src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java`
- `src/test/java/com/makomi/config/RedstoneLinkConfigInteractionAndCrossChunkParseTest.java`
- `src/test/java/com/makomi/data/CoreDispatchBatchSchedulerTest.java`

### 技术取舍

- 采用“在现有 `pendingByTarget` 上记录窗口起点”的方式，而不是新引入跨 tick 队列或层级时间轮，原因是本轮目标只是验证时机控制，不扩大状态复杂度。
- 窗口起点只在目标第一次进入 pending 时写入，后续 merge 不刷新起点，避免 burst 连续流量把同一目标无限后延。
- flush 判断优先基于服务端当前 tick；测试辅助路径保留强制 flush 能力，避免现有内部测试语义失真。

### 预期结果

- `window=0` 时与当前行为等价。
- `window=1` 能平滑自然分散的 ready 流，在 `P20/P24/P25` 上观察 young GC、MSPT p95 与热点分布是否继续改善。
- 不改变 `triggerSource -> core` 的对外功能语义，也不改变 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射。

## 原子步骤清单

### 步骤 1：补齐窗口配置
- **操作对象**：`RedstoneLinkCrossChunkConfig`、`RedstoneLinkCrossChunkConfigParser`、`RedstoneLinkConfigTemplate`
- **具体动作**：新增 `crosschunk.dispatch.batchWindowTicks` 字段、解析与模板说明，默认值设为 `0`，并加上边界夹紧。
- **预期结果**：crosschunk 批提交窗口可以通过配置显式控制。
- **关键里程碑**：是

### 步骤 2：实现 scheduler 动态窗口
- **操作对象**：`CoreDispatchBatchScheduler`
- **具体动作**：为目标级 accumulator 记录窗口起点；flush 时只结算已到期的目标，未到期目标继续保留在 `pendingByTarget`；测试专用强制 flush 保持可直接清空。
- **预期结果**：支持 `window=0/1/2+` 的统一窗口机制，且 `window=0` 行为等价现状。
- **关键里程碑**：是

### 步骤 3：补齐配置与调度器测试
- **操作对象**：相关配置测试与 `CoreDispatchBatchSchedulerTest`
- **具体动作**：新增默认值、边界值、窗口延迟 flush、窗口起点不被重复 merge 推迟、空闲释放不失效等测试。
- **预期结果**：窗口行为有回归保护。
- **关键里程碑**：是

### 步骤 4：执行回归与定向验证
- **操作对象**：Gradle 全标签测试与定向 bench/function case
- **具体动作**：先跑 `test testIntegration testClient testSlow`；再视时间对 `x07/x08/x17/x18/x19` 与 `P20/P24/P25` 做定向验证。
- **预期结果**：确认功能不回退，并拿到窗口策略的第一轮性能证据。
- **关键里程碑**：是

## 语义对齐说明

- 命名校验：新增设计与配置命名不引入旧术语，内部语义仍只面向 `triggerSource/core`。
- 方向校验：本轮仅调整已进入 scheduler 的 `triggerSource -> core` flush 时机，不改变方向约束。
- 映射校验：不改 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射。
- 兼容层校验：无新增旧术语写回；仅新增一个 crosschunk 内部调度配置。
- 残余风险：单独增加窗口只能平滑“自然分散的 ready 流”，不能保证压平“同一 tick 内 1024 目标集中 ready”的峰值；若后续要进一步削峰，仍需配合 flush budget。
