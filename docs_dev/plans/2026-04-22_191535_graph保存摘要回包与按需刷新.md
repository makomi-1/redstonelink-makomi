# graph保存摘要回包与按需刷新

生成时间：2026-04-22 19:15:35
文件名：2026-04-22_191535_graph保存摘要回包与按需刷新.md

## 任务背景

网页 graph 保存在频道模式或大批量拓扑修改时，`graph_write_result` 会因成功回包里携带过多 `updatedNodes` 而超过网络字符串编码上限，最终在服务端编码 clientbound payload 时断线。  
当前前端又依赖保存成功回包里的 revision 补丁来更新本地基线，因此不能只删字段，必须同时补一条“保存后按需刷新最新 graph”的闭环。

## 方案详情

### 现状分析

- 服务端成功保存回包当前仍以 `updatedNodes` 为主体，受影响节点越多，回包越大。
- `graph_write_result` 通过单个 UTF JSON 字符串回传，存在显式长度上限。
- 前端保存成功后会将成功回包里的 `updatedNodes` 直接并回当前基线图，用于后续 OCC 基线延续。
- 现有 graph export 已有稳定的客户端-服务端分块回传链路，可作为“保存后刷新最新 graph”的基础。

### 技术方案

1. 将成功保存回包收缩为最小摘要，仅保留：
   - `status`
   - `result`
   - `reason`
   - `message`
   - `graphRevision`
   - `changedNodeCount`
   - `refreshRequired`
- `preview/conflict/rejected` 分支继续保留现有结构，避免扩大兼容影响。

2. 成功保存后不再依赖 `updatedNodes` 续写前端基线：
   - 仅别名修改且不需要刷新时，前端可直接把当前 draft 应用为新的本地基线。
   - 涉及频道/拓扑真实写入时，成功回包只告知 `refreshRequired=true`，前端随后主动刷新最新 graph。

3. 补一条可同步等待的 graph refresh RPC：
   - 复用现有 graph export 分块回传能力。
   - 为 graph export 请求补 `requestId`，客户端将导出结果与等待中的刷新请求关联。
   - bridge 暴露新的 `/api/graph/refresh`，同步返回最新 graph 资产内容。

4. 同步更新前端与 bench：
   - `webapp` 改为识别新的成功响应字段。
   - bench 摘要中的 `updatedNodeCount` 切换为读取新的 `changedNodeCount`，保证回归输出稳定。

### 影响范围

- Java 服务端 graph 保存与 graph export 网络协议
- 客户端 graph export 接包与本地网页 RPC
- bridge `/api/graph/save` 相关保存闭环
- `webapp` graph 编辑保存成功后的状态更新逻辑
- Java 单测、webapp 单测、bench graph 摘要解析

## 原子步骤清单

### 步骤 1：收缩成功保存回包
- **操作对象**：`src/main/java/com/makomi/data/GraphWriteJsonSupport.java`、`src/main/java/com/makomi/data/GraphWriteService.java`
- **具体动作**：新增成功保存摘要字段，成功分支不再回传按节点展开的 `updatedNodes`，改为回传变更计数与是否需要刷新。
- **预期结果**：成功 `graph_write_result` 不再随受影响节点数量线性膨胀。
- **关键里程碑**：是

### 步骤 2：补 graph refresh RPC
- **操作对象**：`src/main/java/com/makomi/network/*`、`src/client/java/com/makomi/client/network/*`、`src/client/java/com/makomi/client/web/*`
- **具体动作**：为 graph export 增加可等待的 requestId 关联链路，并新增客户端等待刷新结果的 RPC 支持。
- **预期结果**：bridge 可同步获得本次刷新导出的最新 graph 文件。
- **关键里程碑**：是

### 步骤 3：新增 bridge 刷新接口
- **操作对象**：`src/client/java/com/makomi/client/web/LocalWebAppBridgeService.java`、相关 JSON 辅助
- **具体动作**：新增 `/api/graph/refresh`，刷新并读取最新 graph 资产内容后返回给网页端。
- **预期结果**：网页端可在保存成功后主动拉取最新 graph 基线。
- **关键里程碑**：是

### 步骤 4：改前端保存成功闭环
- **操作对象**：`webapp/src/graphTypes.ts`、`webapp/src/components/graphViewer/draft.ts`、`webapp/src/components/GraphViewer.tsx`、必要的 `App/GraphPage/storageApi`
- **具体动作**：解析新的成功响应字段；按 `refreshRequired` 区分“本地落基线”与“刷新最新 graph 后落基线”两条路径。
- **预期结果**：频道/拓扑保存后前端拿到真实最新 revision 基线，连续保存不再 OCC 漂移。
- **关键里程碑**：是

### 步骤 5：更新测试与验证
- **操作对象**：相关 Java 单测、webapp 单测、bench graph 摘要测试
- **具体动作**：更新协议断言与保存闭环测试，并执行 webapp 测试与项目全标签 Gradle 回归。
- **预期结果**：摘要回包、刷新闭环和 bench 输出均有自动化保护。
- **关键里程碑**：是

## 预期结果

- `graph_write_result` 成功回包稳定保持小体积，不再因频道模式大批量保存而断线。
- 前端保存后不再依赖大批量 `updatedNodes` 补丁，而是通过“本地落基线 / 按需刷新最新 graph”两条路径保持正确基线。
- 现有 `triggerSource/core` 术语、方向语义和 OCC 设计保持不变。
