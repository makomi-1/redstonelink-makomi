# quick-link接入occ预检与冲突校验

生成时间：2026-04-07 16:14:12
文件名：2026-04-07_161412_quick-link接入occ预检与冲突校验.md

## 任务背景
当前 `LinkSavedData` 已具备 `graphRevision/sourceRevision` 运行时真值，Pairing GUI 也已经完成“打开界面拿 revision 基线，提交时带 expected revision，服务端 mismatch 拒绝”的乐观并发控制闭环。

但 quick-link 仍然是“一跳 apply 直接写入”模型：客户端右键命中节点后只上传目标定位信息，服务端立即执行真实覆盖写入，没有 expected revision 载体，无法拦截“采集后或点击前目标连接已被其他操作修改”的静默覆盖风险。

本轮目标是在不改动旧存档键、不引入新版本源、不扩展到 bench/命令入口的前提下，把 quick-link 接入与 Pairing 同源的 OCC 校验体系。

## 方案详情

### 现状分析
- `LinkSavedData` 已维护 `graphRevision` 与 `triggerSource` 级 `sourceRevision`，且不参与存档持久化，可直接复用。
- `NodeSnapshotQueryService` 已能按节点返回附带 revision 的连接快照，说明“读取基线”能力已存在。
- quick-link 当前 `ApplyQuickLinkPayload` 只有维度、坐标、期望节点类型和期望节点序号，没有 revision 字段。
- quick-link 不像 Pairing 那样有显式“打开界面”阶段，因此无法在现有单包 apply 里自然携带可靠 revision 真值。

### 技术方案
1. 为 quick-link 新增“apply 预检”专用协议：
   - 客户端右键先请求目标节点的 OCC 基线；
   - 服务端校验命中节点合法后，回传该目标节点对应的 `graphRevision/sourceRevision`。
2. 客户端 apply 链路改为“两段式自动串联”：
   - 第一段：请求 apply 基线；
   - 第二段：收到基线后立即自动发出正式 apply 请求；
   - 用户交互仍保持“一次右键”。
3. 正式 apply 请求新增 expected revision 字段：
   - 当应用目标是 `triggerSource` 时，使用 `expectedSourceRevision`；
   - 当应用目标是 `core` 时，使用 `expectedGraphRevision`；
   - 服务端在真实写入前先校验 mismatch。
4. 冲突反馈复用现有 Pairing 文案：
   - `triggerSource` 目标冲突返回 `message.redstonelink.pairing.conflict.source_revision`
   - `core` 目标冲突返回 `message.redstonelink.pairing.conflict.graph_revision`
5. 补充 payload 与纯逻辑回归测试，并更新使用说明。

### 技术取舍
- 不复用近外显 `CurrentLinksSnapshot` 请求：
  - 该请求受 `overlayResponsePermissionLevel` 控制，不适合作为编辑协议前置步骤；
  - quick-link 需要的是写入用 revision 基线，而不是 HUD 缓存。
- 不在本轮把 bench/命令入口一起接入 expected revision：
  - 这些入口当前没有天然的“先读后写”客户端基线阶段；
  - 本轮先完成 quick-link，控制改动范围。

## 原子步骤清单

### 步骤 1：补 quick-link apply 预检协议
- **操作对象**：`QuickLinkNetwork`、`QuickLinkNetworkPayloadSupport`、`QuickLinkNetworkRegistrationSupport`
- **具体动作**：新增 apply 基线请求/响应 payload，并完成编解码与注册
- **预期结果**：客户端在正式 apply 前可拿到目标节点对应的 revision 基线
- **关键里程碑**：是

### 步骤 2：改 quick-link 客户端 apply 链路
- **操作对象**：`QuickLinkNetworkClientHandlerSupport`
- **具体动作**：右键先发基线请求，收到响应后自动继续发送正式 apply 请求
- **预期结果**：用户仍然一次右键完成 quick-link apply
- **关键里程碑**：是

### 步骤 3：服务端 apply 前接入 OCC 校验
- **操作对象**：`QuickLinkNetworkServerHandlerSupport`
- **具体动作**：按目标类型校验 expected revision，不匹配则拒绝写入并返回冲突反馈
- **预期结果**：quick-link 不再静默覆盖并发修改
- **关键里程碑**：是

- **预期结果**：协议与 OCC 判定具备自动化门禁
- **关键里程碑**：是

### 步骤 5：更新说明与审查文档
- **操作对象**：`docs_dev/使用说明.md`、`docs_dev/reviews/`
- **具体动作**：补 quick-link OCC 说明，实现完成后生成五段式审查文档
- **预期结果**：行为变化与风险边界可追溯
- **关键里程碑**：是

- quick-link apply 改为“预检拿 revision 基线 + 正式提交校验”的两段式内部协议。
- quick-link 冲突校验继续复用 `LinkSavedData` 的 `graphRevision/sourceRevision` 真值。
- 新增协议、注释、说明统一使用 `triggerSource/core` 语义，不引入旧术语输出。
