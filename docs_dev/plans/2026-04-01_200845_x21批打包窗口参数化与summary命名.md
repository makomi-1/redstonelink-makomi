# x21批打包窗口参数化与summary命名

生成时间：2026-04-01 20:08:45
文件名：2026-04-01_200845_x21批打包窗口参数化与summary命名.md

## 任务背景

当前 `x21` samechunk 延迟专项已经能批量采集 `triggerSource/core` 延迟，但它验证的是固定口径，不能把批打包窗口作为参数传入，也无法在 suite summary 中把不同窗口值区分开。用户要求把批打包窗口参数化，并让该参数参与 summary 中的 case id / 标题命名，同时让 `x21` 的断言随窗口参数自动变化。

## 方案详情

### 现状分析

- suite 入口当前只支持固定 `entryId/caseId` 与 `serverConfigOverrides`，没有通用参数层。
- suite 调单 case 时只把静态 `CaseId/MatrixPath` 传给 `run-bench.ps1`，没有 case 参数下传链路。
- `trace_sync_latency_collect` 当前支持 `matchedRatio` 与 `windowCoverageChecks`，但没有“期望延迟 ticks”精确断言。
- `x21` case 当前写死了窗口覆盖断言，无法随外部批打包窗口参数自动调整。
- summary 当前只保留静态 `entryId/caseId`，不同窗口值跑出来无法直接并排区分。

### 技术方案

1. 给 suite entry 增加 `parameters` 与 `title`，并支持 `{{param:name}}` 模板展开。
2. 让 suite 解析后的 `parameters` 同时参与：
   - `entryId`
   - `title`
   - `serverConfigOverrides`
3. 给 `run-bench.ps1` 增加 `CaseParameters` 入参，并在读取 case 后做执行时参数展开。
4. 给 `trace_sync_latency_collect` 新增 `expectedDelayTicks` 精确断言，基于 `inputDelayTicks` 或 `referenceDelayTicks` 直接出 check。
5. 将 `x21` 改成参数化专项：
   - `triggerSource` 仍断言绝对延迟为 `1 tick`
   - `core` 改为断言相对 `triggerSource` 的延迟等于 `dispatchBatchWindowTicks`
6. 将 samechunk latency debug suite 改成多 entry 参数化运行，并在 summary 中输出参数化后的显示 id / 标题。

### 影响范围

- `tools/bench/lib/BenchSuite.Results.ps1`

- `tools/bench/lib/Bench.Matrix.ps1`
- `tools/bench/lib/Bench.EntryPoint.ps1`

- `tools/bench/cases/functional/x21/sync_samechunk_latency_1024_to_1024_banded16_single_burst.json`
- `tools/bench/suites/functional-samechunk-latency-debug.json`

## 原子步骤清单

### 步骤 1：补 suite 参数与命名模板
- **操作对象**：`BenchSuite.Config.ps1`、`BenchSuite.EntryPoint.ps1`、`BenchSuite.Results.ps1`
- **具体动作**：新增 `parameters/title` 解析、默认值与 entry 级覆盖合并、`{{param:name}}` 模板展开，并将参数化显示字段写入 summary
- **预期结果**：summary 中可以直接区分不同窗口值的专项结果
- **关键里程碑**：是

### 步骤 2：补单 case 参数下传
- **操作对象**：`run-bench.ps1`、`Bench.Matrix.ps1`、`Bench.EntryPoint.ps1`
- **具体动作**：新增 `CaseParameters` 入参，并在取到静态 case 后做执行时参数展开
- **预期结果**：suite entry 参数可以直接影响 `x21` case 的 phase 配置与结果命名
- **关键里程碑**：是

### 步骤 3：补延迟精确断言
- **操作对象**：`Bench.FunctionalTrace.ps1`
- **具体动作**：为 `trace_sync_latency_collect` 增加 `expectedDelayTicks` 检查，支持基于 `inputDelayTicks/referenceDelayTicks` 做精确校验
- **预期结果**：专项可以直接验证“额外处理窗口延迟是否等于参数值”
- **关键里程碑**：是

### 步骤 4：改造 x21 与 debug suite
- **操作对象**：`x21` case 与 samechunk latency debug suite
- **具体动作**：把 `dispatchBatchWindowTicks` 作为参数引入，x21 断言随参数变化，suite 生成多条参数化 entry 并覆盖 `crosschunk.directSyncBatching=all_sync`
- **预期结果**：同一专项可并列验证 `window=0/1/2...`
- **关键里程碑**：是

### 步骤 5：执行回归与定向验证
- **操作对象**：Gradle 全标签测试与 samechunk latency debug suite
- **具体动作**：先执行 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`，再跑参数化 `x21` suite
- **预期结果**：验证功能不回退，且参数化窗口专项结果与命名正确
- **关键里程碑**：是

## 预期结果

- `x21` 支持以参数方式传入批打包窗口。
- suite summary 的 case id / 标题会明确带出窗口值。
- `core` 相对 `triggerSource` 的额外处理延迟可以直接按参数自动断言。

## 语义对齐说明

- 命名校验：新增方案与实现统一使用 `triggerSource/core`。
- 方向校验：仍只验证 `triggerSource -> core`。
- 文案校验：不引入旧术语回流。
- 映射校验：不改 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射。
- 兼容层校验：仅增强 bench 参数化与结果展示，不改业务实现语义。
- 残余风险：旧脚本若只读取 summary 中静态 `caseId`，仍看不到参数化信息，因此需要保留兼容字段并新增显示字段。
