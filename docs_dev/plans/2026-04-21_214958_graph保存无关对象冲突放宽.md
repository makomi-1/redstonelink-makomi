# graph保存无关对象冲突放宽

生成时间：2026-04-21 21:49:58
文件名：2026-04-21_214958_graph保存无关对象冲突放宽.md

## 任务背景

当前网页端 `graph` 保存虽然已经在单个 `triggerSource` 与单个 `core` 层面携带对象级 revision，但服务端 `GraphWriteService.preparePlan(...)` 仍会先用整图 `baseGraphRevision` 做一次硬性冲突拦截。这样只要保存期间图上任意其他对象发生拓扑变化，即使本次请求修改的是完全不同的对象，也会被提前判定为冲突并要求重新导出。

本轮目标是把该保守策略收敛为“只对真实修改对象做 OCC 校验”，从而允许“非真实冲突”直接合并保存；同一对象上的真实冲突仍继续拒绝，避免静默覆盖。

## 方案详情

### 现状分析

- `GraphWriteService.preparePlan(...)` 在进入对象级校验前，先比较请求的 `baseGraphRevision` 与当前 `savedData.graphRevision()`，命中不一致就整体返回 `graph_revision_conflict`。
- `ReplaceTriggerSourceTargetsOperation` 已经自带 `expectedSourceRevision`，并在校验阶段按 `triggerSource` 粒度做冲突判断。
- `SetNodeChannelOperation` 已经自带 `expectedSourceRevision/expectedCoreRevision`，并在校验阶段按节点粒度做冲突判断。
- 真实拓扑变化仍会统一推进 `graphRevision + sourceRevision + coreRevision`，因此当前问题不是缺少 revision 真值，而是服务端过早使用了整图门禁。
- 前端当前仍保留 `baseGraphRevision` 字段；本轮先不移除协议字段，只放宽服务端判定，保持请求结构兼容。

### 技术方案

1. 移除 `GraphWriteService.preparePlan(...)` 中对拓扑写入请求的整图 `baseGraphRevision` 预拦截，让请求继续进入后续对象级校验。
2. 保留现有 `ReplaceTriggerSourceTargetsOperation` 的 `expectedSourceRevision` 冲突拦截，以及 `SetNodeChannelOperation` 的 `expectedSourceRevision/expectedCoreRevision` 冲突拦截，不改变真实冲突判定边界。
3. 补充回归测试，覆盖“无关对象变更后仍可保存”和“同一对象变更后仍冲突”两类场景，确保放宽的是误拒绝，不是全部放开。
4. 视测试结果决定是否同步微调文档/前端文案；若当前文案仍描述“任何整图变化都要重导出”，则只在本轮影响范围内修正文档，不扩展到自动加载或同对象自动合并。

### 影响范围

- 服务端 graph 保存编排：`GraphWriteService`
- graph 保存相关单元测试：`GraphWriteServiceTest`，必要时补 `GraphWriteJsonSupportTest` 或前端测试
- 文档与说明：仅在与本轮语义直接冲突时最小修正

### 技术取舍

- 选择“去掉整图误拒绝，保留对象级 OCC”而不是直接做自动重放，是因为前端当前把批量编辑折算成最终 `ReplaceTriggerSourceTargets`，原始 add/remove 意图未保留；若在同一对象冲突后直接自动重放，存在覆盖他人新改动的风险。
- 保留 `baseGraphRevision` 请求字段而不立即删除，是为了维持现有协议兼容与前端最小改动；本轮先改服务端决策，不额外扩大协议变更面。

## 预期结果

完成后，网页端 graph 保存将允许“修改对象不同”的并发变更直接合并保存，不再因无关对象触发整图误拒绝；同一 `triggerSource/core` 的真实冲突仍会按对象级 revision 明确拒绝。当前阶段不包含同对象自动合并、局部自动重载或网页端自动重新导出入口。

## 语义对齐说明

- 命名是否仅使用 `triggerSource/core`：是
- 输入/输出结构是否保持方向一致：是，真实写入仍为 `triggerSource -> core`
- 文案与注释是否无旧术语泄漏：是
- 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource=TRIGGER_SOURCE`，`core=CORE`
- 兼容层是否仅“读旧写新”：是，本轮不新增旧术语写出

残余风险：
- 同一对象上的真实冲突仍需用户刷新基线后重试，本轮不实现自动重放。
- 批量请求中若任一真实冲突命中，当前仍按整批失败处理，本轮不扩展为部分成功。
