# core OCC参数位序修复

生成时间：2026-04-08 16:13:50
文件名：2026-04-08_161350_core_occ参数位序修复.md

## 任务背景

本轮排查 `core pairing` 的 OCC 冲突时，已经确认客户端开屏、客户端提交和服务端收包阶段的 `expectedCoreRevision` 都是正确值；但最终冲突文案仍显示 `expected revision=0`。进一步定位发现，`LinkOccSupport.resolveCoreConflict(...)` 在委托通用冲突 helper 时把 `expectedCoreRevision` 与占位用的 `0L` 传反，导致 `core` 分支实际总是按 `0L` 做比较。

## 方案详情

### 现状分析

- `resolveTargetConflictWithCurrentBaseline(...)` 同时承载 `triggerSource` 与 `core` 两类 OCC 比较，因此签名中同时包含 `expectedCoreRevision` 与 `expectedSourceRevision`。
- `resolveCoreConflict(...)` 的设计本意应是“真实值传给 `expectedCoreRevision`，未使用的 `expectedSourceRevision` 用 `0L` 占位”。
- 当前实现把两者顺序写反，属于薄适配层的参数位序错误，编译期无法发现，但会直接导致运行时比较错槽位。

### 技术方案

1. 修正 `LinkOccSupport.resolveCoreConflict(...)` 对通用 helper 的调用位序：
   - `expectedCoreRevision` 放回第三个参数位
   - `0L` 仅保留给第四个参数位的 `expectedSourceRevision` 占位
2. 新增一个直接覆盖 `resolveCoreConflict(...)` 的单元测试：
   - 断言“匹配的 `expectedCoreRevision` 不应冲突”
   - 断言“冲突结果里应保留真实 `expectedCoreRevision`，而不是掉到 `expectedSourceRevision`”
3. 将本次“连续位置参数传错导致 OCC 错槽位”的排障结论写入经验库，便于后续复用。
