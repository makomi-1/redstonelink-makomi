# core OCC游戏内测试与实跑

生成时间：2026-04-08 10:52:58

## 任务背景

当前仓库已经完成 `core` OCC 从全图级 `graphRevision` 收缩到局部 `coreRevision` 的实现改造，pairing / quick-link / bench/internal 的业务语义也已经同步切到 `expectedCoreRevision`。  
但 dedicated bench 的 OCC 专项 functional case 仍残留旧设计：core 冲突场景依旧抓取 `graphRevision`、提交 `expectedGraphRevision`、断言 `message.redstonelink.pairing.conflict.graph_revision`。  
这会导致游戏内自动化测试与当前实现设计不一致。用户本轮要求继续完成两件事：
1. 修改相应游戏内测试设计，使其与 `coreRevision` 新语义一致。
2. 基于当前工作区真实构建产物，完成一次 dedicated server 场景的实际跑通验证。

## 方案详情

### 现状分析

- `tools/bench/suites/occ-conflict-regression.json` 已提供 OCC 冲突专项 suite。
- `triggerSource` 两个专项 case 仍然是正确语义，因为它们比较 `sourceRevision`。
- `core` 两个专项 case 仍然使用旧口径：
  - `tools/bench/cases/functional/o02/occ_pairing_core_conflict.json`
  - `tools/bench/cases/functional/o04/occ_quick_link_core_conflict.json`
- 这两个 case 的问题集中在：
  - `description` 仍描述 stale `graphRevision`
  - `captureRegex` 只抓 `graphRevision/sourceRevision`
  - 提交参数仍写 `expectedGraphRevision`
  - 冲突断言仍写 `message.redstonelink.pairing.conflict.graph_revision`

### 技术方案

1. 仅修改 `core` OCC 专项 functional case，把测试设计统一改到 `coreRevision`：
   - snapshot 阶段改为抓取 `coreRevision`
   - stale 提交参数改为 `expectedCoreRevision`
   - 冲突断言改为 `message.redstonelink.pairing.conflict.core_revision`
2. 保持 suite 入口不变，继续复用 `occ-conflict-regression.json`，避免把专项场景混入 `regression-core/full`。
3. dedicated 实跑严格按项目规则执行：
   - 先基于当前工作区构建运行 jar
   - 再同步 dedicated server mod jar
   - 然后运行 OCC 专项 suite
4. 若 dedicated 实跑失败，先按设计核对失败属于：
   - 实现缺陷
   - 测试模板错误
   - 观测口径偏差
   再决定下一步修哪一层，禁止直接拿实测结果反推实现正确语义。

### 影响范围

- `tools/bench/cases/functional/o02/occ_pairing_core_conflict.json`
- `tools/bench/cases/functional/o04/occ_quick_link_core_conflict.json`
- 必要时补充 `docs_dev/使用说明.md`
