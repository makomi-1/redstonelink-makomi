# 第六七批 client_network 与命令注释收口

生成时间：2026-03-25 16:40:27

## 任务背景

第五批已完成持久化与索引簇收口，数据层主路径相对稳定。当前剩余较明显的组织债集中在两类 orchestrator 文件：

- `PairingNetwork.java` 同时承担 payload 注册、服务端请求处理、S2C/C2S 编解码与回包适配；
- `LinkSerialHudOverlayRenderer.java` 同时承担快照缓存、懒请求、文案格式化、布局计算与实际绘制。

另外，命令层虽然已经过多轮拆分，但 `CrossChunkCommandRegistry.java` 与 `NodeTraceCommandRegistry.java` 仍存在方法级悬停注释、参数意图说明和错误分支说明不统一的问题，继续放着会拖累后续维护与测试理解。

## 方案详情

### 现状分析

- `PairingNetwork` 当前约 641 行，职责可自然分成：
  1. payload 注册；
  2. 服务端 C2S 请求处理；
  3. payload 编解码与回包适配；
  4. 对外保留的打开配对入口。
- `LinkSerialHudOverlayRenderer` 当前约 821 行，职责可自然分成：
  1. 服务端快照缓存与懒请求；
  2. HUD 文案组装；
  3. HUD 布局计算；
  4. 实际绘制。
- `CrossChunkCommandRegistry` 与 `NodeTraceCommandRegistry` 现有行为已较稳定，继续拆包的收益低于风险；本轮更适合补齐注释与错误分支说明，让“命令为什么失败/为什么返回 0”更直观。
- `PairingNetworkPayloadTest`、`PairingNetworkDispatchTest` 已依赖 `PairingNetwork.*Payload` 的公开嵌套记录类型，拆分时不宜破坏这一稳定契约。

### 技术方案

本轮继续坚持“结构变、行为不变、公开契约尽量不动”的策略。

1. `PairingNetwork` 收口为“壳 + helper”
   - 主类 `PairingNetwork`
     - 保留：公开 payload 记录类型、`register()`、`openTriggerSourcePairing(...)`、`openCorePairing(...)`、`openPairingBySourceType(...)`。
     - 作用：对外稳定入口与 payload 契约承载。
   - `PairingNetworkRegistrationSupport`
     - 负责：payload type 注册、global receiver 注册。
   - `PairingNetworkServerHandlerSupport`
     - 负责：`RequestCurrentLinksPayload`、`RequestRuntimeHudSnapshotPayload` 的服务端校验、距离守卫、节点校验、回包发送。
   - `PairingNetworkPayloadSupport`
     - 负责：编解码 helper、payload 构造辅助、runtime HUD 强度归一。
   - 取舍理由：
     - 保留嵌套 payload 记录，避免测试和下游 import 大面积改动；
     - 将最容易继续膨胀的“注册”和“handler”逻辑抽离，达到组织收口目标。

2. `LinkSerialHudOverlayRenderer` 收口为“薄 orchestrator + 四组 helper”
   - 主类 `LinkSerialHudOverlayRenderer`
     - 保留：缓存常量、公开更新入口、`onHudRender(...)` orchestrator。
   - `LinkSerialHudOverlaySnapshotSupport`
     - 负责：缓存清理、请求节流、懒请求、snapshot 归一。
   - `LinkSerialHudOverlayTextSupport`
     - 负责：状态文案、IO 文案、当前连接文案、缓存命中文案组装。
   - `LinkSerialHudOverlayLayoutSupport`
     - 负责：位置缩放、中心点计算、包围盒计算。
   - `LinkSerialHudOverlayDrawSupport`
     - 负责：底板与文字的实际绘制。
   - 取舍理由：
     - 不改变 `LinkSerialHudOverlayRenderer` 的外部调用点；
     - 把“读快照”“算字”“算位置”“画出来”分离，便于后续调 HUD 而不碰网络缓存。

3. 命令层收口以注释统一为主
   - `CrossChunkCommandRegistry`
     - 补齐：方法级悬停注释、关键参数含义、批量 set/confirm/resident 错误分支说明。
   - `NodeTraceCommandRegistry`
     - 补齐：批量 mount/latest/read/unmount/list 的参数意图说明、限流/过滤/unsupported 分支说明。
   - 不额外拆包，避免在无明显收益处继续分散结构。

## 原子步骤清单

### 步骤 1：收口 PairingNetwork 注册与 handler
- **操作对象**：`PairingNetwork.java` 与新增 network helper
- **具体动作**：提取 payload 注册、服务端请求处理、payload 编解码 helper；主类保留公开入口和 payload 记录
- **预期结果**：`PairingNetwork` 变成稳定外壳，内部职责边界清晰
- **关键里程碑**：是

### 步骤 2：收口 HUD renderer 的快照、文案、布局、绘制
- **操作对象**：`LinkSerialHudOverlayRenderer.java` 与新增 render helper
- **具体动作**：将缓存/懒请求、文案格式化、布局计算、绘制逻辑分别下沉到 helper
- **预期结果**：主渲染器只保留公开入口和顶层流程编排
- **关键里程碑**：是

### 步骤 3：统一命令注册器方法级注释
- **操作对象**：`CrossChunkCommandRegistry.java`、`NodeTraceCommandRegistry.java`
- **具体动作**：补齐方法级悬停注释、参数意图说明、错误分支说明
- **预期结果**：命令失败路径和参数用途可直接从悬停注释读懂
- **关键里程碑**：否

### 步骤 4：回归验证
- **操作对象**：Gradle 测试
- **具体动作**：运行 `.\gradlew.bat test testIntegration testClient testSlow testApiLegacy --no-daemon`
- **预期结果**：确认本轮仅为组织优化和注释收口，无行为回归
- **关键里程碑**：是

## 预期结果

- `PairingNetwork` 不再混合注册、handler、编解码三类职责。
- `LinkSerialHudOverlayRenderer` 不再同时承担缓存、文案、布局和绘制四类职责。
- `CrossChunkCommandRegistry` 与 `NodeTraceCommandRegistry` 的可读性进一步收敛，后续排查失败分支时不需要反复下钻。

## 语义对齐说明

- 命名是否仅使用 `triggerSource/core`：是
- 输入/输出结构是否保持方向一致：是，本轮不改方向校验与数据流向
- 文案与注释是否无旧术语泄漏：是；仅在历史兼容语境下保留既有标识符
- 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource=TRIGGER_SOURCE`，`core=CORE`
- 兼容层是否仅“读旧写新”：是；本轮不新增持久化字段，也不改网络 payload 外观
- 残余风险：
  1. `PairingNetwork` 的 payload 嵌套记录保持不动，但 helper 抽离后若静态调用落点不完整，容易出现注册遗漏；
  2. HUD renderer 的缓存与懒请求拆分后，若 orchestrator 参数传递不完整，可能造成近外显静默不刷新。
