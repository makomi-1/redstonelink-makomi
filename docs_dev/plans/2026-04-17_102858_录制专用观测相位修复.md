# 录制专用观测相位修复

生成时间：2026-04-17 10:28:58
文件名：2026-04-17_102858_录制专用观测相位修复.md

## 任务背景

当前状态面板 recording 的曲线样本直接复用通用 `NodeStateTraceService`。在现有服务端 tick 顺序下，通用 trace 的采样相位偏前，导致 recording 曲线也继承了“首拍常晚 1 tick”的观测偏差。该偏差已经在 bench/trace 文档中被定义为“观测口径问题”，不宜直接通过改全局 trace 顺序来修复，否则会连带改写现有功能专项和 bench 基线。

本轮目标是只修 recording 的观测相位：让 recording 拥有一套更晚的、面向导出的独立采样缓冲，使录制曲线更接近 tick 内最终稳定态，同时保持全局 `NodeStateTraceService` 与 bench 口径不变。

## 方案详情

### 现状分析

- `StatePanelRecordingSessionService` 开始录制时通过 `NodeStateTraceService.mount(...)` 挂载通用 trace，并在结束导出时通过 `NodeStateTraceService.readSamples(...)` 读取样本。
- `NodeStateTraceService` 统一在 `END_SERVER_TICK` 采样，且在模组初始化顺序上早于 `InputPlaybackService` 与 `CoreDispatchBatchScheduler`。
- recording 自动结束逻辑由 `StatePanelNetworkRegistrationSupport` 在 `END_SERVER_TICK` 中触发，注册顺序也早于输入投递与批调度收口。
- 因此 recording 当前既没有独立的采样相位，也无法保证“本 tick 已完成输入投递和 core flush 后再采样”。

### 技术方案

1. `StatePanelRecordingSessionService` 不再依赖通用 trace ring buffer，而是在活动会话内部为每个录制节点维护独立样本缓冲与 `nextSampleTick`。
2. recording 采样仍复用 `NodeRuntimeProbe.snapshot(...)` 生成快照，确保节点身份、`triggerSource/core` 语义和快照字段保持一致。
3. 在 `StatePanelRecordingSessionService.register()` 中新增 recording 专用 `END_SERVER_TICK` 采样钩子，按会话内 `sampleEveryTicks` 规则写入独立缓冲。
4. 调整模组注册顺序，让 recording 采样钩子晚于 `InputPlaybackService`、`ChannelDispatchScheduler`、`CoreDispatchBatchScheduler`，从而尽量采到 tick 内最终稳定态。
5. 将 `StatePanelNetwork.register()` 放到 recording 服务注册之后，确保 recording 自动结束钩子晚于 recording 采样执行。
6. 导出 `recording bundle` 时改为直接从会话内独立缓冲生成 `series`，不改变 JSON 结构、字段名和网页读取协议。

### 影响范围

- `src/main/java/com/makomi/RedstoneLink.java`
- `src/main/java/com/makomi/data/StatePanelRecordingSessionService.java`
- `src/main/java/com/makomi/network/StatePanelNetworkRegistrationSupport.java`（若需最小化 tick 钩子拆分则评估）
- 视实现需要补充对应单测

### 技术取舍

- 不改全局 `NodeStateTraceService`：避免触发 bench `trace_read_tick_assert`、`pulse` 宽度口径和既有专项基线整体迁移。
- 不改 recording bundle 格式：网页端无需适配新协议，已有本地 recording 文件继续可读。
- 第一版保持 `sampleEveryTicks` 严格语义，不在手动/自动 stop 时额外强插非周期尾样本，减少“导出样本与采样配置不一致”的副作用。

### 语义对齐说明

- 新增实现不引入旧术语，内部与对外文案继续使用 `triggerSource/core` 基线。
- 不涉及方向写入路径修改，不影响 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射。
- 不新增 `com.makomi.api.v1.*` 依赖。
- 兼容边界保持“读旧写旧”：recording 文件字段、网页解析结构和导出协议不变。

## 原子步骤清单

### 步骤 1：调整 recording 相关注册顺序
- **操作对象**：`RedstoneLink.java`
- **具体动作**：让 recording 服务与 recording 网络注册晚于输入投递和批调度注册；确保 recording 采样先于 recording auto-stop。
- **预期结果**：recording 观测与导出发生在更晚的 tick 相位。
- **关键里程碑**：是

### 步骤 2：为录制会话引入独立样本缓冲
- **操作对象**：`StatePanelRecordingSessionService.java`
- **具体动作**：把活动会话从“仅保存已挂载节点引用”改为“保存节点引用 + 独立样本缓冲 + 下次采样 tick”。
- **预期结果**：recording 不再依赖通用 trace ring buffer。
- **关键里程碑**：是

### 步骤 3：新增 recording 专用晚相位采样
- **操作对象**：`StatePanelRecordingSessionService.java`
- **具体动作**：注册并实现 recording 专用 `END_SERVER_TICK` 采样逻辑，按 `sampleEveryTicks` 采集快照写入会话缓冲。
- **预期结果**：recording 曲线更接近 tick 内最终稳定态。
- **关键里程碑**：是

### 步骤 4：改造导出逻辑
- **操作对象**：`StatePanelRecordingSessionService.java`
- **具体动作**：导出 `recording bundle` 时改为读取会话内样本缓冲生成 `series`，保持文件格式不变。
- **预期结果**：网页端继续按原协议读取 recording 文件。
- **关键里程碑**：是

### 步骤 5：补测试并执行回归
- **操作对象**：相关测试文件、Gradle 测试与前端构建
- **具体动作**：补最小必要单测/回归测试，执行 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`。
- **预期结果**：确认 recording 相位修复不影响既有全局 trace 与网页端读取。
- **关键里程碑**：是

## 预期结果

recording 录制结果将使用独立的晚相位采样缓冲，`sync/toggle` 曲线首拍更接近真实最终稳定态，`window=0` 同 tick late flush 更容易在 recording 中被采到；与此同时，全局 `NodeStateTraceService`、bench 逐 tick 断言口径、recording bundle 文件结构和网页读取协议保持不变。
