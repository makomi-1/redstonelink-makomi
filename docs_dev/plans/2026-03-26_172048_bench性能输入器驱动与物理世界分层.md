# bench性能输入器驱动与物理世界分层

生成时间：2026-03-26 17:20:48
文件名：2026-03-26_172048_bench性能输入器驱动与物理世界分层.md

## 任务背景

现有 bench 性能场景沿用 `RunCase` 的旧驱动模型：
- `sync` 通过 `north_strip` 在来源阵列外围填充红石块驱动。
- `pulse/toggle` 通过 `node activate` 命令驱动。

这会把“纯模组性能成本”“物理世界端到端成本”“命令路径成本”混在同一组性能结果里。已经确认：
- 多行 `sync emitter` 阵列会被 `north_strip` 明显低估，典型如 `sync_256_to_256_core_banded16` 名义上是 `256` 个 `triggerSource`，实际只直接驱动最北一排 `16` 个。
- `performance-lite` 中的混合场景同样受到这一驱动偏差影响。
- 输入器的设计目的本来就是测试和诊断，且当前实现已经支持对 `triggerSource` emitter 输入口做运行态模拟。

因此，本轮需要一次性把性能测试语义切清：
- 纯模组性能压测统一改用输入器。
- 红石块驱动保留为物理世界端到端测试，不再作为纯性能基线。

## 方案详情

### 现状分析

- `tools/bench/lib/Bench.PlaceAndLink.ps1` 中 `Invoke-DriveSchedule` 仅支持：
  - `sync_square_wave`
  - `activate_batch`
- `tools/bench/templates/performance/drive.json` 的性能模板仍建立在上述两种 step 之上。
- `tools/bench/cases/performance/**` 的 `lite` 与 `baseline-256` 场景均共享这套驱动语义。
- `docs_dev/使用说明.md` 已经说明：
  - `triggerSource` 支持发射器输入口模拟。
  - 输入器按 `真实输入` 与 `模拟输入` 取较大值。
- `InputPlaybackService` 对 `TRIGGER_SOURCE_INPUT` 的目标校验要求是：
  - `LinkTriggerSourceBlockEntity`
  - 对应方块为 `LinkSignalEmitterBlock`
  因而当前已覆盖 `sync/pulse/toggle emitter`。

### 技术方案

1. 在 `RunCase` 驱动层新增输入器 step
- 为性能 `drive.steps` 新增：
  - `input_square`
  - `input_custom`
- 这两个 step 直接复用现有 `/redstonelink input start ...` 命令语义，而不是重复造一套本地 tick 播放逻辑。
- `RunCase` 结束后无论成功失败都统一执行 `redstonelink input clear`，防止运行态 job 污染后续 case。

2. 纯性能 case 全量迁移到输入器
- `performance-lite` 与 `performance-baseline` 下的现有性能 case 全部改为输入器驱动。
- 保持原性能 case 的“波形意图”不变：
  - `sync_square_wave` 迁移为单次启动、持续运行的 `input_square`。
  - `activate_batch_pulse` / `activate_batch_toggle` 迁移为单次启动、持续运行的边沿型 `input_square`。
- 不把现有周期波形偷换成“长时间恒高”，避免改变原本要测的触发频率语义。

3. 新增物理世界端到端层
- 新增独立 `physical-world` suite 与 matrix/case 入口。
- 这层继续保留红石块或真实世界输入驱动，用于接近实际游玩、F3 曲线和原版邻居更新成本。
- 这层与纯性能压测层分离，不再共用“正式性能基线”口径。

4. 文档和调用入口同步收口
- `docs_dev/使用说明.md` 补充：
  - 纯性能压测与物理世界端到端测试的分层说明。
  - 新的 suite / matrix / case 调用方式。
  - 输入器性能驱动的配置前置条件与边界。

### 技术取舍

- 选择“复用现有输入命令层”，而不是在 bench 内单独实现第二套输入播放：
  - 优势：语义统一，测试链路与实际运行态命令一致。
  - 代价：`RunCase` 需要补输入 job 生命周期管理。
- 保留红石块驱动，但降级到物理世界层：
  - 优势：可以继续观察真实世界邻居更新、布局边界和 F3 曲线。
  - 代价：需要新建 suite/case 入口，不能再直接拿旧结果和纯性能基线混比。

### 影响范围

- `tools/bench/lib/Bench.PlaceAndLink.ps1`
- `tools/bench/templates/performance/*.json`
- `tools/bench/cases/performance/**`
- `tools/bench/matrix*.json`
- `tools/bench/suites/*.json`
- `docs_dev/使用说明.md`

## 原子步骤清单

### 步骤 1：落输入器性能 step
- **操作对象**：`tools/bench/lib/Bench.PlaceAndLink.ps1`
- **具体动作**：为 `RunCase` 新增 `input_square/input_custom` step 解析与命令下发，并补 `input clear` 收尾逻辑。
- **预期结果**：性能 case 可以直接通过输入器驱动 `triggerSource/core`，不会残留运行态 job。
- **关键里程碑**：是

### 步骤 2：迁移纯性能 case
- **操作对象**：`tools/bench/templates/performance/*.json`、`tools/bench/cases/performance/**`、`tools/bench/matrix*.json`
- **具体动作**：将 `lite` 与 `baseline-256` 的性能 case 从红石块/命令混合驱动切到输入器驱动，同时保留原波形语义。
- **预期结果**：现有纯性能基线结果不再低估多行 `sync` 阵列，也不再混入命令驱动语义。
- **关键里程碑**：是

### 步骤 3：拆出物理世界端到端层
- **操作对象**：`tools/bench/cases/performance/**`、`tools/bench/suites/*.json`
- **具体动作**：为红石块/真实输入驱动建立独立 suite/case 分层，不再挂在纯性能 suite 下。
- **预期结果**：物理世界端到端结果与纯模组性能结果口径清晰分离。
- **关键里程碑**：否

### 步骤 4：更新说明与入口
- **操作对象**：`docs_dev/使用说明.md`
- **具体动作**：补充新的性能分层说明、调用命令、输入器前置条件和物理世界层定位。
- **预期结果**：后续使用者能明确区分“纯性能压测”和“物理世界端到端测试”。
- **关键里程碑**：否

### 步骤 5：执行验证
- **操作对象**：bench 入口、suite 解析结果、必要脚本验证
- **具体动作**：验证 case/suite 解析和输入器 step 可被正确展开，并执行要求的自动化测试门禁。
- **预期结果**：确认本轮改动没有破坏现有 bench 主流程。
- **关键里程碑**：是

## 语义对齐说明

- 命名是否仅使用 `triggerSource/core`：是，本轮新增设计与文案统一使用 `triggerSource/core`。
- 输入/输出结构是否保持方向一致：是，所有 link 和输入驱动仍保持 `triggerSource -> core`。
- 文案与注释是否无旧术语泄漏：是，本轮仅在 bench 工具层补充输入器/物理世界分层说明，不新增旧术语对外输出。
- 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource=TRIGGER_SOURCE`，`core=CORE`。
- 兼容层是否仅“读旧写新”：本轮不变更业务持久化结构，无额外兼容层。
- 残余风险：`pulse/toggle` 输入波形仍受 `server.emitterEdgeMode` 配置影响；需在纯性能压测说明中明确推荐固定为 `rising`。

## 预期结果

- `performance-lite` 与 `performance-baseline` 成为真正的“纯模组性能压测层”。
- 红石块驱动保留，但只在物理世界端到端层使用。
- `256` 和后续 `512/1024` 的性能结果不再被 `north_strip` 驱动低估。
- bench 分层变为：
  - 纯性能压测层：输入器驱动
  - 物理世界端到端层：红石块/真实输入驱动
  - 命令/改链专项层：命令路径成本
