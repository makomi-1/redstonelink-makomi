# P26过滤器高压拦截功能验证用例

生成时间：2026-04-11 15:59:32
文件名：2026-04-11_155932_P26过滤器高压拦截功能验证用例.md

## 任务背景

现有 `P26` 已经覆盖 `1024 -> 1024` 的 `triggerSource/core` 高压场景，并在双侧放置最小空间覆盖的节点集过滤器，但该用例以性能采样为主，缺少“过滤器配置是否写入”和“过滤器拦截是否在高压下实际生效”的功能断言。

本轮目标是在不改业务实现的前提下，基于 `P26` 派生一条 dedicated functional case，同时覆盖：

- `triggerSource` 侧节点集 blocklist 过滤器的高压拦截验证
- `core` 侧节点集 blocklist 过滤器的高压拦截验证
- 过滤器快照断言
- 实际输出结果断言

## 方案详情

### 现状分析

- `P26` 已具备 1024 个 `triggerSource`、1024 个 `core`、8 个最小覆盖过滤器和共享节点集 blocklist 配置。
- 现有 `X27/X28/X32/X33/X34/X35` 已验证 bench 支持：
  - `command_assert` + `data get block` 的快照断言
  - `trace_latest_assert_core` 的结果断言
  - `input_start_custom_batch_triggerSource` 的批量同步高态输入
- 现有 `banded16` 映射不利于对单个代表 serial 做确定性输出断言，因此不适合作为本轮功能验证拓扑。

### 技术方案

- 新增一条 `X36` functional case，复用 `P26` 的大场地、1024 节点规模与最小覆盖过滤器布局。
- 将连线拓扑改为 `zip` 一对一，以保证在全量并发输入时，代表 `core` 的输出可以做稳定断言。
- 将验证拆成两个阶段：
  - `triggerSource` 侧过滤器启用，`core` 侧过滤器关闭，验证发送侧拦截
  - `core` 侧过滤器启用，`triggerSource` 侧过滤器关闭，验证接收侧拦截
- 过滤器节点集采用四角连续区间、整体镜像对称的短表达式 `1:4/29:32/993:996/1021:1024`，保留四覆盖区验证意义，同时避免超长 RCON 命令把功能用例拖成输入长度压力测试。
- 每个阶段均包含两层验证：
  - `拦截快照`：校验过滤器方块 NBT 中的 `serialExpression`、`nodeSetMode`、`signalThresholdSource`、`fixedSignalThreshold`、`signalMode`
  - `实际结果`：在 1024 个 `triggerSource` 同时打入 `15` 的条件下，断言四个角覆盖区内“区间内 blocked、区间外相邻 serial allowed”两类代表 `core` 输出

### 影响范围

- `tools/bench/cases/functional/x36/`
- `tools/bench/functional-matrix.json`
- dedicated bench 构建与单 case 实跑结果

- 命名统一使用 `triggerSource/core`，与 `LinkNodeType.TRIGGER_SOURCE/CORE` 映射保持一致。
- 输入与输出方向保持 `triggerSource -> core` 单向验证，不涉及反向写入。
- 未引入旧术语作为新增文案，也未新增 `com.makomi.api.v1.*` 依赖。
- 残余风险：本 functional case 已不再复用“全量奇数长串”作为功能断言输入，而是改用更短的连续对称区间，目的在于验证拦截语义本身，而不是继续把功能用例耦合到长命令传输极限。
