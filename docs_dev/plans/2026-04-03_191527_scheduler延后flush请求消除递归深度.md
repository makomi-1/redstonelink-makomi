# scheduler延后flush请求消除递归深度

生成时间：2026-04-03 19:15:27
文件名：2026-04-03_191527_scheduler延后flush请求消除递归深度.md

## 任务背景
`CoreDispatchBatchScheduler` 之前已通过“两阶段 flush”修掉 `pendingByTarget` 迭代期的并发修改问题，但 `window=0` late-arrival 补 flush 仍会在 `TargetFlushPlan.apply()` 下游执行期间再次调用 `flushServerBatches(...)`，形成递归重入。`docs_dev/更新计划草稿与索引.md` 第 315 行将此列为残余项，要求优先在 scheduler 内部用 phase queue / deferred flush request 继续收口。

## 方案详情

### 现状分析
当前 `flushLateArrivalsIfCurrentTickEndAlreadyPassed(...)` 只要判定“当前 tick END 已完成且窗口为 0”，就直接调用 `flushServerBatches(...)`。虽然 `flushServerBatches(...)` 已拆为“摘 bucket”和“统一 apply”两阶段，但 apply 期间的下游逻辑仍可能再次入队并立即请求补 flush，从而把一次 flush 扩展成递归调用链。

### 技术方案
保留现有 batch scheduler 语义，不新增 direct dispatch 旁路，只在 scheduler 内部增加“apply 期防重入 + 延后 flush 请求”：
1. `SchedulerState` 新增 apply phase 标记和 deferred flush request 标记。
2. late-arrival 命中时，如果当前不在 apply phase，仍按现有路径立即进入 flush；如果正在 apply，则只登记一次 deferred request，不做递归调用。
3. `flushServerBatches(...)` 改为外层循环 drain：每一轮先摘 bucket，再进入 apply phase；apply 结束后若检测到 deferred request，则继续下一轮，直到无待处理请求为止。

这样可以保持 `window=0` same-tick 补 flush 语义，同时把“递归立即 flush”转换为 scheduler 内部的循环 drain。
