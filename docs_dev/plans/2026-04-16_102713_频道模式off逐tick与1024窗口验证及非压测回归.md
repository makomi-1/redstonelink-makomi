# 频道模式off逐tick与1024窗口验证及非压测回归

生成时间：2026-04-16 10:27:13
文件名：2026-04-16_102713_频道模式off逐tick与1024窗口验证及非压测回归.md

## 任务背景
- 用户要求补测频道模式下 `crosschunk.directBatching=off` 的游戏内逐 tick 功能验证。
- 用户同时确认 `1024 -> 1024` 的“全窗口批打包验证”不需要新建大规模逐 tick 断言，而是直接复用现有延迟与窗口覆盖率断言框架。
- 两项专项都跑通后，需要再跑当前游戏内所有非压测测试作为收尾回归。

## 方案详情

### 现状分析
- 现有序号模式已有 single-core mixed 逐 tick 断言资产，可复用其 `sync/pulse/toggle` 组合仲裁断言模板。
- 现有 `1024 -> 1024` 专项已有 dedicated server 用的延迟与窗口覆盖率断言框架，不需要再扩新的逐 tick 大规模用例。
- 频道模式目前缺少“samechunk + mixed + directBatching=off”的 dedicated functional case，因此需要补一组最小 bench 资产。
- 当前工作区已有频道模式按边直发的生产改动，本轮不再追加生产逻辑，只补测试资产并执行验证。

### 技术方案
- 新增一个频道模式 samechunk mixed 全组合逐 tick functional case：
  - 复用序号模式 x23 的 arena、source/core 摆放与断言模板。
  - 在前置 phase 中通过 OCC 把 `triggerSource/core` 切到同一频道。
  - suite 侧设置 `crosschunk.directBatching=off`，并只验证 `dispatchBatchWindowTicks=0` 的“关闭批打包”口径。
- 复用现有 `functional-samechunk-latency-debug.json` 执行 `1024 -> 1024` 延迟与窗口覆盖率验证。
- 专项通过后，再顺序执行当前非压测 suite 集合作为收尾回归。
- 全程遵守“先构建当前工作区 jar，再同步 server jar，再开始 dedicated 验证”的规则。

### 影响范围
- `tools/bench/cases/functional/`
- `tools/bench/suites/`
- `docs_dev/plans/`
- `docs_dev/reviews/`
