# bench逐tick对齐修复

生成时间：2026-03-23 23:04:24
文件名：2026-03-23_230424_bench逐tick对齐修复.md

## 任务背景

第二阶段 bench suite 首次实跑时，5 个功能用例全部失败。结果文件显示大部分失败不是业务行为错误，而是 `trace_read_tick_assert` 只在过窄的锚点窗口内搜索起点，导致真实存在的样本被误报为 `missing_tick`。另外 `pulse_activate_sparse_zip` 的读取窗口过短，高电平样本在读取时已经滚出历史窗口。

## 方案详情

### 现状分析

- `run-bench.ps1` 当前把逐 tick 对齐搜索上界固定在 `commandEndTick + alignmentSlackTicks`。
- 实际 `trace read` 返回样本中，sync/toggle 的有效起点普遍晚于该上界，因此出现系统性假阴性。
- `pulse_activate_sparse_zip` 的 `limit=10` 无法覆盖等待结束后更早出现的脉冲高电平样本。

### 技术方案

1. 保留 `mountRef` 裁掉挂载基线样本的规则不变。
2. 在 `trace_read_tick_assert` 中基于 `eligibleSamples` 的真实最大 tick 计算扩展搜索上界，让起点搜索覆盖“真实样本最后一个可完整窗口起点”。
3. 修正失败结果中的 `candidateCount`，确保失败时记录总共尝试过多少候选，而不是“最佳失败候选”当时的局部计数。
4. 仅调整 `pulse_activate_sparse_zip` 的 `trace_read_tick_assert.limit`，保证读取结果仍能包含脉冲高电平窗口。

### 影响范围

- `tools/bench/run-bench.ps1`
- `tools/bench/functional-matrix.json`

## 原子步骤清单

### 步骤 1：修复逐 tick 搜索窗口
- **操作对象**：`tools/bench/run-bench.ps1`
- **具体动作**：在 `trace_read_tick_assert` 中引入基于真实返回样本的扩展搜索上界，并把该上界传给匹配函数。
- **预期结果**：sync/toggle 用例可以从真实样本起点完成对齐，不再因为窗口过窄而误报。
- **关键里程碑**：是

- **操作对象**：`tools/bench/run-bench.ps1`

- **预期结果**：结果文件里的 `candidateCount` 语义与真实搜索过程一致。
- **关键里程碑**：否
