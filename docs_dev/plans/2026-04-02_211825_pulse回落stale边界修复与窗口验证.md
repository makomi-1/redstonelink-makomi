# pulse回落stale边界修复与窗口验证

生成时间：2026-04-02 21:18:25
文件名：2026-04-02_211825_pulse回落stale边界修复与窗口验证.md

## 任务背景
`x24` 与新增的 pure pulse 临时 case 在 `window=2` 下会丢失第二段 pulse。已有复现表明：
- 配置覆盖与旧 jar 不同步不是剩余主因；
- `pure pulse` 场景可独立复现，说明问题不依赖 `sync/toggle` 干扰；
- `pulseDurationTicks=4` 与 trace 观测到 3 tick 高电平属于采样口径问题，不是这次功能失效的直接根因。

用户进一步要求先复核 `authorityTimeKey` 现有用途，再决定修复策略，并在实现后执行临时 `x23` 验证与 `x22` 全窗口值验证。

## 方案详情

### 现状分析
- `LinkedTargetDispatchService` 对 loaded direct 派发使用源侧当前 tick 生成 `EventMeta.timeKey`，表达“事件发生时刻”。
- `CoreDispatchBatchScheduler` 只按 `dueTick` 延迟 flush，但不会改写 `DispatchBatchEntry.eventMeta`。
- `ActivatableTargetBlockEntity.onPulseTick()` 在 pulse 回落后，若当前没有新的 winner，会以“当前 tick”作为 fallback 重算 authority。
- 该 fallback 的原始作用是给 `NONE` 态建立新的 stale guard 边界，阻止过时旧事件在回落后重新激活 `core`。
- 问题在于 loaded direct batching 合法地允许事件晚于 `eventMeta.timeKey` 若干 tick 到达；当 `window=2` 时，pulse 回落先把 authority 推到当前 tick，后续合法 delayed pulse 就会被误判为 stale。

### 技术方案
- 保持 `eventMeta.timeKey` 的语义不变，继续表示源事件发生时刻，不把 batched event 整体改写成 `dueTick`。
- 保留 pulse 回落后更新 stale guard 边界的设计，但把 fallback 从“当前 tick”调整为“当前 tick 向前回退 `dispatchBatchWindowTicks`”。
- 这样可以同时满足两点：
  - `window=0` 保持原行为不变；
  - `window>0` 时允许窗口内合法 delayed event 在回落后仍可被接受；
  - 早于该窗口的旧事件仍会被拒绝。
- 在单元测试中补两个边界：
  - pulse 回落后，窗口内 delayed pulse 仍应被接受；
  - pulse 回落后，超出窗口的旧 pulse 仍应被拒绝。

## 原子步骤清单

### 步骤 1：调整 pulse 回落 stale 边界
- **操作对象**：`ActivatableTargetBlockEntity`
- **具体动作**：抽取 pulse 回落 fallback 时间键计算逻辑，将 authority fallback 从 `now` 改为 `now - dispatchBatchWindowTicks`
- **预期结果**：`window=2` 时第二段 delayed pulse 不再被误判为 stale
- **关键里程碑**：是

### 步骤 2：补充单元测试
- **操作对象**：`ActivatableTargetBlockEntityInternalTest`
- **具体动作**：新增窗口内 delayed pulse 可通过、窗口外旧 pulse 仍拒绝的测试
- **预期结果**：修复点具备稳定回归保护
- **关键里程碑**：是

### 步骤 3：执行验证
- **操作对象**：Gradle 测试与 bench case
- **具体动作**：先跑相关单测，再跑临时 `x23` 验证与 `x22` 全窗口值验证
- **预期结果**：确认修复不破坏 `window=0/1`，并恢复 `window=2`
- **关键里程碑**：是

## 预期结果
- 保持 `triggerSource/core` 语义与事件时间键模型不变；
- 修复 pulse 在 `window=2` 下第二段波形丢失的问题；
- 不放松窗口外旧事件的 stale guard；
- 为后续继续分析“pulse 为何观测为 3 tick 高电平”保留独立问题边界。
