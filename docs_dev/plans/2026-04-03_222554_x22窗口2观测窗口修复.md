# x22窗口2观测窗口修复

## 任务背景

完整游戏内回归后，`functional-mixed-direct-debug` 的 `x22_window2` 失败。进一步对比 dedicated server 结果发现，失败点集中在 `mixed_direct_target_pulse_ticks`：`window=2` 下期望出现 pulse 高态，但 target recent trace 读到的是一段全零窗口。结合同批通过的 `x23`、既有 pulse stale guard 单测和当前结果 JSON，当前更像 bench 观测窗口不足导致的假阴性，而不是 mixed 运行时语义回归。

## 方案详情

### 现状分析

1. `x22` 的 `trace_mount_*` 已使用 `capacity=512`，但各个 `trace_read_tick_assert` 仍固定 `limit=256`。
2. 本次 `x22_window2` 结果中，`mixed_direct_target_pulse_ticks` 的 `startTickMin=4711`、`searchTickMax=4978`，跨度为 `267`，已超过 `limit=256`，真实 pulse 窗口被 recent sample 截断。
3. 同样使用 `mixed_direct_pulse_relative` 的 `x23 combo_p_target_ticks` 在 `window=2` 下通过；其 `searchTickMax-startTickMin=201`，仍落在 `256` 以内。
4. 运行时已有针对 pulse 回落 stale guard 的自动化保护，且 `x23 window=2` 能通过，因此本轮优先判定为测试模板/观测口径问题。

### 技术方案

1. 仅调整 `x22` bench case，不改运行时：
   - 将 `tools/bench/cases/functional/x22/mixed_samechunk_direct_tick_assert.json` 中相关 `trace_read_tick_assert.limit` 统一提升到 `512`。
   - 让读取窗口与 mount capacity 对齐，避免长链路下真实脉冲窗口被 recent trace 裁掉。
2. 保持 `x23` 与运行时代码不变：
   - 当前 `x23` 已通过，说明 `window=2` 下 pulse 相对延迟语义并未整体失效。
   - 避免把测试口径问题误扩散成运行时改造。
3. 验证顺序：
   - 先跑 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
   - 再重跑 `functional-mixed-direct-debug`
   - 必要时补跑 `functional-mixed-combinations-direct-debug` 作为旁证
