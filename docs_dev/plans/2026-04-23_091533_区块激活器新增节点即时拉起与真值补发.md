# 区块激活器新增节点即时拉起与真值补发

生成时间：2026-04-23 09:15:33
文件名：2026-04-23_091533_区块激活器新增节点即时拉起与真值补发.md

## 任务背景

当前区块激活器在节点集新增成员后，只会更新持久化真值与聚合贡献；新增节点往往要等后续 tick、节点重新 attach，或下一次真实输入后才体现效果。目标是补齐“新增即生效”的即时链路，并严格区分三类语义：

- `resident`：新增节点时立即补票拉起区块，随后进入常驻保持。
- `force_load`：仅对新增 `core` 做临时加载，不转成常驻。
- `triggerSource`：不为补发而加载自身区块；直接按当前真值或持久化 replay 真值补发一次 `sync`。

同时需要保持现有 `triggerSource/core` 命名与 `triggerSource -> core` 单向语义不变。

## 方案详情

### 现状分析

- 区块激活器保存链路当前只会调用 `PlacedChunkActivatorSavedData.upsert(...)`，没有节点集新增后的即时副作用。
- resident 常驻票与 transient 临时票的底座已经存在，但 resident 收集当前要求节点先 `ready`，因此不会对未 ready 节点主动补票。
- 跨区块派发之所以能拉起未加载目标，不是因为 pending 自己知道位置，而是因为 `LinkSavedData` 会保留节点最后登记的 `dimension + pos`，普通区块卸载不会立刻删掉；队列入队时先从 `LinkSavedData.findNode(...)` 拿到坐标，再把坐标写进 `PendingDispatchEntry`。
- `triggerSource` 当前可从 live block entity 或 `LinkSavedData` 的 replay snapshot 中解析“可恢复 sync 真值”，因此不必为补发额外加载其区块。

### 技术方案

1. 在区块激活器保存后，对“本次新增进入当前生效配置的节点”做增量 diff。
2. resident 新增节点时，直接基于 `LinkSavedData.findNode(...)` 得到的最后登记坐标，强制补 resident ticket bootstrap，不再受现有 resident 收集的 ready 过滤限制。
3. `force_load` 新增 `core` 时，仅补 transient ticket；等待其 chunk attach 后复用现有自动重算/target replay。
4. `triggerSource` 新增时，不加载其自身 chunk，直接按 live truth / persisted replay truth 向已链接 `core` 补发一次 `SYNC_SIGNAL UPSERT`。
5. 将“按当前真值补发一次 sync”的逻辑抽成独立 helper，供 activator 新增路径与来源 attach replay 共享，避免规则分叉。

### 影响范围

- 区块激活器保存与应用链路
- resident / transient ticket runtime 状态
- `triggerSource` sync replay helper
- 相关 Java 单元测试

### 步骤 1：补即时生效 runtime helper
- **操作对象**：新增 `com.makomi.data` helper
- **具体动作**：输入 activator 变更前后快照，计算本次新增进入生效集合的 `triggerSource/core` serial，并按 `resident / force_load / triggerSource / core` 分流执行即时效果
- **预期结果**：节点集新增后的即时效果有统一入口
- **关键里程碑**：是

### 步骤 2：接入区块激活器保存链路
- **操作对象**：`LinkChunkActivatorBlockEntity`
- **具体动作**：在 `syncPlacedActivatorState()` 中围绕 `PlacedChunkActivatorSavedData.upsert(...)` 读取前后 entry，变更成功后触发即时生效 helper
- **预期结果**：编辑器保存与 quick-link 应用后立刻生效
- **关键里程碑**：是

### 步骤 3：resident 强制补票 bootstrap
- **操作对象**：`CrossChunkDispatchTicketSupport` / `CrossChunkDispatchService.DispatchState`
- **具体动作**：复用 resident ticket 类型，基于 `LinkSavedData` 中的最后登记坐标直接添加 resident ticket，并把 ticket 写入当前 dispatch state
- **预期结果**：resident 新增节点可立即拉起区块
- **关键里程碑**：是

### 步骤 4：force_load core 临时加载
- **操作对象**：`CrossChunkDispatchTicketSupport`
- **具体动作**：复用 transient ticket 机制，对新增 `core` 补临时加载，不追加第二次手工派发
- **预期结果**：未加载 `core` 可立即 attach，后续自动重算
- **关键里程碑**：否

### 步骤 5：triggerSource 当前真值补发
- **操作对象**：`InternalDispatchDeltaRuleSupport` / `LinkNodeLifecycleDispatchEvents`
- **具体动作**：抽出 live truth + persisted replay truth 的统一解析与补发 helper，对新增 `triggerSource` 直接向已链接 `core` 补一次 sync
- **预期结果**：`triggerSource` 新增后无需加载自身区块也能立即补发当前真值
- **关键里程碑**：是

### 步骤 6：补测试与回归
- **操作对象**：`src/test/java/com/makomi/data/**`
- **具体动作**：覆盖 resident bootstrap、force_load core transient、triggerSource persisted replay truth 补发三条路径
- **预期结果**：新增语义有自动化保护
- **关键里程碑**：是

## 预期结果

- `resident` 节点集新增后，节点对应区块会立即被补 resident ticket 拉起并持续常驻。
- `force_load` 新增 `core` 后，会立即得到 transient ticket，attach 后自动重算，无额外重复补发。
- `triggerSource` 新增后，会立即按当前可恢复真值补发一次 sync，不依赖 `syncSourceAttachReplay.enabled`。
- 全流程继续保持 `triggerSource/core` 命名和 `triggerSource -> core` 单向语义不变。
