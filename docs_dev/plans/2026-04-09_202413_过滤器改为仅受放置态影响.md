# 过滤器改为仅受放置态影响

生成时间：2026-04-09 20:24:13
文件名：2026-04-09_202413_过滤器改为仅受放置态影响.md

## 任务背景
当前发送/接收过滤器的参与判定仍同时依赖两类运行时条件：一是区块上下文附着时才进入内存索引，二是过滤器自身邻居输入为非零时才返回运行时求值视图。用户要求把过滤器改为“不受区块活动影响，只受放置态改变影响”，并明确放置态变化的自感知可参考节点的生命周期方法。

## 方案详情

### 现状分析
- 过滤器索引目前由 `LinkDispatchFilterService` 以纯运行时内存结构维护，不写入 `SavedData`。
- `AbstractLinkFilterBlockEntity.clearRemoved()/setRemoved()` 直接跟随区块附着/脱附对索引做 upsert/remove，导致区块卸载会让过滤器离线。
- `AbstractLinkFilterBlockEntity.buildRuntimeViewIfEnabled()` 又把邻居输入 `<= 0` 视为过滤器整体未激活。
- 当前实现无法满足“只要还放着就有效”的语义，尤其在区块未加载或服务端重启后会丢失过滤器真值。

### 技术方案
1. 新增过滤器专用持久化 `SavedData`，把“已放置过滤器”的真值持久化为维度、位置、过滤器种类、配置快照、解析后序号集合与最近一次邻居采样值。
2. 为过滤器引入简化版生命周期状态机，参考节点生命周期对“普通上下文脱附”和“真实物理移除”做区分：
   - 区块卸载触发的 `setRemoved()` 不删除过滤器持久化记录
   - 方块被破坏或替换时才移除记录
3. 重构 `LinkDispatchFilterService`：
   - 运行时区块倒排索引改为由持久化记录重建与维护
   - 查询时不再依赖当前已加载的 `BlockEntity`
   - 去掉“邻居输入非零才整体参与”的总开关
4. 保留 `POWERED` 作为客户端/状态外显；若配置选择 `NEIGHBOR_MAX_INPUT`，则通过邻居变化时采样并持久化最近一次输入值参与阈值计算。

## 原子步骤清单

### 步骤 1：新增过滤器持久化模型与存储
- **操作对象**：`src/main/java/com/makomi/data/`
- **具体动作**：新增过滤器条目模型、`SavedData` 与编解码，并提供 upsert/remove/query 接口
- **预期结果**：过滤器真值能够跨区块卸载与服务端重启保持存在
- **关键里程碑**：是

### 步骤 2：引入过滤器生命周期状态机
- **操作对象**：`AbstractLinkFilterBlockEntity`、`AbstractLinkFilterBlock`
- **具体动作**：区分普通上下文脱附和真实物理移除，只在放置态变化时更新持久化过滤器条目
- **预期结果**：区块活动不再改变过滤器是否存在
- **关键里程碑**：是

### 步骤 3：重构过滤查询与求值
- **操作对象**：`LinkDispatchFilterService`
- **具体动作**：改为从持久化过滤器条目收集候选并构造运行时视图，去掉邻居非零总开关
- **预期结果**：过滤器只要处于放置态就参与查询
- **关键里程碑**：是

### 步骤 4：收口邻居输入更新
- **操作对象**：`AbstractLinkFilterBlock`、`AbstractLinkFilterBlockEntity`
- **具体动作**：在邻居变化时更新 `POWERED` 外显和最近一次邻居输入采样值
- **预期结果**：`NEIGHBOR_MAX_INPUT` 仍可用，但不再决定过滤器是否存在
- **关键里程碑**：否

- **关键里程碑**：是

## 预期结果
发送过滤器与接收过滤器会从“运行时已加载对象”转为“放置态持久化对象”：只要过滤器仍放在世界中，就会继续参与 `triggerSource -> core` 过滤；区块加载、卸载和服务端重启不再改变其存在性，只有放置、破坏、替换等放置态变化才会影响过滤器真值。
