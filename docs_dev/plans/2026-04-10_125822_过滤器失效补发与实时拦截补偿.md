# 过滤器失效补发与实时拦截补偿

生成时间：2026-04-10 12:58:22
文件名：2026-04-10_125822_过滤器失效补发与实时拦截补偿.md

## 任务背景

当前过滤器已经从“仅依赖运行时已加载实例”改为“放置态持久化真值”，并且 attach replay 已经能够在发布前按持久化过滤真值补判。但过滤器后续发生配置变化、邻居输入零态变化、`NEIGHBOR_MAX_INPUT` 阈值变化或物理移除时，现有实现只会更新 `PlacedLinkFilterSavedData`，不会回推已经存在的 `triggerSource -> core` 贡献。

这会带来两类问题：
1. 过滤器由放行变拦截后，目标上可能残留旧的 `sync/toggle/pulse` 贡献，缺少主动失效。
2. `sync` 新信号在实时派发时若被 send/receive 过滤器拦截，当前实现只是跳过派发，不会清掉同源旧贡献，导致“前信号未拦截、后信号被拦截”时目标态残留。

本轮目标是在不破坏现有 `triggerSource -> core` 单向语义、不把阻塞世界读取带回启动附着路径的前提下，补齐过滤器变化触发的失效/补发事件，以及 `sync` 实时拦截时的残留清理。

## 方案详情

### 现状分析

- 过滤器配置和邻居输入更新目前主要通过 `AbstractLinkFilterBlockEntity.applySnapshot(...)`、`AbstractLinkFilterBlock.neighborChanged(...)`、`onPlace(...)`、`setRemoved()` 与 `LinkDispatchFilterService.refreshLoadedNeighborSignalSnapshotsAfterServerStarted(...)` 汇总到 `LinkDispatchFilterService`。
- `AbstractLinkFilterBlockEntity.clearRemoved()` 当前只恢复放置态真值，不做邻居读取；这是为了避免启动附着阶段同步读取世界邻居输入而卡住世界进入流程。
- attach replay 已经会在 `LinkNodeLifecycleDispatchEvents` 中直接按持久化过滤真值判定是否允许重放，但这条链只覆盖“节点 attach 时是否发 replay”，不覆盖“过滤器运行期变化后如何回推已存在贡献”。
- 现有 delta 主链已经具备可复用的事件：
  - `TRIGGER_SOURCE_INVALIDATION + REMOVE` 可清掉同源在目标上的 `toggle/pulse/sync` 贡献；
  - `SYNC_SIGNAL + UPSERT` 可用于重新补发当前 `sync` 真值。
- 当前缺失的是“过滤器变化 -> 受影响链路 diff -> 发布 delta”这一层桥接。

### 技术方案

1. 为在线节点引入仅运行时生效的空间索引，按 `dimension + nodeType + chunk` 维护在线 `triggerSource/core` 候选集合，供过滤器立方域扫描复用，避免每次过滤器变化都全表遍历在线节点。
2. 在 `LinkDispatchFilterService` 中增加过滤器变化协调入口，区分两类路径：
   - 恢复路径：`clearRemoved()` 仍只做“恢复放置态真值”，不触发失效/补发扫描；
   - 真实变化路径：配置修改、邻居变化、启动后非阻塞补采样成功、物理移除，统一走“before/after 差分协调”。
3. 差分协调统一按 `beforeAllowed/afterAllowed` 收口：
   - `beforeAllowed && !afterAllowed`：发布 `TRIGGER_SOURCE_INVALIDATION`；
   - `!beforeAllowed && afterAllowed`：仅对 `sync` 发布 `SYNC_SIGNAL UPSERT`。
4. send/receive 两类过滤器分别按方向展开受影响链路：
   - send 过滤器变化：先找过滤器立方域内的 `triggerSource`，再展开其已连接 `core`；
   - receive 过滤器变化：先找过滤器立方域内的 `core`，再反查其已连接 `triggerSource`。
5. 补发严格限制为 `sync`。当前仓库只有 `SyncReplaySourceBlockEntity` 与 `LinkSavedData.triggerSourceReplaySyncSnapshots` 能稳定提供“当前可恢复 sync 真值”；`toggle/pulse` 仍保留事件语义，不做历史补发。
6. `sync` 实时派发链补齐“被拦截时主动失效”补偿：
   - send 过滤器拒绝时，对来源此前仍放行的已连接目标发布 invalidation；
   - receive 过滤器拒绝时，对该 `triggerSource -> core` 发布 invalidation。
   这样可以覆盖“同源新信号被拦截，且前信号未被拦截”的残留场景。
7. 过滤器变化导致的失效/补发采用“当前变化时刻”的时间键，而不是复用历史 replay 时间键；因为这里是“当前过滤条件重算”，不是“历史事件原样回放”。

## 原子步骤清单

### 步骤 1：新增在线节点运行时空间索引
- **操作对象**：`LinkSavedData` 及其 support
- **具体动作**：维护按维度、节点类型、区块键组织的在线节点索引，并提供“按过滤器立方域收集在线 `triggerSource/core` 候选”的查询入口
- **预期结果**：过滤器变化扫描只命中局部候选节点，不再全量遍历在线节点表
- **关键里程碑**：是

### 步骤 2：抽出过滤器变化协调入口
- **操作对象**：`LinkDispatchFilterService`
- **具体动作**：保留仅恢复真值的 `upsert` 路径，同时新增“before/after 差分协调”入口，供配置修改、邻居变化、启动后补采样、物理移除复用
- **预期结果**：启动恢复路径与真实变化路径语义分离，避免误把 `clearRemoved()` 当作一次过滤器生效事件
- **关键里程碑**：是

### 步骤 3：实现 send/receive 过滤器变化的失效与补发扫描
- **操作对象**：过滤器变化协调 helper、`LinkDispatchFilterService`
- **具体动作**：按 send/receive 两种过滤器方向展开受影响链路，计算 `beforeAllowed/afterAllowed`，发布 invalidation 或 `sync` upsert
- **预期结果**：配置变化、邻居零态变化、邻居最大输入变化和物理移除都能统一触发失效/补发
- **关键里程碑**：是

### 步骤 4：补齐 `sync` 实时派发被拦截时的残留清理
- **操作对象**：`LinkSyncEmitterBlock`、`TriggerSourceBlockEntity`、`LinkedTargetDispatchService`
- **具体动作**：在 send/receive 过滤器拦截实时 `sync` 新信号时，对此前仍放行的同源贡献发布 invalidation，再提交新的观察快照
- **预期结果**：`sync` 新信号被拦截时不再残留旧贡献
- **关键里程碑**：是

### 步骤 5：补充测试并回归验证
- **操作对象**：过滤器相关测试、dispatch 相关测试
- **具体动作**：覆盖 send/receive 拦截失效、邻居阈值变化、`sync` 被拦截残留清理、`sync` 解除拦截补发、`clearRemoved()` 不触发协调等边界
- **预期结果**：失效/补发与实时拦截补偿具备可自动回归验证的证据
- **关键里程碑**：是

## 预期结果

过滤器后续发生配置变化、邻居输入零态变化、`NEIGHBOR_MAX_INPUT` 阈值变化或物理移除时，会以当前持久化真值为基准重新扫描受影响的 `triggerSource -> core` 链路：

- 原本放行、现在拦截的链路会主动发布失效事件，清掉目标上的旧贡献；
- 原本拦截、现在重新放行的链路，若来源存在当前可恢复的 `sync` 真值，则会补发一次 `sync`；
- `toggle/pulse` 继续保持事件语义，不做历史补发；
- 启动附着路径仍保持非阻塞，不把世界同步邻居读取带回 `clearRemoved()`。

## 语义对齐说明

- **命名检查**：新增设计与文案统一使用 `triggerSource/core`，不引入 `button/source/target` 等旧术语。
- **方向检查**：所有扫描、判定与事件发布都只围绕 `triggerSource -> core` 方向展开，不新增反向写入。
- **映射检查**：内部仍与 `LinkNodeType.TRIGGER_SOURCE/CORE` 一一对应。
- **兼容检查**：兼容层仅保持“读旧写新”；不引入 `com.makomi.api.v1.*` 依赖。
- **残余风险**：
  1. 若运行时空间索引裁剪不充分，过滤器频繁邻居抖动时仍可能产生额外主线程扫描成本。
  2. 离线目标上的历史 `SYNC_SIGNAL` 与后续 invalidation 仍可能存在瞬态先亮后灭窗口；如本轮不顺手补“失效优先短路”，该窗口仍属已知残余风险。
