# occ游戏内回归与bench接入

生成时间：2026-04-07 17:29:35
文件名：2026-04-07_172935_occ游戏内回归与bench接入.md

## 任务背景
当前 `PairingNetwork` 与 `QuickLinkNetwork` 已分别具备基于 `graphRevision/sourceRevision` 的乐观并发控制能力，但游戏内 bench/functional 仍缺少一条可重复、可回归、可注入 stale baseline 的测试链路。

现状下：
- pairing 与 quick-link 的 OCC 判定分散在各自服务端入口；
- bench 只能通过命令和文本断言驱动，无法直接读取 revision 基线并在后续阶段安全复用；
- dedicated functional 尚未覆盖 `triggerSource/core` 两类目标下的 OCC 冲突场景。

本轮目标是在不引入 `com.makomi.api.v1.*`、不改变 `triggerSource -> core` 方向约束的前提下，完成共享 OCC 提交适配、bench OCC 命令、functional 捕获能力与 dedicated regression case/suite 的接入。

## 方案详情

### 现状分析
- `LinkSavedData` 已提供 `graphRevision/sourceRevision` 运行时真值，可作为唯一 OCC 基线来源。
- `PairingNetworkServerHandlerSupport` 与 `QuickLinkNetworkServerHandlerSupport` 均已在正式提交前校验 expected revision，但判定和反馈组装仍散落在入口层。
- `BenchCommandRegistry` 目前只有 `input/link/trace`，没有 OCC baseline 读取与 stale baseline 提交入口。
- `tools/bench/lib/Bench.FunctionalTrace.ps1` 已支持 `phase:*` 属性引用，但 `command_assert` 只保存原始 response，不会把命令文本中的 revision 捕获为结构化字段。

### 技术方案
1. 新增共享 OCC 提交适配层：
   - 抽出 revision mismatch 判定、冲突反馈构造与提交前校验；
   - pairing / quick-link / bench 统一复用该适配层；
   - 保持 `triggerSource` 目标比较 `sourceRevision`，`core` 目标比较 `graphRevision`。
2. 新增 bench OCC 命令：
   - `bench occ snapshot`：按节点读取稳定 revision 基线；
   - `bench occ pairing submit`：以 bench/internal 方式提交 stale baseline；
   - `bench occ quick_link ...`：以 bench/internal 方式触发 quick-link OCC 提交。
3. 扩展 functional `command_assert`：
   - 支持基于 regex 命名组或键值解析，把 response 提取为 `captures.*`；
   - 允许后续 phase 通过 `{{phase:<name>.captures.<field>}}` 引用动态 revision。
4. 新增 OCC functional case 与 suite：
   - pairing + `triggerSource`
   - pairing + `core`
   - quick-link + `triggerSource`
   - quick-link + `core`
   均采用“读 baseline -> 插入真实修改 -> 用旧 baseline 提交 -> 断言冲突且拓扑不被覆盖”的固定时序。

### 技术取舍
- 不优先实现 bench 真并发：
  Minecraft 服务端提交最终仍串行落在主线程，本轮需要验证的是 stale baseline 冲突，而不是 CPU 级并行。
- 不走 UI 自动化点击回放：
  直接提供 bench/internal OCC 命令更稳定，失败定位也更明确。
- 不新增第二套 revision 源：
  所有 baseline 与冲突判定统一复用 `LinkSavedData` 真值。

### 影响范围
- `src/main/java/com/makomi/network/PairingNetworkServerHandlerSupport.java`
- `src/main/java/com/makomi/network/QuickLinkNetworkServerHandlerSupport.java`
- `src/main/java/com/makomi/command/bench/**`
- `tools/bench/lib/Bench.FunctionalTrace.ps1`
- `tools/bench/cases/functional/**`
- `tools/bench/functional-matrix.json`
- `tools/bench/suites/**`
- `docs_dev/使用说明.md`
- `docs_dev/reviews/`

### 语义对齐说明
- 命名校验：新增命令、字段、注释、文案统一使用 `triggerSource/core`。
- 方向校验：所有真实写入仍限定为 `triggerSource -> core`，`core` 视角仅作为观察/批量编辑入口。
- 文案校验：不新增旧术语输出；若存在兼容输入，仅限读取旧语义，不写回旧术语。
- 映射校验：`triggerSource=LinkNodeType.TRIGGER_SOURCE`，`core=LinkNodeType.CORE`。
- 兼容层校验：bench/internal 仅“读真值、写新协议”，不引入 API 层依赖。
- 残余风险：quick-link 的游戏内 bench 驱动若需要模拟物品缓存，可能需要补一个 bench/internal 最小工具快照入口；当前先按最小实现预留。

## 原子步骤清单

### 步骤 1：抽共享 OCC 提交适配层
- **操作对象**：`PairingNetworkServerHandlerSupport`、`QuickLinkNetworkServerHandlerSupport`、必要的新 helper
- **具体动作**：抽出 revision 判定、冲突反馈与提交前校验，使 pairing/quick-link/bench 共用同一套 OCC 提交逻辑
- **预期结果**：网络入口与 bench 不再重复维护 OCC 判定细节
- **关键里程碑**：是

### 步骤 2：新增 bench OCC 命令
- **操作对象**：`src/main/java/com/makomi/command/bench/**`
- **具体动作**：补 `occ snapshot/submit` 子命令，支持读取 baseline 并用指定 expected revision 提交 stale baseline
- **预期结果**：游戏内可稳定构造 OCC 冲突场景
- **关键里程碑**：是

### 步骤 3：扩 functional command_assert 捕获能力
- **操作对象**：`tools/bench/lib/Bench.FunctionalTrace.ps1`
- **具体动作**：在 phase result 中保存结构化 `captures`，并允许模板通过 `phase:*` 读取
- **预期结果**：上一阶段读取的 revision 可安全传递到下一阶段
- **关键里程碑**：是

### 步骤 4：新增 OCC functional cases 与 suite
- **操作对象**：`tools/bench/cases/functional/**`、`tools/bench/functional-matrix.json`、`tools/bench/suites/**`
- **具体动作**：接入四类 OCC 冲突 case，并提供 dedicated regression suite
- **预期结果**：OCC 场景进入 dedicated regression 门禁
- **关键里程碑**：是

### 步骤 5：验证、说明与审查文档
- **操作对象**：Gradle 全标签测试、OCC 专项 suite、`docs_dev/使用说明.md`、`docs_dev/reviews/`
- **具体动作**：完成实现后执行自动化验证，按规则补使用说明与五段式审查文档
- **预期结果**：实现、测试与风险结论可追溯
- **关键里程碑**：是

## 预期结果
- pairing / quick-link / bench 复用同一套 OCC 提交判定闭环；
- bench functional 能读取 revision 并安全传递到后续 phase；
- dedicated server 下可稳定回归四类 stale baseline 冲突场景；
- 整体实现继续遵守 `triggerSource/core` 语义与 `triggerSource -> core` 方向约束。
