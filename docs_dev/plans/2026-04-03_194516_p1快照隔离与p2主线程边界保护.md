# p1快照隔离与p2主线程边界保护

生成时间：2026-04-03 19:45:16
文件名：2026-04-03_194516_p1快照隔离与p2主线程边界保护.md

## 任务背景
`docs_dev/更新计划草稿与索引.md` 第 251-302 行对“并发控制完善”提出了两类近期应先收口的结构性风险：
1. `LinkSavedData` 的内部链接集合仍可能以可变视图形式流入生命周期事件链，缺少快照隔离；
2. `CrossChunkDispatchService` 与 `CoreDispatchBatchScheduler` 的全局状态容器主要依赖“默认在服务端主线程调用”的约定，缺少显式线程边界防护。

当前仓库已不是“完全无结构化入口”的旧状态：GUI 配对已走结构化 payload，内部监听器列表也已改为 `CopyOnWriteArrayList`。因此本轮不做事务层/版本化改造，而是先以最小改动收口 P1/P2。

## 方案详情

### 现状分析
- `linkedTargetsViewBySourceType(...)` 仍会返回内部 `Set` 视图；生命周期调度直接拿它去发 detach / attach / replay 事件，规则层又会继续遍历该集合。
- `CrossChunkDispatchService.STATE_BY_SERVER` 与 `CoreDispatchBatchScheduler.STATE_BY_SERVER` 目前没有像 `LinkNodeLifecycleDispatchEvents` 那样的显式边界保护，未来若从异步任务误入，容易静默污染状态。
- 现有大量单测会用 `server = null` 的反射方式直接调用内部方法，因此主线程 guard 需要对 `null` 服务器保持测试友好。

### 技术方案
1. P1 快照隔离：
   - 将生命周期调度对链接集合的读取统一改为快照语义，避免继续暴露内部可变 `Set`。
   - 收缩 `linkedTargetsViewBySourceType(...)` 的对外使用面，使其不再作为生命周期事件链的读取入口。
2. P2 主线程边界保护：
   - 在 `com.makomi.data` 下新增一个轻量主线程校验 helper。
   - 对 `CrossChunkDispatchService` 与 `CoreDispatchBatchScheduler` 的状态入口加统一校验：若 `server != null` 且当前不在服务端主线程，则立即抛出明确异常。
   - 对 `server == null` 的测试调用保持放行，避免打断现有反射单测。

### 影响范围
- `src/main/java/com/makomi/data/LinkSavedData.java`
- `src/main/java/com/makomi/data/LinkSavedDataLinkIndexSupport.java`
- `src/main/java/com/makomi/data/LinkNodeLifecycleDispatchEvents.java`
- `src/main/java/com/makomi/data/CrossChunkDispatchService.java`
- `src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java`
- `src/main/java/com/makomi/data/*` 下新增主线程 guard helper
- 相关 `src/test/java/com/makomi/data/**` 测试

## 原子步骤清单

### 步骤 1：收缩内部集合视图暴露
- **操作对象**：`LinkSavedData`、`LinkSavedDataLinkIndexSupport`
- **具体动作**：补稳定快照读取 helper，并移除生命周期路径对 `linkedTargetsViewBySourceType(...)` 的依赖
- **预期结果**：生命周期与事件规则链路拿到的都是稳定快照
- **关键里程碑**：是

### 步骤 2：改造生命周期调度读取链
- **操作对象**：`LinkNodeLifecycleDispatchEvents`
- **具体动作**：detach / target attach replay / source attach replay 三处统一改成快照读取
- **预期结果**：P1 风险点被最小范围收口
- **关键里程碑**：是

### 步骤 3：新增统一主线程边界 helper
- **操作对象**：`com.makomi.data` 新 helper
- **具体动作**：封装“`server != null` 且不在主线程时抛异常”的校验逻辑
- **预期结果**：后续状态服务可复用同一套 guard
- **关键里程碑**：是

### 步骤 4：接入 CrossChunk / Scheduler
- **操作对象**：`CrossChunkDispatchService`、`CoreDispatchBatchScheduler`
- **具体动作**：把状态 map 的关键读写入口和外部入口接到统一主线程 guard
- **预期结果**：P2 从“依赖约定”升级为“代码显式保护”
- **关键里程碑**：是

### 步骤 5：补测试并验证
- **操作对象**：相关 data 测试
- **具体动作**：补快照隔离和线程边界断言，然后执行 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
- **预期结果**：P1/P2 的结构性修复具备自动化保护
- **关键里程碑**：是

## 预期结果
生命周期调度不再把 `LinkSavedData` 的内部可变链接集合直接传入事件链；`CrossChunkDispatchService` 与 `CoreDispatchBatchScheduler` 对跨线程误用具备显式失败保护，同时不改变当前 `triggerSource -> core` 语义和现有存档结构。
