# core配对链路迁移

生成时间：2026-04-03 17:57:50
文件名：2026-04-03_175750_core配对链路迁移.md

## 任务背景
`docs_dev/更新计划草稿与索引.md` 第 312 行指出：`core` 配对仍走旧命令路径，其旧方向语义尚未完全收口。当前仓库已经完成两项前置工作：

1. `triggerSource` 配对界面提交已从命令字符串迁移到结构化 `C2S` 协议。
2. `link set` 已抽出共享写入服务 `LinkSetExecutionService`，可供命令与网络入口复用。

本轮目标是在不引入 `com.makomi.api.v1.*` 依赖、不扩大玩法入口的前提下，把 `core` 配对界面的提交链路迁移到新实现上，并保证真实写入仍统一收口为 `triggerSource -> core`。

## 方案详情

### 现状分析
1. `CorePairingScreen` 当前没有覆写提交逻辑，仍沿用 `AbstractMultiPairingScreen` 默认命令兼容路径，发送 `redstonelink link set core <coreSerial> ...`。
2. `PairingNetwork` 当前只为 `triggerSource` 配对提供了结构化提交 payload，`core` 侧仍只有“打开界面”回包，没有对应的结构化写入请求。
3. `LinkSavedData` 与 `LinkSavedDataLinkIndexSupport` 虽然保留了 `CORE` 视角的兼容查询/替换能力，但项目语义规范要求新增实现统一使用 `triggerSource/core`，且真实写入必须保持 `triggerSource -> core` 单向约束。
4. `QuickLinkApplyService.applyCachedTriggerSourcesToCore(...)` 已经证明“以 core 为观察中心、内部拆成多个 triggerSource 正向写入”是可行路径；本轮可沿用相同语义，而不是继续把 `core` 视为来源。

### 技术方案
1. 在 `LinkSetExecutionService` 中补一层“结构化目标集合准备”入口：
   - 输入固定为 `triggerSource` 序列号与结构化 `core` 集合。
   - 复用现有校验、写控判定、命令成本计算与后续 apply 闭环。
2. 在 `PairingNetwork` 中新增 `SubmitCorePairingPayload`：
   - 客户端提交 `coreSerial + triggerSourceExpression`。
   - 服务端解析出期望的 `triggerSource` 集合后，按差异把这次编辑转换为多个 `triggerSource -> core` 正向覆盖操作。
3. 为 `core` 侧新增专用协调逻辑：
   - 先校验 `coreSerial` 本身有效。
   - 读取当前已连接到该 `core` 的 `triggerSource` 集合。
   - 计算“需要保留连到该 core 的 triggerSource”与“需要从该 core 上移除的 triggerSource”。
   - 对每个受影响的 `triggerSource` 生成其新的 `core` 目标集合，再统一走共享写入服务准备与执行。
4. `CorePairingScreen` 改为发送结构化 payload，不再拼装 `link set core ...` 命令字符串。

### 技术取舍
1. 不直接把旧 `link set core` 命令路径换成新 payload：
   - 优势：避免把旧方向语义固化到新协议层。
   - 代价：需要额外写一个“core 视角协调层”。
2. 保留 `core` 配对界面作为用户入口，但只把它视为“观察中心/编辑器”，不把 `core` 视为真实来源：
   - 优势：用户交互变化最小。
   - 代价：服务端执行会拆成多条正向写入，反馈汇总略复杂。
3. 继续复用 `LinkSetExecutionService` 而不是再写一套 `core` 专用写入规则：
   - 优势：写控、限流、副作用同步口径保持一致。
   - 代价：需要对共享服务做最小扩展，支持结构化目标集合准备。

### 语义对齐说明
1. 命名是否仅使用 `triggerSource/core`：是。新增 payload、服务端协调逻辑、文档说明统一使用 `triggerSource/core`。
2. 输入/输出结构是否保持方向一致：是。`core` 只作为编辑上下文，真实写入统一拆成 `triggerSource -> core`。
3. 文案与注释是否无旧术语泄漏：是。新增实现不输出 `button/source/target` 等旧术语。
4. 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource=TRIGGER_SOURCE`，`core=CORE`。
5. 兼容层是否仅“读旧写新”：是。旧界面打开与历史存量数据读取继续兼容，新增提交链路全部按新正向实现写入。
6. 残余风险：旧的显式命令兼容入口 `link set core ...` 仍在命令层保留，本轮仅迁移 GUI/网络提交链路，不主动清理该命令。

## 原子步骤清单

### 步骤 1：补共享写入服务的结构化准备入口
- **操作对象**：`LinkSetExecutionService`
- **具体动作**：抽出可接受结构化目标集合的准备入口，供 `core` 视角协调逻辑复用
- **预期结果**：服务端可以直接为某个 `triggerSource` 计算并准备“下一版 core 集合”
- **关键里程碑**：是

### 步骤 2：新增 core 配对结构化 payload
- **操作对象**：`PairingNetwork`、`PairingNetworkPayloadSupport`、`PairingNetworkRegistrationSupport`
- **具体动作**：新增 `SubmitCorePairingPayload` 的定义、编解码与接包注册
- **预期结果**：`core` 配对界面具备独立结构化提交入口
- **关键里程碑**：是

### 步骤 3：实现 core 视角到正向写入的协调层
- **操作对象**：`PairingNetworkServerHandlerSupport`
- **具体动作**：解析目标 `triggerSource` 集合，按差异计算每个受影响 `triggerSource` 的新 `core` 集合，并统一复用共享写入服务执行
- **预期结果**：`core` 配对提交真实落地为多条 `triggerSource -> core` 写入
- **关键里程碑**：是

### 步骤 4：切换客户端 core 配对提交链路
- **操作对象**：`CorePairingScreen`
- **具体动作**：覆写提交/清空逻辑，改发 `SubmitCorePairingPayload`
- **预期结果**：客户端不再发送 `link set core ...` 命令字符串
- **关键里程碑**：是

### 步骤 5：补齐测试与验证
- **操作对象**：`src/test/java/com/makomi/network/`、Gradle 测试任务
- **具体动作**：补 payload 编解码和服务端协调逻辑测试，随后执行全标签自动化测试
- **预期结果**：迁移行为有自动化回归约束
- **关键里程碑**：是

## 预期结果
1. `core` 配对界面的提交链路迁移到结构化 `C2S` 协议。
2. `core` 视角编辑不再把 `core` 固化为真实来源，实际写入统一按 `triggerSource -> core` 落地。
3. 写控、限流、delta、副作用同步继续复用共享写入闭环，不新增第二套规则。
4. `docs_dev/更新计划草稿与索引.md` 第 312 行所述“core 配对仍走旧命令路径”的残余问题在 GUI/网络入口层完成收口。
