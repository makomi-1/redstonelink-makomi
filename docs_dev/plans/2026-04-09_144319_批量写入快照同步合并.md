# 批量写入快照同步合并

生成时间：2026-04-09 14:43:19
文件名：2026-04-09_144319_批量写入快照同步合并.md

## 任务背景
当前 `quick-link` 批量把多组 `triggerSource` 覆写到同一个 `core`，以及 `core` 视角批量编辑时，都会逐条执行 `LinkSetExecutionService.applyPreparedReplace(...)`。真实写入语义正确，但每条写入后都会立即触发一次受影响节点客户端同步与物品快照刷新，导致同一个目标节点在热点批量场景下被重复同步。

## 方案详情

### 现状分析
- `LinkSetExecutionService.applyPreparedReplace(...)` 当前在每次单条写入后立即调用受影响节点同步与物品快照刷新。
- `QuickLinkApplyService.applyCachedTriggerSourcesToCore(...)` 会对每个来源逐条调用一次写入闭环。
- `CoreLinkEditingService.applyPreparedReplace(...)` 也会遍历 prepared operations 逐条执行。

### 技术方案
- 在 `LinkCommandSupport` 中新增批量同步收集器，负责按“节点类型 + 序号”去重收集受影响节点，以及按“来源类型 + 序号”去重收集需要回写物品快照的来源。
- 将 `LinkSetExecutionService.applyPreparedReplace(...)` 的后置同步拆成“登记到收集器”与“即时同步”两种路径：
  - 旧入口保持即时同步，确保普通单条写路径行为不变。
  - 新增带收集器的入口，供批量路径延迟到最后统一 flush。
- 把 `QuickLinkApplyService` 与 `CoreLinkEditingService` 接入新入口，在批量循环结束后统一 flush。

### 影响范围
- `src/main/java/com/makomi/command/link/LinkCommandSupport.java`
- `src/main/java/com/makomi/command/link/LinkSetExecutionService.java`
- `src/main/java/com/makomi/data/QuickLinkApplyService.java`
- `src/main/java/com/makomi/command/link/CoreLinkEditingService.java`

## 原子步骤清单

### 步骤 1：抽取批量同步收集器
- **操作对象**：`LinkCommandSupport`
- **具体动作**：新增去重收集与统一 flush 入口，封装节点同步和物品快照同步
- **预期结果**：批量写路径可复用统一的后置同步合并能力
- **关键里程碑**：是

### 步骤 2：扩展单条写入执行服务
- **操作对象**：`LinkSetExecutionService`
- **具体动作**：保留旧即时同步入口，新增可选批量收集器路径
- **预期结果**：不改变单条写入语义，同时为批量路径提供合并同步能力
- **关键里程碑**：是

### 步骤 3：接入热点批量入口
- **操作对象**：`QuickLinkApplyService`、`CoreLinkEditingService`
- **具体动作**：逐条执行真实写入，但把后置同步改为批后统一 flush
- **预期结果**：同一个 `core` 在批量编辑热点下只做一次客户端同步
- **关键里程碑**：是

### 步骤 4：验证与审查
- **操作对象**：相关 Java 文件与自动化测试
- **具体动作**：执行全标签自动化测试并补审查文档
- **预期结果**：确认语义不变且回归通过
- **关键里程碑**：是

## 预期结果
批量写入场景下，真实拓扑写入、revision 推进与 OCC 语义保持不变，但受影响节点客户端同步与物品快照刷新改为按唯一节点/来源合并，减少重复同步成本。
