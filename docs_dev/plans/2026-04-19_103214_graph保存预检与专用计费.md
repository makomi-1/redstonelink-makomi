# graph保存预检与专用计费

生成时间：2026-04-19 10:32:14
文件名：2026-04-19_103214_graph保存预检与专用计费.md

## 任务背景

当前 graph 网页编辑的“应用到草稿”只是前端本地动作，只有点击 Save 时才会真正进入服务端 `prepare + 限流 + 落地` 链路。这样会导致：

- 用户在草稿阶段看不到真实保存成本与限流风险；
- 保存失败后只能依赖一级撤回，体验不足；
- 现有 `LINK_RW` 计费口径原本面向普通游戏内改边，不适合网页的大批量 graph 保存。

本轮目标是在不改变真实 `triggerSource -> core` 保存语义的前提下，新增 graph 专用保存计费与 preview 预检链路，把风险前移到“应用到草稿”阶段。

## 方案详情

### 现状分析

- graph 保存当前统一走 `GraphWriteService.submit(...)`，并直接复用 `LINK_RW` 分组做限流。
- `LINK_RW` 当前成本来自普通 `PreparedReplaceOperation.commandCost()` 叠加，口径偏向普通逐次改边。
- 前端 `applyLocalDraftChange(...)` 只写本地草稿，不触达服务端，因此无法拿到真实限流窗口状态。
- 本地网页 bridge 目前只有 `/api/graph/save` 与 `/api/graph/draft`，没有 graph preview 接口。

### 技术方案

- 新增 graph 专用命令分组与容量配置，例如 `GRAPH_WRITE`，与普通 `LINK_RW` 解耦。
- 在 `GraphWriteService` 中提取 graph 专用写入单元与成本模型：
  - 显式 `ReplaceTriggerSourceTargets`：按真实变更的 `triggerSource` 数量计单元；
  - 批量频道编辑：按 `changedTriggerSourceCount + changedChannelNodeCount` 计单元；
  - 别名仍保留在 `OTHER` 分组，但 preview 同步反馈。
- 新增 graph preview 入口，复用 graph 保存的 prepare 逻辑，但不真正落地、不消费额度，只返回：
  - alias 成本
  - graph 成本
  - 当前是否可保存
  - 若不可保存，预计还需等待 ticks
  - 服务端提示文案
- 新增本地 bridge `/api/graph/preview`、client RPC 和 S2C 回包。
- 前端在“应用到草稿”成功后触发防抖 preview，把结果展示到保存区域，做到“先提示风险，再决定是否 Save”。

### 影响范围

- 命令限流配置与分组
- graph 保存服务与 JSON 返回结构
- StatePanel graph RPC 载荷与回包
- 本地网页 bridge graph API
- GraphViewer 草稿应用后的预检反馈

## 原子步骤清单

### 步骤 1：新增 graph 专用限流分组与配置
- **操作对象**：`CommandRateLimitService`、`RedstoneLinkRateLimitConfig`、`RedstoneLinkConfigParser`、`RedstoneLinkConfigTemplate`
- **具体动作**：新增 `GRAPH_WRITE` 分组和对应 actor-group 容量配置，并提供查询当前窗口是否可消费/需等待多久的只读能力
- **预期结果**：graph 保存与普通 `LINK_RW` 解耦，preview 可读取真实窗口状态
- **关键里程碑**：是

### 步骤 2：提取 graph 保存专用成本模型与 preview 结果
- **操作对象**：`GraphWriteService`、`GraphWriteJsonSupport`
- **具体动作**：复用现有 prepare 逻辑，生成 graph 专用写入单元、graph 成本和 preview JSON；真实 save 改走 `GRAPH_WRITE`
- **预期结果**：preview 与真实 save 使用同一套成本口径
- **关键里程碑**：是

### 步骤 3：新增 graph preview bridge / RPC / 网络通道
- **操作对象**：`LocalWebAppBridgeService`、`LocalWebGraphSaveRpc`、`StatePanelNetwork*`
- **具体动作**：增加 `/api/graph/preview` 与对应 C2S/S2C 载荷、编解码、服务端处理
- **预期结果**：网页可从服务端获取真实预检结果
- **关键里程碑**：是

### 步骤 4：前端接入草稿预检与保存反馈
- **操作对象**：`graphTypes.ts`、`graphViewer/draft.ts`、`GraphViewer.tsx`
- **具体动作**：新增 preview 响应类型与调用函数，在草稿应用后触发预检并展示提示
- **预期结果**：用户在应用草稿后立刻看到预计保存成本与限流风险
- **关键里程碑**：是

### 步骤 5：补测试与回归
- **操作对象**：后端测试、前端 typecheck、Gradle 构建与全量测试
- **具体动作**：补充 graph preview / graph 专用计费回归，执行 `npm.cmd run typecheck`、`.\gradlew.bat buildWebapp --no-daemon`、`.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
- **预期结果**：预检口径与真实保存口径一致，回归通过
- **关键里程碑**：是

## 预期结果

- graph 保存不再复用普通游戏内改边的旧计费口径；
- “应用到草稿”后即可获得服务端真实预检反馈；
- 真实保存语义仍保持 `triggerSource -> core`；
- 保存失败风险前移，一级撤回不再承担唯一补救职责。
