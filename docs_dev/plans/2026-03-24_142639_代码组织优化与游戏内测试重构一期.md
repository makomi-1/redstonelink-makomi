# 代码组织优化与游戏内测试重构一期

生成时间：2026-03-24 14:26:39
文件名：2026-03-24_142639_代码组织优化与游戏内测试重构一期.md

## 任务背景

当前仓库已经进入“功能逐步完善、结构复杂度快速上升”的阶段，多个核心文件超过 1000 行，命令、配置、抽象基类与 bench 脚本的职责边界逐渐变宽。与此同时，旧版游戏内测试场景文档形成较早，和当前 `tools/bench/**` 的自动执行入口映射不够直接，导致后续重构缺少稳定的回归护栏。

本轮目标不是一次性大拆，而是先建立可持续推进的分批方案，并从“游戏内测试脚本与场景基线”这一最小高收益切口开始落地，为后续 Java 侧大文件拆分提供可回归、可观测、可追踪的护栏。

## 方案详情

### 现状分析

当前主要热点与组织风险如下：

- 命令入口集中在 `ModCommands.java`，命令树注册、参数解析、权限校验、执行逻辑、格式化工具共处一处，后续继续扩展时维护成本高。
- 配置入口集中在 `RedstoneLinkConfig.java`，默认值、解析、校验、分类结构、权限相关配置耦合度偏高。
- 抽象基类 `ActivatableTargetBlockEntity.java` 同时承担运行态聚合、派发行为、同步、可观测、恢复相关逻辑，职责过重。
- `tools/bench/run-bench.ps1` 与 `tools/bench/run-bench-suite.ps1` 已承担功能 case、性能 case、suite 编排、结果汇总等多项职责，但场景分层与脚本结构尚未完全对齐。
- 新版 [游戏内测试场景文档](D:/OpenProjects/RedstoneLink/rl-release-no-mixin/docs_dev/references/游戏内测试场景.md) 已建立 `F/X/P/R` 四层结构，但尚未完全落到矩阵和 case 实现。

### 技术方案

整体采用“先护栏、再拆分、分批回归”的路径，按以下顺序推进：

#### 批次 1：bench 与游戏内测试基线

- 先将 `docs_dev/references/游戏内测试场景.md` 中的首批必跑集映射到 `tools/bench/**` 的实际入口。
- 梳理 `run-bench.ps1`、`run-bench-suite.ps1`、`matrix.json`、`functional-matrix.json` 之间的职责边界，优先做目录、命名、入口参数和结果摘要层面的组织优化。
- 首批补齐以下基线场景：
  - `F02` 建链生命周期
  - `F03` 三类语义基础
  - `F04` 输入器、激活命令与追踪联动
  - `X01` 跨区块派发与加载边界
  - `X04` 存档重载一致性
  - `P01` 单源广播压测
  - `P03` 混合并发压测
  - `R02` 重启回归

#### 批次 2：命令系统结构优化

- 将 `ModCommands.java` 按职责拆为“根注册入口 + 子命令注册器 + 执行服务/工具类”。
- 优先把以下部分从大文件中剥离：
  - `node` 查询/trace/retire
  - `link` 读写与写入控制
  - `place`、`audit`、`input`
  - 共享参数解析与格式化工具
- 保持现有命令语义、权限与文案稳定，不在本批次引入新命令设计。

#### 批次 3：配置结构优化

- 将 `RedstoneLinkConfig.java` 拆为“配置键定义 / 默认值 / 解析校验 / 分类 accessor”几个稳定层次。
- 优先抽离命令权限、crosschunk、输入器、显示与调试相关配置分组。
- 保持现有配置键兼容，不改持久化键名，不引入 `com.makomi.api.v1.*` 依赖。

#### 批次 4：抽象基类与运行态职责收敛

- 对 `ActivatableTargetBlockEntity.java` 做职责切片，抽离：
  - 信号聚合与状态机
  - 客户端同步/观测输出
  - 恢复与重建辅助逻辑
- 拆分时优先保证行为不变与测试可控，避免一次性大面积改动调用链。

#### 批次 5：方法级注释补全与二级清理

- 对完成拆分后的核心类补足类注释、方法悬停注释与复杂逻辑中文注释。
- 第二轮清理剩余高行数文件、重复工具函数与命名噪声。

### 技术取舍

- 先做 bench 护栏，而不是立刻拆 Java 大文件：
  - 优势：后续大改有自动回归支撑，风险最低。
  - 代价：短期内不会立刻降低 Java 文件体积。
- 先做“结构重排 + 职责切分”，不做“语义重设计”：
  - 优势：范围可控，回归面更清晰。
  - 代价：部分历史命名和兼容壳会暂时保留。
- 测试场景采用分层首批必跑集，而不是一次性全量铺开：
  - 优势：能先建立稳定最小闭环。
  - 代价：次级场景仍需后续补齐。

### 语义对齐说明

- 命名是否仅使用 `triggerSource/core`：
  - 是。新增文档、方案与后续新增 case 命名统一使用 `triggerSource/core`。
- 输入/输出结构是否保持方向一致：
  - 是。所有新增测试场景与后续重构约束均按 `triggerSource -> core` 固定方向设计。
- 文案与注释是否无旧术语泄漏：
  - 是。新增正文统一使用新术语；仅在分析历史现状时保留对旧实现名的引用。
- 与 `LinkNodeType` 映射是否一一对应：
  - 是。`triggerSource=LinkNodeType.TRIGGER_SOURCE`，`core=LinkNodeType.CORE`。
- 兼容层是否仅“读旧写新”：
  - 本轮不新增持久化兼容层改造，保持现状，不扩展旧术语写入面。

残余风险：

- `NodeRuntimeProbe` 驱动的近外显 I/O 轮询在“单玩家单节点观察”场景下足够轻量，但未来若扩展为多节点并发显示或多玩家集中观察，现有轮询不应按同样模式线性放大，届时更适合切到订阅式推送或复用 BE 同步链路。该项已作为保留问题记录。

## 预期结果
