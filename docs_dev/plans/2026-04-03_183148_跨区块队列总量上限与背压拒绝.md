# 跨区块队列总量上限与背压拒绝

生成时间：2026-04-03 18:31:48
文件名：2026-04-03_183148_跨区块队列总量上限与背压拒绝.md

## 任务背景
`docs_dev/更新计划草稿与索引.md` 第 305-307 行指出：当前跨区块持久派发队列虽然具备 `crosschunk.dispatch.maxPerTick` 的消费预算，但没有队列总量硬上限，也没有在超限时对新入队请求做背压拒绝。  
这会导致问题焦点落在“队列能处理多少”之外，还存在“队列能积压多少”无边界的问题。用户要求直接解决该缺口，并在完成后执行完整游戏内回归测试。

## 方案详情

### 现状分析
- `RedstoneLinkConfigTemplate` 当前只暴露 `crosschunk.dispatch.maxPerTick`，没有总量上限配置。
- `CrossChunkDispatchRuntimeSupport.processPendingDispatches(...)` 仅按 `dispatchMaxPerTick` 控制每 tick 处理预算，不负责限制 `pendingByKey` 的总体规模。
- 真正的持久队列写入入口落在 `CrossChunkDispatchQueueSavedData` / `CrossChunkDispatchQueueStateSupport`，现有 `upsertPending` / `upsertPendingBatch` 对新 key 没有容量闸门。
- 服务层 `QueueResult` 目前只有 `accepted/forceLoadPlanned` 语义；本轮以最小改动为原则，只补硬保护，不扩展拒绝原因协议。

### 技术方案
1. 在跨区块配置中新增 `crosschunk.queue.maxPendingEntries`，专门表达持久队列总量硬上限。
2. 在队列数据层实现容量判定：
   - 若请求命中已存在 key，则允许覆盖更新，不受总量上限影响。
   - 若请求是新增 key，则只有当前剩余容量足够时才允许写入，否则直接返回 rejected。
3. 批量 upsert 按“本批最后有效请求”去重后，先计算新增 key 需要占用的槽位，再按剩余容量进行预留，确保批量路径不会绕过上限。
4. 服务入口继续复用现有 accepted/rejected 分支，不修改调用方对 `QueueResult` 的消费方式。
5. 补齐配置解析测试、数据层容量边界测试，并同步更新使用说明与计划索引。
