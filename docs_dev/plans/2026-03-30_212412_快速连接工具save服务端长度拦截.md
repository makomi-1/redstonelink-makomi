# 快速连接工具 save 服务端长度拦截

生成时间：2026-03-30 21:24:12  
文件名：2026-03-30_212412_快速连接工具save服务端长度拦截.md

## 任务背景
当前 quick-link 缓存保存链路在服务端接包后会直接写入物品缓存。  
虽然 apply 阶段已有 `server.command.linkSet.maxInputLength` 校验，但 save 阶段仍可写入超长输入，存在“先写入、后失败”的一致性与防护缺口。+
## 方案详情

### 现状分析
- 服务端入口：`QuickLinkNetworkServerHandlerSupport.handleSaveQuickLink(...)`
- 当前行为：校验主手物品类型后，直接将 `SaveQuickLinkPayload` 写入 `QuickLinkToolData`
- 现有长度防护：仅在 `QuickLinkApplyService.apply(...)` 阶段对 `serialCacheExpression` 校验

### 技术方案
- 在 `handleSaveQuickLink(...)` 增加服务端长度校验，读取 `RedstoneLinkConfig.command().linkSetMaxInputLength()`
- 当 `serialCacheExpression` 或 `channelCache` 任一超限时：
  - 不写入物品缓存
  - 通过现有 quick-link 反馈通道返回 `message.redstonelink.link.set.input_too_long`
- 校验通过后保持原有写入与 `broadcastChanges` 行为不变

### 影响范围
- `src/main/java/com/makomi/network/QuickLinkNetworkServerHandlerSupport.java`
- 行为影响：quick-link save 阶段新增服务端拦截；apply、collect、网络协议结构不变

## 原子步骤清单

### 步骤 1：补充服务端长度校验
- **操作对象**：`QuickLinkNetworkServerHandlerSupport.handleSaveQuickLink`
- **具体动作**：读取 `maxInputLength`，对 `payload.serialCacheExpression()` 与 `payload.channelCache()` 做长度判定
- **预期结果**：超长输入在 save 阶段被拦截，无法写入缓存
- **关键里程碑**：是

### 步骤 2：复用 quick-link 反馈回执
- **操作对象**：`QuickLinkNetworkServerHandlerSupport.sendFeedback`
- **具体动作**：超限时回传失败反馈 `message.redstonelink.link.set.input_too_long`
- **预期结果**：客户端 HUD 获取明确失败提示，行为与 apply 侧一致
- **关键里程碑**：是

### 步骤 3：编译与回归验证
- **操作对象**：Gradle 测试任务
- **具体动作**：执行 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
- **预期结果**：验证改动未破坏既有行为；若失败则汇报失败点与影响范围
- **关键里程碑**：是

## 预期结果
- quick-link save 与 apply 两阶段都具备服务端输入长度防护
- 客户端绕过本地输入限制时，服务端依旧可阻断超长缓存写入
- 保持现有协议与主流程，属于最小粒度修复
