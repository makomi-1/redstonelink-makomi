# 固定延迟批窗口语义收紧

生成时间：2026-04-02 08:58:15
文件名：2026-04-02_085815_固定延迟批窗口语义收紧.md

## 任务背景

当前 `crosschunk.dispatch.batchWindowTicks` 在 `window>=1` 时采用“目标级单窗口”模型：同一 `core` 第一次进入 pending 时记录一次窗口起点，后续同目标条目继续向同一窗口 merge，但不会刷新窗口起点。  
这会导致：

1. 首条进入窗口的条目通常延迟 `N tick`。
2. 同窗口后续条目的实际延迟会落在 `0..N tick`。
3. `window=0` 已通过 late-arrival 补 flush 收紧为 same-tick 语义，而 `window>=1` 仍不是严格固定延迟。

用户当前目标是：

1. 保留 `window=0` 的现有 same-tick 语义与补 flush。
2. 将 `window>=1` 收紧为“每条已进入 scheduler 的 batchable dispatch 都严格固定延迟 `N tick`”。
3. 不引入 flush budget，也不把 flush 时机迁到首 tick 或中间 tick。

## 方案详情

### 现状分析

1. `CoreDispatchBatchScheduler` 当前以 `target -> accumulator` 组织状态；单个 accumulator 内只有一份 `entriesBySourceAndKind` 与一个 `windowStartTick`。
2. flush 判定基于 `currentTick - windowStartTick >= batchWindowTicks`，因此窗口内后续条目共享首条的到期时刻。
3. `window=0` 额外依赖 `LAST_COMPLETED_END_TICK_BY_SERVER` 做 same-tick late-arrival 补 flush；该补偿只适用于“尽量当前 tick 对齐”的语义。

### 技术方案

采用“目标级 `dueTick` 小桶”模型替换 `window>=1` 的单窗口模型：

1. 保留 `target -> accumulator` 的目标级状态组织，不引入全局时间轮。
2. accumulator 内部从“单窗口”改为“`dueTick -> bucket`”：
   - 每个 bucket 维护一份 `entriesBySourceAndKind`。
   - 同 bucket 内继续沿用现有 merge / 覆盖规则。
3. `window=0` 保持现有路径：
   - 继续写入“即时桶”。
   - 继续允许 `END_SERVER_TICK` 之后的 same-tick late-arrival 补 flush。
4. `window>=1` 改为严格固定延迟：
   - 入队时计算 `dueTick = enqueueTick + windowTicks`。
   - 只写入该 `dueTick` 对应 bucket。
   - `END_SERVER_TICK` 仅 flush `dueTick <= currentTick` 的 bucket。
   - 不再对 `window>=1` 做 after-END 补 flush。
5. 为降低实现复杂度，bucket 只在目标内部维护；由于实际使用窗口主要集中在 `0/1/2`，活跃 bucket 数量可控。

### 影响范围

1. `src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java`
2. `src/test/java/com/makomi/data/CoreDispatchBatchSchedulerTest.java`
3. 如需补充边界验证，可能触及现有 x21 或相关 bench 专项，但本轮优先保证单元测试先收口。

### 技术取舍

1. 不改 flush 时机：
   - 保持 `END_SERVER_TICK` 统一 flush，保留“同时性更好、碎片更少”的既有优点。
   - 不迁移到首 tick 或中间 tick，避免把调度语义绑到 vanilla 更细粒度阶段。
2. 不做 flush budget：
   - 用户已确认本轮不考虑分批出桶。
   - 本轮目标是收紧固定延迟语义，而不是进一步削峰。
3. 不做全局大缓冲：
   - 用户已明确窗口主要只用 `0/1/2`，目标级小桶足够。

### 预期与风险

预期效果：

1. `window=1` 时，每条入队条目的额外延迟固定为 `1 tick`。
2. `window=2` 时，每条入队条目的额外延迟固定为 `2 tick`。
3. `window=0` 继续保持当前 same-tick 语义。

潜在风险：

1. `window>=1` 不再“借窗”，同一目标跨 tick 的 merge 粒度会更细，性能可能略差于现有模型。
2. 调度器内部状态从单桶变多桶，测试与对象池复用逻辑需要同步更新。
3. 若后续再引入 flush budget，需要重新定义 overdue bucket 的处理顺序。

## 原子步骤清单

### 步骤 1：重构目标级 accumulator 为 dueTick 小桶
- **操作对象**：`CoreDispatchBatchScheduler`
- **具体动作**：将单一 `entriesBySourceAndKind/windowStartTick` 改为目标级 `dueTick -> bucket` 结构，并补齐桶回收逻辑。
- **预期结果**：`window>=1` 可按 `dueTick` 隔离等待，不再共享首条窗口起点。
- **关键里程碑**：是

### 步骤 2：拆分 `window=0` 与 `window>=1` 的 flush 语义
- **操作对象**：`CoreDispatchBatchScheduler`
- **具体动作**：保留 `window=0` late-arrival 补 flush；`window>=1` 仅在 `END_SERVER_TICK` flush 到期桶，且不做 after-END 补 flush。
- **预期结果**：`window=0` 与固定延迟窗口语义边界清晰。
- **关键里程碑**：是

## 预期结果

本轮完成后，`crosschunk.dispatch.batchWindowTicks` 的运行时语义将收敛为：

1. `0`：尽量 same-tick，对 `END_SERVER_TICK` 后 late-arrival 保持补 flush。
2. `1/2`：严格固定延迟 `1/2 tick`，不再存在“首条开窗、后续借窗”的 `0..N` 波动。
3. 调度器内部仍保持目标级聚合与统一 `END_SERVER_TICK` flush，不额外引入全局时间轮、flush budget 或公开配置项。
