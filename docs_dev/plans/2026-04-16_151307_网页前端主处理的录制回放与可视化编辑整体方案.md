# 网页前端主处理的录制回放与可视化编辑整体方案

生成时间：2026-04-16 15:13:07

## 任务背景

当前 README 中仍保留两项后续能力：`状态面板支持录制回放` 与 `可视化网络分析器`。  
经过本轮方案收敛，目标进一步明确为：

- 录制入口保留在游戏内 GUI，由游戏内负责录制对象选择、录制参数配置、开始与结束控制。
- 录制完成后，再切换到离线网页端做主展示、时间轴浏览、筛选与导出，不要求录制过程实时推送网页。
- 可视化网络编辑器先只做 `serial` 模式；后续再扩展到 `channel` 模式。
- `channel` 模式前端可复用 `serial` 模式的画布与交互壳，但在视图层引入虚拟频道中转节点，支持两级展开/收起。
- 网页端编辑采用“本地草稿 + 用户主动保存”的模式，不做自动同步；前端必须提示“已编辑未保存”。
- 前端必须支持离线运行，并随 Mod 一起打包，不依赖外部站点或 CDN。

### 技术方案

#### 1. 总体架构分层

整体采用“服务端真值 / 运行态服务 -> 导出 DTO -> 客户端本地桥接 -> Jar 内网页前端”的四层结构：

```text
服务端真值 / 运行态服务
  -> 生成录制 / 图快照 DTO
  -> Fabric 分块回传客户端
  -> 客户端本地 Bridge 缓存与文件落盘
  -> 本地 HTTP 提供 Jar 内静态网页资源与数据接口
  -> 网页端做主展示、主编辑、主分析

网页端保存
  -> 本地 HTTP RPC
  -> 客户端桥转发 C2S
  -> 服务端写控 / OCC / 语义校验
  -> 返回保存结果与刷新基线
```

约束如下：

- 内部真实方向始终保持 `triggerSource -> core`。
- 网页端任何改动都只是“草稿意图”，只有点击 `Save` 后才进入服务端真值。
- 网页端本地布局、筛选器、折叠状态、未保存草稿都属于客户端本地资产，不进入世界真值。

- 客户端将结果写入本地文件，例如 `gameDir/redstonelink/web/recordings/*.json.gz`。
- 网页端只读取本地录制资产，不直接读取服务端采样器。

- 状态面板物品 NBT 只继续承担订阅列表与轻量入口作用，不承载录制结果、图快照、布局或编辑草稿。

##### 2.3 `channel` 模式视图化兼容

`channel` 模式后续复用同一网页壳，但在前端读模型中引入虚拟频道中转节点：

- 虚拟节点例：`channel:12`
- 视图边：
  - `triggerSource -> channel:12`
  - `channel:12 -> core`

该中转节点只存在于网页视图中：

- 不写入 `LinkSavedData`
- 不成为新的真实节点类型
- 仅用于频道级聚合、两级展开/收起、简化大图展示

#### 3. 前后端数据流设计

##### 3.1 录制数据流

```text
状态面板 / 录制 GUI
  -> C2S 提交 RecordingSessionConfig
  -> 服务端启动 RecordingSession
  -> 游戏内 GUI 显示录制中状态
  -> 用户主动结束录制
  -> 服务端停止会话并导出 RecordingBundle
  -> 分块 S2C 回传客户端
  -> 客户端本地写 recordings/*.json.gz
  -> 游戏内入口打开本地网页 recording 视图
```

设计取舍：

- 第一版不做录制过程实时网页推送，只在结束后导出。
- 录制 GUI 负责“配置 + 开始 + 停止 + 打开网页入口”，网页端负责“主处理”。
- 这样可以显著降低桥接复杂度，也减少录制时的网络和前端刷新负担。

##### 3.2 拓扑展示数据流

```text
游戏内入口
  -> C2S 请求导出 GraphSnapshotBundle
  -> 服务端按当前玩家读权限生成 serial 图快照
  -> 分块 S2C 回传客户端
  -> 客户端写本地 graphs/*.json.gz 或内存缓存
  -> 网页端读取 snapshotId 做主展示
```

约束：

- 导出快照必须经过隐私读控裁剪。
- 快照包含 revision 基线，供后续保存时做 OCC。
- 图快照默认按需生成，不新增额外世界持久化。

##### 3.3 网页编辑保存数据流

```text
网页端本地编辑
  -> 修改 GraphDraft（仅本地 dirty）
  -> 用户点击 Save
  -> 本地 HTTP RPC 提交 GraphWriteIntent
  -> 客户端转发 C2S
  -> 服务端做语义校验 / 写控 / OCC / 权限判定
  -> 返回成功或冲突结果
  -> 成功后回传新基线或要求刷新图快照
```

关键规则：

- 网页端不自动同步。
- 所有改动默认停留在本地草稿，直到用户主动保存。
- 网页端必须有明显的 `Unsaved` 提示；关闭页面、切换快照、刷新页面时需要提醒用户尚未保存。
- 服务端拒绝使用“整张图覆盖式写回”，只接受结构化编辑意图。

#### 4. 可视化拓扑展示与编辑设计

##### 4.1 交互基线

第一版目标是“简单好用”，不做自由拉线。

推荐交互：

- 滚轮缩放
- 按住空白区拖动画布
- 框选多个节点
- 单节点点击查看详情侧栏
- 双击节点聚焦
- 搜索节点别名 / 序号 / 类型
- 一键自动布局
- 手动拖拽节点仅改变本地布局坐标，不改变服务端真值

前端图渲染应优先复用成熟图形方案，避免自研渲染器；依赖必须随网页静态资源一起打包，不依赖在线加载。

##### 4.2 编辑方式

第一版采用“结构化批量编辑”，而不是自由拉线：

- 别名编辑
  - 在节点详情侧栏中修改
  - 修改后只更新本地 draft，等待 `Save`
- 拓扑编辑
  - 以 `triggerSource` 为主入口
  - 支持选中一组 `triggerSource`
  - 支持选中一组 `core`
  - 操作类型：`replace / add / remove`
  - 提交前显示预览：影响多少来源、多少目标、多少边

这样可直接覆盖 `n -> m` 编辑模式：

- `n` 个 `triggerSource`
- 对 `m` 个 `core`
- 做结构化批量替换、增量添加或增量删除

优势：

- 与现有 `triggerSource -> core` 真值方向一致
- 更容易对接 `LinkSetExecutionService`
- 更容易做写控、权限校验与 OCC
- 风险明显低于自由拖线

##### 4.3 未保存提示

网页前端需要明确的草稿状态机：

- `clean`
  - 当前草稿与服务端基线一致
- `dirty`
  - 本地已有改动未保存
- `saving`
  - 正在提交保存
- `conflict`
  - 服务端返回 revision 冲突或权限拒绝

提醒策略：

- 顶部状态条显示 `已编辑未保存`
- 切换快照前提醒
- 关闭页面或刷新前提醒
- 保存成功后清除 `dirty`
- 保存冲突后保留本地 draft，并提示用户刷新基线或手动处理

#### 5. 打包与离线运行策略

网页资源与桥接采用“离线随 Mod 打包”方案：

- 网页静态资源放入 `src/main/resources/assets/redstonelink/webapp/**`
- 由客户端本地 Bridge 提供 `127.0.0.1` 本地 HTTP 入口
- 网页资源、依赖脚本、样式、图形库全部从 Jar/classpath 提供
- 不使用外部站点、在线字体、在线脚本、CDN

本地桥接负责：

- 提供网页静态资源
- 提供录制/图快照读取接口
- 提供草稿保存 RPC
- 管理客户端本地缓存目录

#### 6. 网页前端框架选型

前端框架推荐确定为：

- `React`
- `TypeScript`
- `Vite`
- `React Flow`

选型原因：

- `Vite` 更适合产出纯静态资源，便于直接打包进 `src/main/resources/assets/redstonelink/webapp/**`，并由本地 Bridge 以静态网页形式提供。
- `React` 更适合处理“本地草稿 / 显式保存 / 未保存提醒 / 保存中 / 冲突态”这类前端状态机。
- `React Flow` 已经覆盖缩放、拖拽、平移、多选、节点/边渲染等基础交互，可直接支撑 `serial` 模式分析器与结构化编辑器。
- 当前目标不是 SSR 或站点分发，因此不建议引入 `Next.js`、`Nuxt` 之类更重的框架。

额外约束：

- 所有依赖都必须能离线打包，禁止依赖外部 CDN。
- 第一版优先满足图展示、详情侧栏、草稿保存与未保存提醒，不追求复杂动画或重型状态管理框架。
- 若后续需要录制波形图，可在不改变主框架的前提下，再补轻量图表库；不作为当前主框架选型前置条件。

#### 7. 技术取舍

- 录制结果与图快照采用额外 DTO 和本地文件，而不是完全依赖 NBT
  - 优点：体积可控、结构清晰、网页消费简单、便于离线查看
  - 代价：需要新增客户端本地缓存与分块协议
- 编辑采用显式保存，不做自动同步
  - 优点：可控、易理解、便于做未保存提醒和冲突处理
  - 代价：需要本地草稿与保存按钮状态管理
- 第一版不做自由拉线
  - 优点：实现简单、语义稳定、易对接现有写入闭环
  - 代价：图上交互感略弱，但更符合“简单好用”
- `channel` 模式后置，且先做虚拟中转视图
  - 优点：先把 `serial` 模式跑通，避免一次同时改动真实拓扑与频道读模型
  - 代价：频道写入接口需在后续阶段单独设计

#### 8. 推荐实现步骤（分期）

推荐按“先把网页运行底座搭起来，再逐层接能力”的顺序推进：

##### P0：前端工程与离线打包底座

- 在仓库内新增独立网页前端工程，技术栈固定为 `React + TypeScript + Vite`。
- 建立构建产物输出到 `src/main/resources/assets/redstonelink/webapp/**` 的打包流程。
- 客户端补本地 Bridge 最小壳：能打开本地网页首页、能从 Jar 提供静态资源。

预期结果：

- 网页端已能离线随 Mod 运行，但暂时不接真实业务数据。

##### P1：客户端本地缓存与 Bridge 数据通道

- 补本地 HTTP 数据接口与本地文件缓存目录。
- 先打通“客户端内存缓存 / 本地文件 -> 网页读取”的通道。
- 约定录制 bundle、图快照、草稿、布局四类本地资产目录与格式。

预期结果：

- 网页端已能读取本地缓存资产，后续业务只需往 Bridge 填数据。

##### P2：录制 GUI 与录制结果网页查看

- 状态面板 `录制` 按钮切到独立录制 GUI。
- 服务端新增录制会话服务，录制结束后导出 `RecordingBundle`。
- 客户端接收 bundle 并写本地文件，网页端先实现录制结果浏览页。

预期结果：

- 录制链路先闭环，形成“游戏内配置与起停 -> 结束后网页查看”的最小可用能力。

##### P3：serial 模式只读可视化网络分析器

- 服务端导出 `GraphSnapshotBundle`。
- 网页端用 `React Flow` 实现缩放、平移、搜索、自动布局、节点详情侧栏。
- 只读展示阶段先不接入编辑保存。

预期结果：

- 拿到简单好用的 `serial` 模式图分析器。

##### P4：serial 模式显式保存编辑

- 接入本地 `GraphDraft`。
- 实现别名编辑和 `n -> m` 的 `replace / add / remove` 结构化编辑。
- 增加 `Save` 按钮、`dirty / saving / conflict` 状态机、关闭前提醒。

预期结果：

- 不做自由拉线，也能完成高频编辑任务；且不会静默同步。

##### P5：保存预览、冲突处理与用户体验收口

- 保存前展示影响预览：影响多少 `triggerSource`、多少 `core`、多少边。
- 接入 OCC 冲突结果展示与刷新基线路径。
- 统一页面级未保存提示、保存成功反馈、失败重试入口。

预期结果：

- 网页编辑器的“主动保存”交互完整可用。

##### P6：channel 视图模式扩展

- 在网页视图层引入虚拟频道中转节点。
- 支持频道两级展开/收起。
- 尽量复用 `serial` 模式的画布、布局和详情侧栏。

预期结果：

- 频道模式获得可视化视图，但不破坏现有真实语义边界。

##### P7：权限与限流补齐

- 对图导出、录制导出、保存 RPC 分别补节流与权限门闩。
- 继续复用现有写控、隐私读控与 OCC，而不是新增独立网页权限体系。

预期结果：

- 在已有最小可用体验跑通后，再集中补齐安全与限流约束，降低前期实现耦合。

### 影响范围

- 客户端状态面板 / 新录制 GUI
- 本地网页桥接服务
- 网页前端工程与打包流程
- 录制会话与录制结果导出
- 拓扑快照导出
- 网页前端静态资源打包路径
- 别名保存与 serial 批量拓扑保存接口
- 后续 channel 视图层扩展

### 语义对齐说明

- 新增设计、命名、文案统一使用 `triggerSource/core`。
- 内部真实写入方向固定为 `triggerSource -> core`。
- `serial` 模式图边代表真实边；`channel` 模式中的频道节点仅是网页视图中转层，不是新真值。
- 网页端未保存草稿不代表真实配置已变更；只有用户点击 `Save` 且服务端校验通过后，才进入真值层。
- 当前方案不依赖 `com.makomi.api.v1.*`，不新增 API 依赖。
- 兼容层保持“读旧写新”原则；本方案不引入旧术语回流。
- 残余风险：
  1. 大录制结果与大图快照需要稳定的分块协议与客户端本地缓存清理策略。
  2. 显式保存模式下，草稿与服务端 revision 可能漂移，必须有明确冲突提示与刷新路径。
  3. 若后续误把频道虚拟节点上升为真实持久化对象，会破坏现有 `triggerSource/core` 真值边界。

## 预期结果

最终形成一套“游戏内负责入口与控制、网页端负责主分析与主编辑、服务端继续守住真值/权限/OCC 边界”的整体方案：  
录制能力由游戏内 GUI 发起并结束，录制结果在结束后导出为本地离线网页资产；  
可视化网络工具先以 `serial` 模式落地，提供缩放、拖拽、搜索、自动布局、详情侧栏和结构化 `n -> m` 编辑；  
所有网页修改都停留在本地草稿中，只有用户主动保存后才回写服务端，从而在保持 `triggerSource -> core` 语义与现有写控/OCC 体系不变的前提下，提供简单、稳定、可扩展的前后端协作入口。
