# graph保存回包瘦身

生成时间：2026-04-19 11:29:39
文件名：2026-04-19_112939_graph保存回包瘦身.md

## 任务背景

频道模式大批量保存时，前端预检已经很快，但点击保存后会长时间停留在“保存中”，最终报 `Graph save request timed out.`。  
用户已通过重进验证确认：实际保存结果已经落盘，因此当前问题不是“保存未执行”，而是“保存成功后的响应回传链路失败”。

## 方案详情

### 现状分析

- `GraphWriteService.submit(...)` 会把保存影响到的 override 节点、受影响 `triggerSource`、受影响 `core` 全部塞进 `updatedNodes`。
- `StatePanelNetworkPayloadSupport` 对 graph save request/result 都限制为 `16384` 字符。
- `LocalWebGraphSaveRpc` 的本地 RPC 固定等待 15 秒。
- 当前前端 `handleSave()` 实际上先用本地草稿结果 `applyDraftToGraph(...)` 生成下一版 graph，再仅用 `updatedNodes` 回填 alias / channel / revision 等服务端真值字段。

因此，本轮优先怀疑“保存成功回包过大”，而不是继续加超时或引入更复杂的分块协议。

### 技术方案

本轮只做“成功保存回包最小化”：

1. 服务端保存成功响应不再回传大批量 `updatedNodes`。
2. 保存成功响应只保留前端当前必须立即消费的最小字段：
   - `status`
   - `result`
   - `reason`
   - `message`
   - `graphRevision`
   - `updatedNodes=[]`
3. 前端保持现有“先按本地草稿生成下一版 graph”的逻辑。
4. 前端继续兼容 `updatedNodes` 为空，避免依赖服务端在 save success 回包里返回全量受影响节点。

### 技术取舍

- 不选“分块回包”：
  - 需要扩协议、客户端拼装、顺序保证和失败重试，复杂度高。
  - 目前问题集中在 save success 响应过大，先做最小修复更稳。
- 不优先“拉长超时”：
  - 只能掩盖回包膨胀问题，不能解决 `16384` 长度上限。
- 保留前端本地草稿应用：
  - 这是当前最轻的刷新路径，不需要保存成功后再额外拉整图。

### 影响范围

- 服务端：
  - `src/main/java/com/makomi/data/GraphWriteService.java`
  - `src/main/java/com/makomi/data/GraphWriteJsonSupport.java`
- 前端：
  - `webapp/src/components/graphViewer/draft.ts`
  - 如有必要，`webapp/src/graphTypes.ts`

## 原子步骤清单

### 步骤 1：裁剪 save 成功回包
- 操作对象：`GraphWriteService` / `GraphWriteJsonSupport`
- 具体动作：改为 save success 默认返回空 `updatedNodes`，不再构造和序列化大批量节点状态
- 预期结果：大批量频道保存时 response JSON 显著缩小
- 关键里程碑：是

### 步骤 2：前端兼容最小回包
- 操作对象：`webapp/src/components/graphViewer/draft.ts`
- 具体动作：保持 `applyUpdatedNodeStates(...)` 在 `updatedNodes=[]` 时不破坏本地草稿应用结果，并继续吸收新的 `graphRevision`
- 预期结果：save success 即使没有节点增量详情，也能正确更新前端基线 graph
- 关键里程碑：是

### 步骤 3：回归验证
- 操作对象：webapp 与服务端构建链路
- 具体动作：执行 `npm.cmd run typecheck`、`.\gradlew.bat buildWebapp --no-daemon`、`.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
- 预期结果：确认协议裁剪没有破坏现有保存与预检流程
- 关键里程碑：是

## 语义对齐说明

- 命名仅使用 `triggerSource/core`：是
- 输入/输出结构保持方向一致：是，本轮不改真实保存语义
- 文案与注释无旧术语泄漏：计划中是
- 与 `LinkNodeType` 映射是否一一对应：是
- 兼容层是否仅“读旧写新”：本轮不涉及旧术语兼容扩展

残余风险：

- 若 save timeout 的真实瓶颈还包含保存后同步广播，则本轮可能只能解决“回包过大”部分；届时再继续分析 apply/sync 链路。

## 预期结果

频道模式下大批量保存时，前端不再因为 save success 响应过大而在本地桥/RPC 层超时；保存完成后能够立即结束“保存中”状态，并以本地草稿结果作为新基线继续编辑。
