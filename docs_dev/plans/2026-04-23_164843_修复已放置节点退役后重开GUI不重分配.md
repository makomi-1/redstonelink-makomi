# 修复已放置节点退役后重开GUI不重分配

生成时间：2026-04-23 16:48:43
文件名：2026-04-23_164843_修复已放置节点退役后重开GUI不重分配.md

## 任务背景

已放置的 `triggerSource/core` 节点在序号被命令退役后，重新打开配对 GUI 时不会自动重新分配新序号。现状分析表明：

- 物品侧 `LinkItemData.ensureSerial(...)` 已支持“已退役则重分配”。
- 放置侧 `LinkSavedData.resolvePlacementSerial(...)` 已支持“未分配 / 已退役 / 位置冲突”统一解析。
- 但已放置节点的 `openPairingScreen(...)` 入口仍只检查 `serial <= 0`，导致 block entity 内残留的旧 retired serial 会继续被拿去打开 GUI。

因此本轮只修复“已放置节点 reopen GUI 前的 serial 自愈”，不调整网络层、客户端界面或其他配对语义。

## 方案详情

### 现状分析

- `LinkCoreBlock`、`LinkRedstoneDustCoreBlock`、`LinkButtonBlock`、`LinkSignalEmitterBlock`、`LinkSyncLeverBlock` 的 GUI 打开入口都只在 `serial <= 0` 时分配新 serial。
- `PairableNodeBlockEntity.setLinkData(...)` 已经具备“旧节点注销、新节点注册、附着事件发布、客户端同步”的完整副作用，适合承接 reopen 时的 serial 修正。
- `LinkSavedData.resolvePlacementSerial(...)` 已经封装了“未分配 / 已退役 / 分配集合丢失 / 坐标冲突”的统一解析逻辑，可直接复用。

### 技术方案

新增一个服务端共享辅助逻辑，供所有“已放置节点打开配对 GUI”入口复用：

- 输入：`ServerLevel`、节点类型、当前位置、当前 block entity serial。
- 行为：调用 `LinkSavedData.resolvePlacementSerial(...)` 解析 reopen 时应使用的有效 serial。
- 若解析结果与 block entity 当前 serial 不一致，则调用 `setLinkData(...)` 回写并完成运行态注册刷新。
- GUI 打开入口统一依赖该辅助逻辑，而不再分别手写 `serial <= 0` 分支。

这样可以保证 reopen GUI 与“物品 ensure / 放置 resolve”三条路径语义一致。
