# 跨模式混合保存失败修复

生成时间：2026-04-20 11:51:16
文件名：2026-04-20_115116_跨模式混合保存失败修复.md

## 任务背景

网页 graph 编辑器在“另一模式节点池”参与编辑时，会生成混合草稿：同一请求中既包含 `SetNodeChannel`，也包含 `ReplaceTriggerSourceTargets`。当前后端 `GraphWriteService` 仍按“先校验显式 replace，再校验频道切换”的旧口径处理，导致：

- `channel -> serial` 后立刻把这些 core 作为显式目标保存时，被误判为“目标 core 仍处于 channel 模式”，报错“网页编辑当前只支持 serial 模式目标 core”。
- `serial -> channel` 与显式边编辑混在同一请求时，即使不报错，也存在频道派生 replace 覆盖显式 replace 的风险。

本次目标是把网页混合请求统一收敛为稳定、可预检、可保存的后端执行语义。

## 方案详情

### 现状分析

- `GraphWriteService.preparePlan(...)` 当前先验证 `ReplaceTriggerSourceTargets`，再验证 `SetNodeChannel`。
- `LinkSetExecutionService.prepareConfirmedReplaceResolvedTargets(...)` 在 `requireSerialTargets=true` 时会拒绝仍处于 `channel` 模式的 core。
- 频道编辑服务 `LinkChannelEditingService` 会根据频道成员解析出普通 `triggerSource -> core` 派生 replace 计划；如果同一来源同时存在显式 replace，两者目前没有统一优先级。
- 提交阶段当前顺序是“先 apply 显式 replace，再 apply 频道批量计划”，这会让后应用的频道派生 replace 覆盖显式结果。

### 技术方案

本次只在 `GraphWriteService` 做混合请求编排修复，不改变命令层 `LinkSetExecutionService` 的通用校验规则。

核心做法：

1. 先准备频道批量计划，识别本次请求会迁回 `serial` 的 `core` 集合。
2. replace 校验阶段对“同请求迁回 serial 的 core”放宽 `invalid_target_channel_mode` 限制，但其它真实处于 `channel` 模式的 core 仍保持拒绝。
3. 对频道批量计划里的派生 replace 按来源做裁剪：如果同一 `triggerSource` 已有显式 replace，则频道派生 replace 让位给显式 replace。
4. 提交阶段改为“先应用频道配置和剩余派生 replace，再应用显式 replace”，保证最终真值以显式边编辑为准。
5. 预检成本与保存成本统一基于裁剪后的最终计划计算，避免口径漂移。

## 原子步骤清单

### 步骤 1：调整混合请求计划准备顺序
- **操作对象**：`GraphWriteService.preparePlan(...)`
- **具体动作**：先校验并生成频道批量计划，再基于该计划准备 replace 校验所需的“同请求迁回 serial 的 core”上下文。
- **预期结果**：跨模式迁回后，显式 replace 不再按旧真值误判。
- **关键里程碑**：是

### 步骤 2：裁剪频道派生 replace 与显式 replace 冲突
- **操作对象**：`GraphWriteService.validateChannelOperations(...)` 或其后置整理逻辑
- **具体动作**：当某个 `triggerSource` 同时存在显式 replace 与频道派生 replace 时，保留显式 replace，移除频道派生 replace，并重算成本。
- **预期结果**：混合请求下不会出现后写覆盖前写的问题。
- **关键里程碑**：是

### 步骤 3：调整提交顺序
- **操作对象**：`GraphWriteService.submitInternal(...)`
- **具体动作**：先应用频道配置与剩余派生 replace，再应用显式 replace。
- **预期结果**：最终落地结果与草稿语义一致。
- **关键里程碑**：是

### 步骤 4：补充自动化测试
- **操作对象**：`src/test/java/com/makomi/data/`
- **具体动作**：新增“同一请求中迁回 serial 并写显式边”测试，必要时补“显式 replace 覆盖频道派生 replace”测试。
- **预期结果**：问题可稳定复现并自动验证修复。
- **关键里程碑**：是

### 步骤 5：验证与审查留痕
- **操作对象**：`webapp`、Gradle 测试任务、`docs_dev/reviews/`
- **具体动作**：执行前端与后端回归，随后产出五段式审查文档。
- **预期结果**：交付具备验证证据和可追溯审查记录。
- **关键里程碑**：否

## 预期结果

- 混合草稿中 `SetNodeChannel` 与 `ReplaceTriggerSourceTargets` 可在同一请求内稳定协作。
- `channel -> serial -> 显式边编辑` 的保存链路恢复正常。
- `serial -> channel` 与显式边编辑并存时，不会再出现频道派生写入覆盖显式结果。
- 预检、保存、成本统计与最终真值保持同一口径。
