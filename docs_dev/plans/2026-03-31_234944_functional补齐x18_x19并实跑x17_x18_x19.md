## 任务背景

当前 functional bench 已有 `x17`，覆盖 loaded direct `SYNC` 在 `crosschunk.directSyncBatching=all_sync` 下的目标级批打包。

但第 6.1 项仍缺两类 functional 覆盖：
- pending 队列 ready/release 的批打包；
- 强制加载区块预加载后的批打包。

用户要求在当前工作区内直接补齐 `x18/x19`，并实际跑通 `x17/x18/x19` 三条用例。

## 方案详情

### 现状分析

- `x07` 覆盖 reload replay，但 suite 中显式关闭了 `crosschunk.queue.enabled`，不能证明 pending batching。
- `x09` 覆盖 `forceLoad.mode=all` 自动拉起，但同样关闭了 `crosschunk.queue.enabled`，不能证明 preload batching。
- `x17` 已存在并接入 `functional-phase2/regression-full`，但只覆盖 loaded direct `SYNC` batching。
- performance/stress 侧已有 `P20/P24`，只能作为压力侧参考，不能替代 functional 黑盒断言。

### 技术方案

1. 新增 `x18`
   - 目标：验证 `queue.enabled=true`、`forceLoad.enabled=false` 时，多来源 `SYNC` 在目标离线期间进入 pending，目标回归 ready 后能按批打包结果一次性恢复正确状态。
   - 手段：先手工 `forceload remove` 让目标区块离线，再让两个来源同时进入稳定高态，最后手工 `forceload add` 让目标上线，断言目标 `online=true`、`active=true`，并保留两来源连接。

2. 新增 `x19`
   - 目标：验证 `queue.enabled=true`、`forceLoad.enabled=true`、`forceLoad.mode=all` 时，多来源 `SYNC` 在目标离线期间触发 force-load 预加载，目标在自动 ready 后得到正确批结果。
   - 手段：先手工 `forceload remove` 让目标区块离线，再让两个来源同时进入稳定高态，不再手工 reload，由 force-load 自动拉起，最后断言目标 `online=true`、`active=true`，并保留两来源连接。

3. 接入 bench matrix/suites
   - `functional-matrix.json`
   - `functional-phase2.json`
   - `regression-full.json`

4. 同步 `docs_dev/使用说明.md`
   - 把 functional phase2 的覆盖范围补到当前实际集合。

5. 实际执行
   - 逐条执行 `x17/x18/x19`
   - 若 dedicated server / RCON / bench 客户端环境不可用，则如实记录阻断点，不伪称跑通
