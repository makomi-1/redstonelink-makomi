# 迁移到26.1 Fabric

生成时间：2026-04-30 10:44:47
文件名：2026-04-30_104447_迁移到26.1_Fabric.md

## 任务背景
当前工作区已切到 `D:\OpenProjects\RedstoneLink\rl-fabric-26.1`，目标分支为 `migration/fabric-26.1`。现有项目仍停留在 `Minecraft 1.21.11 + Fabric API 0.141.3+1.21.11 + Fabric Loader 0.19.2 + Loom 1.15.5 + Java 21` 的构建基线。

本轮目标不是顺带重构玩法或补做游戏内回归，而是严格以 `1.21.11 -> 26.1` 的官方实现差异为准，先完成机制、接口、方法迁移，再按阶段打通编译链路。用户已明确：本次迁移不需要游戏内测试迁移，每一步仅以“该部分编译通过”为验收标准。

## 方案详情

### 现状分析
- 当前项目已使用 Mojang 官方映射 `loom.officialMojangMappings()`，满足 26.1 未混淆迁移的前置条件。
- 当前 `gradle/wrapper/gradle-wrapper.properties` 已是 `Gradle 9.3.0`，本机 `java -version` 为 `Java 25`，具备 26.1 所需的 Java 25 构建环境。
- 当前 `build.gradle` 仍沿用 1.21.11 时代的 `fabric-loom` 插件、`mappings` 依赖、`modImplementation/modRuntimeOnly` 写法，以及 Java 21 编译目标。
- 当前仓库已命中的 26.1 热点主要集中在：
  - 客户端入口：`src/client/java/com/makomi/RedstoneLinkClient.java`
  - 客户端世界渲染：`src/client/java/com/makomi/client/render/**`
  - 创造标签注册：`src/main/java/com/makomi/registry/ModItemGroups.java`
  - 方块实体注册：`src/main/java/com/makomi/registry/ModBlockEntities.java`
  - 网络注册层：`src/main/java/com/makomi/network/*RegistrationSupport.java`
  - `ItemStack` 使用面：主源码、客户端与测试中共 46 个文件
- 当前项目不迁移游戏内测试链路，`tools/bench/**`、dedicated server、suite、物理世界验证不在本轮完成条件内。

### 官方版本基线
- 目标游戏版本：`26.1`
- 当前 Fabric 文档页版本：`26.1.2`
- 官方构建脚本迁移要求：
  - 26.1 为未混淆版本，需要改用 `net.fabricmc.fabric-loom`
  - 移除 `mappings` 依赖
  - `modImplementation/modCompileOnly/modApi` 切换到 `implementation/compileOnly/api`
  - Java 兼容级别从 `21` 升到 `25`
  - `remapJar` 改为 `jar`
- 通过官方元数据确认的候选版本：
  - Fabric Loader：`0.19.2`
  - Fabric Loom：优先采用 `1.15.5`
  - Fabric API：优先采用与 `26.1` 对齐的 `0.145.0+26.1`
- 若阶段 1 构建解析证明某个组件组合存在阻断，则只在 `26.1` 同族兼容版本内微调，不跨到 `26.1.1/26.1.2` 作为主目标版本。

### 机制/接口/方法变化摘要
#### 构建链
- `fabric-loom` 插件名需要改为 `net.fabricmc.fabric-loom`
- 依赖配置由 `modImplementation` 等 Fabric 专用配置切换为标准 Gradle 配置
- 移除 `mappings loom.officialMojangMappings()` 行
- Java 目标版本改为 `25`

#### Fabric API 重命名
- `ClientCommandManager` -> `ClientCommands`
- `FabricClientCommandSource` 保留类型但其 `getWorld()` 等语义改为 `getLevel()`
- `KeyBindingHelper` -> `KeyMappingHelper`
- `BlockRenderLayerMap` -> `ChunkSectionLayerMap`
- `FabricItemGroup` -> `FabricCreativeModeTab`
- `ItemGroupEvents` -> `CreativeModeTabEvents`
- `PacketByteBufs` -> `FriendlyByteBufs`
- `PayloadTypeRegistry.playC2S/playS2C` -> `serverboundPlay/clientboundPlay`
- `WorldRenderContext`/`WorldRenderEvents` 所在包由 `client.rendering.v1.world` 迁到 `client.rendering.v1.level`
- `ClientTickEvents.START_WORLD_TICK/END_WORLD_TICK` -> `START_LEVEL_TICK/END_LEVEL_TICK`

#### 26.1 新语义
- `HudRenderCallback` 已移除，需改为 `HudElementRegistry`
- Minecraft 会自动推断区块渲染层，旧的 `BlockRenderLayerMap.putBlock(...)` 很可能可直接删除，仅在确有模型覆盖需求时再补充替代实现
- `ItemStack` 在世界加载前不再可安全创建，迁移对象需改用 `ItemStackTemplate` 或延后到已加载上下文再实例化
- 配方序列化转向 `MapCodec + StreamCodec` 形式；若现有自定义配方/序列化仍为旧接口，需要在主源码阶段一并收敛

### 技术方案
1. 先完成构建链迁移，只改 `gradle.properties`、`build.gradle`、`settings.gradle`、`fabric.mod.json` 与运行时依赖版本，让 Gradle 能在 26.1 语义下解析工程。
2. 使用分层编译方式定位真实断点，顺序固定为：
   - 阶段 1：构建与资源元数据
   - 阶段 2：`src/main/java`
   - 阶段 3：`src/client/java`
   - 阶段 4：`src/test/java`
3. 每阶段只修该阶段阻断编译的真实差异，不在迁移过程中顺带改玩法逻辑、视觉设计或游戏内测试流程。
4. 迁移时一律以 26.1 目标实现语义为准：
   - 若旧实现与目标版本机制冲突，优先按目标版本改造
   - 若只是命名/API 重定向，优先做最小替换
   - 若 26.1 改变了对象生命周期（如 `ItemStack`），优先调整创建时机与测试基建，而不是绕过约束
5. 每个阶段达成编译通过后立即提交，形成可回退的迁移里程碑。

### 技术取舍
- 游戏版本保持精确目标 `26.1`，不主动升级到 `26.1.2`，避免把“迁移到 26.1”扩大成“顺带追最新补丁线”。
- Fabric Loader 使用官方当前稳定版本 `0.19.2`，Loom 先采用 26.1 当期稳定线 `1.15.5`；若后续编译器证明需要跟进官方 example mod 当前使用的 `1.16-SNAPSHOT`，再仅对 Loom 单独升级。
- Fabric API 采用 `0.145.0+26.1` 作为首选起点：它仍对齐 `26.1`，同时比更早的 `0.143.x/0.144.x` 更完整；若编译器显示 API 缺口，再在 `+26.1` 族内微调。
- 不迁移游戏内 bench/dedicated/world 测试链路，避免把本轮目标从“代码迁移”扩大成“测试场景迁移”。

### 语义对齐说明
- 命名基线：迁移方案与后续实现说明继续统一使用 `triggerSource/core`
- 方向一致性：若迁移触及来源/目标链路，继续保持 `triggerSource -> core` 单向合法性校验
- `LinkNodeType` 映射：保持 `triggerSource=TRIGGER_SOURCE`、`core=CORE`
- 兼容策略：旧术语仅允许作为输入兼容，迁移期间不新增旧术语输出
