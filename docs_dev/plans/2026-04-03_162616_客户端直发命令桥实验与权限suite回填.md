# 客户端直发命令桥实验与权限suite回填

生成时间：2026-04-03 16:26:16
文件名：2026-04-03_162616_客户端直发命令桥实验与权限suite回填.md

## 任务背景

当前服务器基本权限专项 `C07/C08` 已完成 dedicated server + Prism bench 客户端的真实跑测，但失败结果仍混入“bench 玩家命令链不是真实客户端直发”这一干扰项。  
进一步复核 bench suite 调用链后，还发现 `run-bench-suite.ps1` 启动 bench 客户端后，单 case `run-bench.ps1` 未显式继承客户端桥接上下文，存在继续退回 `RCON + execute as <player>` 的风险。

因此本轮目标不是直接改权限实现，而是先把权限专项的测试执行链校准为“真正由客户端发命令，并把结果可靠回填到 bench”。

## 方案详情

### 现状分析

当前 bench 客户端桥包含两部分：

1. PowerShell 侧通过 request/response 文件桥与客户端实例交互。
2. 客户端默认把 request 转成 `BenchCommandNetwork.ExecutePlayerCommandPayload`，由服务端再用 `player.createCommandSourceStack()` 代执行。

当前存在两个问题：

1. suite 启动的 bench 客户端桥接路径未显式透传到单 case bench。
2. 即便桥接生效，当前命令仍是“服务端代执行”，不是“客户端原生命令发送”，权限口径仍有偏差风险。

### 技术方案

本轮采用“双修正”方案：

1. 为 bench 脚本补齐桥接透传参数：
   - 单 case bench 显式接收 `BenchClientPlayerName`
   - 显式接收 request/response 文件路径
   - 显式接收桥接分发模式
2. 在客户端文件桥中新增按次分发模式：
   - `server_network`：保留原有自定义 payload + 服务端代执行路径
   - `client_direct_command`：客户端直接调用 `minecraft.player.connection.sendCommand(...)`
3. 在客户端注册 `ClientReceiveMessageEvents.GAME`：
   - 只在直发命令请求进行中收集系统消息
   - 以“短静默窗口”作为命令回包结束信号
   - 将收集到的输出按现有 response 文件格式回写

### 影响范围

- `tools/bench/run-bench.ps1`
- `tools/bench/run-bench-suite.ps1`
- `tools/bench/lib/BenchSuite.EntryPoint.ps1`
- `tools/bench/lib/Bench.Client.ps1`
- `tools/bench/lib/Bench.Rcon.ps1`
- `src/client/java/com/makomi/RedstoneLinkClient.java`
- `src/client/java/com/makomi/client/bench/BenchClientCommandBridge.java`
- `docs_dev/使用说明.md`

### 技术取舍

- 不直接删除现有网络桥，保留兼容模式，避免一次性影响其他 bench 场景。
- 不使用 mixin 抓客户端消息，优先采用 Fabric 现成客户端消息事件，降低侵入性。
- 分发模式按 request 指定，而不是全局硬切，便于权限专项和其他 case 分开验证。

### 设计依据与修复层次

- 设计依据：权限命令的真实玩家语义应尽量接近“客户端原生命令发送链”。
- 当前实测与设计差异：现有专项 bench 仍可能退回 `RCON + execute as` 或“服务端代执行”路径。
- 本轮修复层次：测试执行链与观测口径，不直接修改权限/限流生产实现。

### 语义对齐说明

- 命名校验：本轮不引入旧术语，继续使用 `triggerSource/core`。
- 方向校验：不修改来源/目标方向语义。
- 文案与注释校验：新增注释与文档统一使用现有术语基线。
- `LinkNodeType` 映射校验：无变更。
- 兼容层校验：仅新增测试链路调度与客户端回包口径，不改业务存储。
- 残余风险：客户端消息采集可能混入额外系统消息，需要通过静默窗口与最小闭环验证进一步确认。
