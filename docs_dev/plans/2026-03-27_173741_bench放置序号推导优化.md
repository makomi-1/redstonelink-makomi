# bench 放置序号推导优化

生成时间：2026-03-27 17:37:41
文件名：2026-03-27_173741_bench放置序号推导优化.md

## 任务背景

当前 bench 在每次放置 `triggerSource/core` 阵列后，都会逐点通过 RCON 执行 `data get block ... Serial` 回读序号。

该策略虽然稳妥，但在 `1 -> 2048`、`1024 -> 1024` 这类重压 case 上，准备阶段会被数百到数千次同步往返严重放大，已经成为套件执行的主要额外耗时来源之一。

同时，现有 `/redstonelink place` 命令的节点序号分配本身具有明确特征：

- 新放置节点按固定遍历顺序逐个落块并补齐序号
- `triggerSource` 与 `core` 分别使用独立的连续递增计数器

因此，bench 可以优先利用“连续区间 + 固定顺序”直接推导 `坐标 -> serial`，只在不满足条件时退回逐点回读。

## 方案详情

### 现状分析

- `tools/bench/lib/Bench.PlaceAndLink.ps1` 当前的 `Convert-PositionsToSerialMap` 会对每个坐标逐点回读 `Serial`
- `tools/bench/lib/Bench.EntryPoint.ps1` 在 target/source 两侧都依赖这份映射做建链和结果写出
- `src/main/java/com/makomi/command/place/PlaceCommandRegistry.java` 当前只返回“更新了多少块”，没有返回 bench 可直接消费的结构化序号摘要
- 命令放置路径下的节点初始化顺序与 bench 侧 `Expand-CuboidPositions` 的顺序都为 `Y -> Z -> X`

### 技术方案

采用“place 结构化摘要优先，逐点回读兜底”的双层方案：

1. 为 `/redstonelink place setblock/fill` 增加显式 bench 回包分支 `bench`
2. `bench` 分支输出机器可解析的放置摘要，至少包含：
   - 节点类型：`triggerSource/core`
   - 放置顺序：`yzx`
   - 生效数量：`count`
   - 区间起止：`startSerial/endSerial`
3. bench 放置节点时默认走 `... force bench`
4. 若 place 摘要满足：
   - `order=yzx`
   - `count == positions.Count`
   - `endSerial - startSerial + 1 == count`
   则直接按已知坐标顺序推导整组 `position -> serial`
5. 若摘要缺失、不可解析、数量不一致，或 `reuseExisting=true`，则自动回退到现有逐点 RCON 回读
6. 结果 JSON 额外记录本组 serial 来源，便于后续分析是否命中优化路径

### 影响范围

- `src/main/java/com/makomi/command/place/PlaceCommandRegistry.java`
- `tools/bench/lib/Bench.PlaceAndLink.ps1`
- `tools/bench/lib/Bench.EntryPoint.ps1`
