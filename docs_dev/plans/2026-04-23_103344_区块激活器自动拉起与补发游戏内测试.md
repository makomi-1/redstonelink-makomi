# 区块激活器自动拉起与补发游戏内测试

生成时间：2026-04-23 10:33:44
文件名：2026-04-23_103344_区块激活器自动拉起与补发游戏内测试.md

## 任务背景

当前 dedicated functional 用例已经覆盖区块激活器对 `triggerSource/core` 节点集的 `resident/force_load` 在线保持、撤销与节点集切换，但仍缺少一类更贴近本轮实现目标的游戏内验证：

- `triggerSource` 信号先固定到目标态；
- 之后不再改变信号；
- 再通过区块激活器新增生效，验证是否能自动拉起相关区块并把当前真值补发到目标 `core`。

本轮只补测试，不调整业务实现。测试语义必须严格围绕“自动拉起 + 补发”，避免让中途新的输入变化干扰结论。

## 方案详情

### 现状分析

- 现有 `x44/x47` 会在目标离线后重新启动输入，验证的是“后续新事件能否触发 force_load 接管”，不能证明“信号不变时区块激活器自身能否完成自动拉起与补发”。
- 现有 `x45/x48` 主要验证 `resident` 对 `triggerSource/core` 的在线保持和撤销，也没有观察目标 `core` 在固定输入下是否恢复当前真值。
- 当前实现已经提供区块激活器即时副作用入口：`resident` 补票、`core` 当前真值补发、`triggerSource` 当前/持久化真值补发，因此缺口在测试层，而不是实现层。

### 技术方案

1. 新增 4 条 dedicated functional case，最小化为单对 `triggerSource -> core`：
   - `triggerSource + force_load`
   - `triggerSource + resident`
   - `core + force_load`
   - `core + resident`
2. 每条 case 统一采用以下节奏：
   - 先建立链路并把 `triggerSource` 固定到高态；
   - 等待真值稳定；
   - 卸载目标区块，必要时卸载来源区块；
   - 从这一刻起不再改动 `triggerSource` 信号；
   - 再放置并激活区块激活器，使目标节点集首次进入当前生效集合；
   - 断言目标 `core` 被自动拉起并恢复高态。
3. `resident` 场景额外补充在线保持断言，证明不是一次性的瞬时强加载。
4. 将 4 条用例接入 `functional-matrix`、`regression-lifecycle`、`regression-full`，与现有区块激活器用例一起进入 dedicated 回归。

- **具体动作**：分别编写 `triggerSource/core × force_load/resident` 四条 dedicated case，统一固定“信号先建立、后续不再变化”的节奏
- **预期结果**：游戏内测试可直接观测区块激活器自动拉起与补发
- **关键里程碑**：是

## 预期结果

- dedicated functional 将新增 4 条专门验证区块激活器“自动拉起 + 补发”的最小用例。
- 测试会严格保持 `triggerSource` 信号在激活器生效后不再变化，避免把新输入误判成补发成功。
- `triggerSource/core` 与 `resident/force_load` 四种组合都将具备 dedicated 回归保护。
