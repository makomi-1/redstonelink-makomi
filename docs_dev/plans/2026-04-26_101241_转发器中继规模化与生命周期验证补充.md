# 转发器中继规模化与生命周期验证补充

生成时间：2026-04-26 10:12:41
文件名：2026-04-26_101241_转发器中继规模化与生命周期验证补充.md

## 任务背景

`docs_dev/更新计划草稿与索引.md` 已提出三组待补验证：

1. 先对齐现有 `sync` 延迟验证规模，再补转发器中继 `1tick/2tick`。
2. 补转发器重启与跨区块验证，并覆盖 `force-load/resident` 与链路两端位置差异。
3. 补 `32` 个转发器串联，在 `1tick/2tick` 下验证累计延迟。

用户已进一步确认两项边界：

1. 同规模转发器中继采用 `1024-1-1024` 拓扑，即 `1024 triggerSource -> 1 repeater -> 1024 core`。
2. 跨区块场景需避开出生点常驻区块干扰，且不以延迟为断言目标，只验证跨区块是否生效；断言口径参考现有区块激活器/常驻加载用例。

本轮仅输出用例设计方案，不修改实现，不新增 `com.makomi.api.v1.*` 依赖。

## 方案详情

### 现状分析

- 现有 `sync` 延迟规模基线在 `x20/x21`，核心是同区块 `1024 triggerSource -> 1024 core` 的大规模延迟观测。
- 现有转发器延迟基线在 `x57/x58`，只覆盖同区块单链路 `sync -> repeater -> core` 的 `1tick/2tick`。
- 现有生命周期与跨区块口径主要由 `x02`、`x45/x48/x49/x50/x52/x54` 一组用例提供，重点是“离线 -> 拉起/保持 -> 再次生效”的状态验证，而不是固定 tick 数延迟。
- `trace` 观测点位于 `END_SERVER_TICK`，因此跨区块或重载场景若直接拿“可见变化发生在第几 tick”作硬断言，容易把区块装载波动误判成实现退化。

### 技术方案

1. 保留 `x57/x58` 作为单链路纯延迟基线，不向其中混入跨区块、重启或大规模变量。
2. 新增“同规模转发器中继”用例族，直接对齐 `1024-1-1024` 拓扑，分别验证 repeater `1tick/2tick`。
3. 新增“跨区块生效”用例族，参考区块激活器/常驻加载口径，覆盖链路输入端跨区块、输出端跨区块，以及 `force-load/resident` 两种保持方式；该组只断言跨区块生效与保持，不断言精确延迟。
4. 新增“重启恢复”用例族，采用 `prepare/verify` 成对结构，覆盖 `force-load/resident` 与链路两端位置差异；该组重点验证链路、配置与功能恢复，其中延迟只在参与区块已经重新上线并稳定后再做复测。
5. 新增 `32` 个转发器串联用例族，分别验证 `1tick/2tick` 下的累计延迟是否线性增长。
6. 各组用例拆分为独立 suite，避免把“规模延迟”“跨区块加载”“重启恢复”“长链累计延迟”混成一个回归入口，降低定位成本。

### 用例设计 / 目的 / 断言

#### A. 同规模转发器中继

**用例 A1：`1024-1-1024` 同区块中继 `1tick`**
- **目的**：验证在现有 `sync` 主规模上插入单个转发器后，输出仍按 `1tick` 延迟生效，且 `1024` 个目标不会出现旁路直连、漏触发或多余附加 tick。
- **设计**：
  - 拓扑固定为 `1024 triggerSource -> 1 repeater -> 1024 core`。
  - 上游 `1024` 个 `triggerSource` 沿用现有大规模 `single burst/square` 触发方式。
  - 所有上游仅连到 repeater `core`，所有下游仅由 repeater `triggerSource` 驱动。
- **断言**：
  - 结构断言：repeater `core` 聚合所有上游 `triggerSource`；repeater `triggerSource` 扇出到全部 `1024 core`；不存在 `triggerSource -> core` 直连旁路。
  - 延迟断言：repeater 输出相对上游触发窗口增加 `1 tick`。
  - 结果断言：`1024` 个目标最终全部生效，且目标相对 repeater 输出不再额外增加一拍。

**用例 A2：`1024-1-1024` 同区块中继 `2tick`**
- **目的**：验证相同规模下，repeater `2tick` 档位不会被聚合规模吞掉或错误退化成 `1tick`。
- **设计**：与 A1 相同，仅把 repeater 档位切换为 `2tick`。
- **断言**：
  - 结构断言与 A1 相同。
  - 延迟断言：repeater 输出相对上游触发窗口增加 `2 tick`。
  - 结果断言：`1024` 个目标全部生效，且目标相对 repeater 输出不额外加 tick。

#### B. 跨区块生效

**用例 B1：输入端跨区块 + `force-load`**
- **目的**：验证 `triggerSource -> repeater core` 这一侧跨区块时，强加载能够把需要的区块拉起并让链路生效。
- **设计**：
  - 使用小拓扑 `triggerSource -> repeater -> core`，但把 `triggerSource` 放在不同区块。
  - 选点避开出生点常驻区块，优先使用远离原点的 distinct chunks。
  - 先确认相关节点离线，再施加 `force-load` 条件，最后触发。
- **断言**：
  - 预置断言：施加保持前，目标区块或节点确实处于离线状态。
  - 生效断言：施加保持后，对应区块被拉起，repeater 链路可以把状态传到最终 `core`。
  - 保持断言：在预期保持窗口内节点持续在线。
  - 非目标断言：不检查精确 tick 延迟，只检查“是否上线、是否生效、是否保持”。

**用例 B2：输入端跨区块 + `resident`**
- **目的**：验证 `resident` 模式下，输入端跨区块链路能在区块卸载后继续保持在线并再次生效。
- **设计**：与 B1 相同，仅把保持方式换成 `resident`。
- **断言**：沿用 B1 的“离线 -> 上线 -> 保持 -> 生效”口径，不检查延迟。

**用例 B3：输出端跨区块 + `force-load`**
- **目的**：验证 `repeater triggerSource -> core` 这一侧跨区块时，下游区块可被正确拉起并接收输出。
- **设计**：
  - `triggerSource + repeater` 保持在一侧，最终 `core` 放在另一侧区块。
  - 仍避开出生点常驻区块，并沿用区块激活器用例的离线/上线验证节奏。
- **断言**：
  - 预置断言：下游 `core` 所在区块先离线。
  - 生效断言：施加 `force-load` 后，下游区块被拉起，最终 `core` 能收到输出。
  - 非目标断言：不对跨区块传播延迟作精确 tick 判断。

**用例 B4：输出端跨区块 + `resident`**
- **目的**：验证 `resident` 模式下，下游区块可被持续保持并正确接收 repeater 输出。
- **设计**：与 B3 相同，仅把保持方式换成 `resident`。
- **断言**：沿用 B3 的“离线 -> 上线 -> 保持 -> 生效”口径，不检查延迟。

#### C. 重启恢复

**用例 C1/C2：输入端保持 + `force-load/resident` 重启恢复**
- **目的**：验证输入端相关区块在重启前后的链路、序号、delay 配置与功能恢复。
- **设计**：
  - 采用 `prepare/verify` 成对结构。
  - `prepare` 阶段布置 `triggerSource -> repeater -> core`，设置非默认 repeater 档位，写入保持方式并记录链路。
  - `verify` 阶段在服务器重启后，等待相关区块重新上线并稳定，再重新触发链路。
- **断言**：
  - 持久化断言：repeater serial、别名、上下游 link 关系与保持配置未丢失。
  - 恢复断言：重启后再次触发时，最终 `core` 仍能正确生效。
  - 延迟复测断言：待参与区块稳定上线后，repeater 输出延迟仍与 `prepare` 阶段配置一致。

**用例 C3/C4：输出端保持 + `force-load/resident` 重启恢复**
- **目的**：验证输出端相关区块在重启前后的链路与恢复语义。
- **设计**：与 C1/C2 相同，但把保持侧切换到下游 `core` 所在区块。
- **断言**：
  - 持久化断言：下游链路、保持配置与 repeater delay 配置未漂移。
  - 恢复断言：重启后重新触发，最终 `core` 仍能恢复输出。
  - 延迟复测断言：仅在区块稳定上线后复测，不把加载抖动视为延迟失败。

#### D. 三十二级串联

**用例 D1：`32` 个转发器串联 `1tick`**
- **目的**：验证长链下不会出现短路、跳级、合并拍或额外附加拍，累计延迟严格线性。
- **设计**：
  - 拓扑固定为 `1 triggerSource -> 32 repeater -> 1 core`。
  - 至少在 `R1 / R16 / R32 / final core` 布置观测点，避免只看首尾而漏掉中途折损。
- **断言**：
  - 结构断言：每一级只连接相邻一级，无跨级旁路。
  - 延迟断言：若以源侧可见变化为锚，则 `R32` 输出累计增加 `32 tick`。
  - 结果断言：final `core` 相对 `R32` 输出不再额外加 tick。

**用例 D2：`32` 个转发器串联 `2tick`**
- **目的**：验证 `2tick` 档位下累计延迟仍按级数线性叠加。
- **设计**：与 D1 相同，仅把全部 repeater 切换为 `2tick`。
- **断言**：
  - 结构断言与 D1 相同。
  - 延迟断言：若以源侧可见变化为锚，则 `R32` 输出累计增加 `64 tick`。
  - 结果断言：final `core` 相对 `R32` 输出不额外加 tick。

### 技术取舍

- 同规模用例采用 `1024-1-1024`，直接响应用户要求，不再拆成 `1024 -> 1024 repeater -> 1024`，避免把“同规模中继”误做成“同规模逐点转发”。
- 跨区块用例只做“生效/保持”口径，不做延迟门禁，避免把区块装载波动、spawn chunks 常驻或重算时机差异误报成实现缺陷。
- 重启用例保留延迟复测，但把它放在“区块稳定上线后”的第二层断言，先保证链路恢复语义，再判断延迟是否回到配置值。
- `32` 级串联只做单源单终点，避免把累计延迟问题与大规模扇出/装载问题混在同一组。

## 语义对齐说明

- 命名统一：方案文档仅使用 `triggerSource/core`，不引入 `source/target/button` 等旧术语。
- 方向一致：所有设计都保持 `triggerSource -> core`，转发器模型统一为“上游进入 repeater `core`，下游从 repeater `triggerSource` 输出”。
- 映射一致：文档语义与 `LinkNodeType.TRIGGER_SOURCE/CORE` 一一对应，不改变内部映射。
- 兼容边界：旧术语仅作为历史背景说明，不作为新增字段、断言名或文案输出。
- 残余风险：
  - 跨区块场景的装载时序天然有波动，因此只能把“生效/保持”作为主断言。
  - 若后续实现阶段发现出生点周边仍存在隐性常驻干扰，需要进一步把测试坐标外移并在用例前置阶段显式确认离线状态。
