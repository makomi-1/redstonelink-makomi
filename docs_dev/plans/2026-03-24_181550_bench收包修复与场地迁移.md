# bench收包修复与场地迁移

生成时间：2026-03-24 18:15:50
文件名：2026-03-24_181550_bench收包修复与场地迁移.md

## 任务背景
首批必跑最新有效重跑结果中，仅剩以下 2 个功能 case 未通过：
- `sync_triggerSource_slash_square_basic`
- `sync_triggerSource_custom_mixed_basic`

进一步分析后发现，本轮残留问题并不适合直接下结论为 mod 业务逻辑错误，而是先收敛到了 bench 基础设施与测试场地设计两类风险：
1. `run-bench.ps1` 的 RCON 收包逻辑会把迟到响应错归到下一条命令，造成空响应、phase 串包与假失败；
2. 模板世界出生点位于 `(0, -60, 0)`，且 `spawnChunkRadius=2`，当前部分功能场地仍压在出生区附近，容易污染加载/强加载相关判断；
3. `custom` 输入 case 虽然表现出“后半段掉到 0”，但在 bench 收包失真尚未修复前，不应贸然修改 Java 运行时实现。

## 方案详情

### 现状分析
- `tools/bench/run-bench.ps1` 的 `Invoke-RconCommand` 目前默认把读到的首个包纳入本次命令处理，再对收集结果按 `requestId` 过滤。
- 当上一个命令的迟到包在当前命令发送后才到达时，当前命令会先消费旧包，随后在短等待窗口内拿不到本命令的真正响应，最终出现：
  - 当前命令 `response=""`
  - 或下一条命令的 `response` 混入前一条命令的输出
- `sync_triggerSource_custom_mixed_basic` 的 `clear_custom_jobs` phase 已直接出现“`NodeTrace` 输出 + `Input clear` 输出”串在一个响应里的现象。
- `tools/bench/functional-matrix.json` 中，`sync_triggerSource_slash_square_basic` 与 `sync_triggerSource_custom_mixed_basic` 的 arena 坐标仍位于世界原点附近，对 Java 1.21.1 默认 spawn chunks 环境不够干净。

### 技术方案
- 改造 `Invoke-RconCommand`：
  - 发送命令后，循环等待当前 `requestId` 的响应包；
  - 对非当前 `requestId` 的迟到包直接忽略，不再作为本次命令的首包；
  - 在收到首个匹配包后，再按短静默窗口聚合后续同 `requestId` 响应，兼容多包输出。
- 为 bench 关键命令补最小回包校验：
  - `link set` 成功回包必须以 `[RedstoneLink]` 开头；
  - `input start` / `input clear` 成功回包必须以 `[RedstoneLink/Input]` 开头；
  - setup 阶段与 phase 阶段都把关键命令响应写入结果，便于下一轮诊断。
- 将当前仍位于出生区内的残留失败 case 迁移到出生区外，但保持各 case 内部相对布局、serial 映射与断言模板不变。

### 影响范围
- `tools/bench/run-bench.ps1`
- `tools/bench/functional-matrix.json`
