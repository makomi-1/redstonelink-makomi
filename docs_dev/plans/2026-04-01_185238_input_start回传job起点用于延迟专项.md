# input start回传job起点用于延迟专项

生成时间：2026-04-01 18:52:38
文件名：2026-04-01_185238_input_start回传job起点用于延迟专项.md

## 任务背景
当前同区块 `sync` 延迟专项里，`trace_sync_latency_collect` 把 `input start` 命令外层 RCON 观测到的 `tickWindow.startTick` 当作绝对起点。实测结果表明，这会稳定引入一个固定的绝对偏移，导致 `expectedStartTick` 不是服务端真正创建输入 job 的 tick。用户要求把延迟专项的真正起点改成服务端 `job.startTick`。

## 方案详情

### 现状分析
- 服务端 `InputPlaybackService.start(...)` 已经在创建 job 时记录了 `startTick`，并通过 `JobInfo` 对外持有。
- 当前 `input start` 成功回包没有显式输出 `startTick`，bench 只能依赖命令外层 `tickWindow` 做锚点。
- `trace_sync_latency_collect` 当前固定读取 `anchorRef.tickWindow.start/end`，因此会把命令包络窗口边界误当作真正起点。

### 技术方案
- 在 `input start` 成功回包中补充 `startTick=<job.startTick>` 字段，直接回传服务端权威起点。
- 在 bench 的 `input_start_*` phase 中解析并保存 `jobStartTick`。
- 在 `trace_sync_latency_collect` 中优先使用 `anchorPhaseResult.jobStartTick` 作为 `expectedStartTick`；若字段不存在，再回退到旧的 `tickWindow.start/end` 逻辑，保证兼容旧响应格式。

### 影响范围
- 服务端输入命令返回文案与 bench 解析逻辑。
- 同区块/跨区块延迟专项的绝对起点口径。
- 不影响输入 job 的调度逻辑，不影响 `triggerSource -> core` 业务语义。

- **预期结果**：RCON 响应可直接拿到服务端真实 job 起点
- **关键里程碑**：是

- **预期结果**：bench phase 结果持有真实 job 起点
- **关键里程碑**：是

- **操作对象**：`Bench.FunctionalTrace.ps1`

- **预期结果**：延迟专项的绝对起点与服务端 job 起点一致

- **关键里程碑**：是
