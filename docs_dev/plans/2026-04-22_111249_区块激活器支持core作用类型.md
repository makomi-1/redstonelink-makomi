# 区块激活器支持core作用类型

生成时间：2026-04-22 11:12:49
文件名：2026-04-22_111249_区块激活器支持core作用类型.md

## 任务背景

当前区块激活器仅能对白名单与 resident/force-load 聚合贡献 `triggerSource`。本轮需要把区块激活器扩展到同时支持 `triggerSource/core` 两种作用类型，但单个激活器任一时刻只能有一种作用类型生效；切换作用类型时需要明确确认，且切换后不能清空另一种类型已保存的配置。

## 方案详情

### 现状分析

- 区块激活器当前配置模型只有一套 `serialExpression + mode`，持久化、物品 NBT、网络 payload、GUI 编辑器均按这套单配置读写。
- `PlacedChunkActivatorSavedData` 当前仅维护 `triggerSource` 反向索引与 `forceLoad/resident` 聚合引用计数。
- `CrossChunkEffectiveWhitelistService` 当前只把区块激活器贡献合并到 `LinkNodeType.TRIGGER_SOURCE + SOURCE` 口径。
- bench 用例已覆盖 `triggerSource` 的 force-load、resident、物理破坏失效，但尚未覆盖 `core` 与作用类型切换保留配置。

### 技术方案

1. 将区块激活器配置模型升级为“双配置存储 + 单类型生效”：
   - 新增“当前作用类型”字段，取值仅允许 `triggerSource/core`。
   - 为 `triggerSource` 与 `core` 各保留一套独立配置快照，不因切换清空另一侧。
   - 运行时只解析并贡献“当前作用类型对应配置”的节点集。
2. 扩展持久化与网络：
   - 方块实体、物品 NBT、已放置激活器真值、S2C/C2S payload 一并升级到双配置结构。
   - 旧存档按“读旧写新”兼容：历史单配置默认迁移为 `triggerSource` 配置，`core` 配置初始化为空。
3. 扩展服务层贡献：
   - `PlacedChunkActivatorSavedData` 改为分别维护 `triggerSource/core` 的索引和 `forceLoad/resident` 聚合引用。
   - `CrossChunkEffectiveWhitelistService` 与 `NodeSnapshotQueryService` 按节点角色分别合并 `triggerSource` 或 `core` 的区块激活器贡献。
4. 扩展 GUI 交互：
   - 编辑器新增“作用类型”切换控件。
   - 用户从当前类型切换到另一类型时，若当前编辑内容会切换视图，则先弹确认，再切到另一套已保存配置。
   - 保存时仅提交当前作用类型与两套配置快照，不清空未生效类型数据。
5. 补充验证：
   - 新增至少一组 `core` 作用类型 dedicated bench 用例。
   - 新增或补充切换作用类型后保留另一侧配置的自动化覆盖。

### 影响范围

- `src/main/java/com/makomi/data/` 区块激活器配置快照、物品数据、已放置真值、白名单聚合、节点身份查询
- `src/main/java/com/makomi/block/entity/` 区块激活器方块实体
- `src/main/java/com/makomi/network/` 区块激活器网络 payload 与服务端处理
- `src/client/java/com/makomi/client/screen/` 区块激活器编辑界面
- `tools/bench/cases/functional/` 区块激活器 dedicated 功能验证

## 语义对齐说明

- 命名是否仅使用 `triggerSource/core`：是，新增类型、字段、文案统一使用 `triggerSource/core`。
- 输入/输出结构是否保持方向一致：是，区块激活器对白名单贡献按 `triggerSource=SOURCE`、`core=TARGET` 映射，不允许反向写入。
- 文案与注释是否无旧术语泄漏：目标如此实施；实现后需再做一次全文校验。
- 与 `LinkNodeType` 映射是否一一对应：是，`triggerSource -> TRIGGER_SOURCE`，`core -> CORE`。
- 兼容层是否仅“读旧写新”：是，旧单配置只在读取时迁移到 `triggerSource` 配置，后续统一按新结构保存。

## 预期结果
