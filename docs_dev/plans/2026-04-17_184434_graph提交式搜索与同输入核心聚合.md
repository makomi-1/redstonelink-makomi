# Graph 提交式搜索与同输入核心聚合

生成时间：2026-04-17 18:44:34
文件名：2026-04-17_184434_graph提交式搜索与同输入核心聚合.md

## 任务背景

上一轮已经把 Graph 视图的临时显示残留、横向布局和类型筛选补齐，但继续实测后仍存在两类性能问题：

- 搜索输入时每个按键都会立即刷新画布，导致重算链路过长、卡顿明显
- 当多个 `triggerSource` 共同指向大量“相同输入集合”的 `core` 时，展开后边数量暴涨，当前按单来源摘要的策略压不住这种稠密连接

本轮目标是在不改 snapshot、draft、服务端真值和真实保存方向的前提下，继续优化前端视图层的搜索刷新时机与大规模边渲染表现。

## 方案详情

### 现状分析

- 当前搜索只有一套实时状态，输入框和类型筛选的每次变化都会驱动 `matchedNodes -> matchedNodeKeys -> forcedVisibleNodeKeys -> graphCanvasView -> buildEdges` 整条链路刷新。
- 当前虚拟节点只有“高扇出摘要节点”，表达的是单个来源节点的目标折叠；还没有“多个来源共同指向同一批核心节点”的聚合表达。
- 当多个 `triggerSource` 对同一批 `core` 的上游集合完全一致时，真实边会形成高密度矩阵，ReactFlow 需要同时渲染大量重复结构的边。

### 技术方案

1. 将搜索状态拆分为“输入态 / 应用态”：
   - 新增草稿搜索文本与草稿类型筛选
   - 保留已应用搜索文本与已应用类型筛选作为真正驱动画布刷新的状态
   - 输入框、类型筛选只改草稿态，不立即刷新画布
   - 回车或点击“应用搜索”按钮时才提交到应用态
   - 清空搜索时同步清空草稿态和应用态
2. 引入“同输入核心聚合块”：
   - 以每个 `core` 的上游 `triggerSource` 集合完全一致作为聚合条件
   - 用排序后的来源 `nodeKey` 列表构建签名键
   - 当同一签名下同时满足“来源数量 >= 2、核心数量 >= 2”时，生成前端虚拟聚合块
   - 聚合块折叠时，每个相关 `triggerSource` 只用一条边连接该块
   - 聚合块展开时恢复真实 `core` 与真实边
3. 聚合顺序与强制显示边界：
   - 先做“同输入集合聚合”，再对剩余高扇出来源应用现有摘要节点逻辑
   - 若聚合内真实 `core` 被搜索命中、选中、草稿差异或编辑选择强制显示，则自动打开展示真实节点
4. 同步调整工具栏和提示文案：
   - 搜索区增加“应用搜索 / 清空搜索”
   - 聚合块增加明确的块级文案和展开提示
   - 保持现有视觉风格与响应式布局

## 预期结果

- 搜索输入不会再按键即刷新，只有提交后才更新画布。
- 同输入集合完全一致的多个 `core` 会被聚成一个前端虚拟块，相关 `triggerSource` 只保留到该块的一条边。
- 高密度边场景的边数量显著下降，画布性能优于仅做样式降载。
- 真实保存语义仍保持 `triggerSource -> core`，本轮只改前端视图层。
