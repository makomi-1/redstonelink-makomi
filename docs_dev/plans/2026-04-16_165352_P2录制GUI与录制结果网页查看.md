# P2 录制 GUI 与录制结果网页查看

生成时间：2026-04-16 16:53:52
文件名：2026-04-16_165352_P2录制GUI与录制结果网页查看.md

## 任务背景

`P0` 已完成网页前端离线打包底座，`P1` 已完成客户端本地资产仓与只读 Bridge 数据通道。

当前进入既有整体方案中的 `P2`，目标不是实现拓扑图分析器，而是先把“状态面板录制入口 -> 独立录制 GUI -> 服务端采样会话 -> 本地 recording bundle 落盘 -> 网页端查看”这条链路闭环。

本轮仍坚持既有收敛结果：

- 录制配置与开始/结束控制由游戏内 GUI 负责
- 录制完成后再导出到网页端，不做实时网页推送
- 状态面板工具物品 NBT 继续只承担订阅列表入口作用，不承载录制结果
- 网页端只做录制结果主查看，不提前引入 `P3` 的拓扑图分析器

## 方案详情

### 现状分析

- 状态面板已经有 `录制` 按钮，但当前仍是占位入口，点击后只走一个空的 `RecordStatePanelPayload`，服务端返回 `future` 文案。
- 当前状态面板只有一个主界面，没有独立录制 GUI。
- `NodeStateTraceService` 已具备按节点挂载采样、固定间隔采样、ring buffer 保留最近样本的能力，适合作为录制底座。
- `NodeRuntimeProbe` 能把 `core` 和在线 `triggerSource` 解析为稳定的运行态快照与探针类型，适合作为录制目标探针解析入口。
- `P1` 已经具备 `gameDir/redstonelink/web/recordings` 本地目录、单文件读取能力和网页端资产预览页，因此 `P2` 不需要重做网页壳和本地资产仓。

### 技术方案

#### 1. 游戏内入口与录制 GUI

- 保留状态面板作为订阅对象管理入口
- 把状态面板中的 `录制` 按钮改为打开独立录制 GUI
- 录制 GUI 负责：
  - 展示当前状态面板订阅数量
  - 配置 `title`
  - 配置 `sampleEveryTicks`
  - 配置 `capacityPerNode`
  - 配置 `autoOpenWeb`
  - 执行开始录制
  - 执行结束录制
  - 执行返回状态面板

录制对象不在 `P2` 新增另一套选择逻辑，直接复用当前状态面板工具中的订阅列表，避免 GUI 和协议同时扩张。

#### 2. 服务端录制会话编排

新增服务端运行时录制会话服务，按玩家维度维护活动录制：

- 一名玩家同一时刻最多一个活动录制
- `start` 时服务端重新读取玩家主手状态面板工具中的订阅
- 逐个订阅通过 `NodeRuntimeProbe.resolveCurrent` 解析可录制探针
- 对可录制节点复用 `NodeStateTraceService.mount`
- `stop` 时读取各节点样本，导出 `RecordingBundle`
- 导出完成后卸载本次会话挂载的 trace

#### 3. 录制结果 DTO 与保存策略

录制结果不写世界真值，不写状态面板物品 NBT，而是导出为本地网页资产：

- 运行中状态只保存在服务端运行时
- 录制结束后导出 `RecordingBundle`
- 客户端接收后写入 `gameDir/redstonelink/web/recordings/*.json.gz`
- 网页端从本地资产仓读取该 bundle

最小 DTO 结构：

- `RecordingBundle`
  - `manifest`
  - `nodes`
  - `series`
  - `markers`
- `manifest`
  - `recordingId`
  - `title`
  - `startedTick`
  - `endedTick`
  - `sampleEveryTicks`
  - `nodeCount`
  - `sampleCount`
  - `formatVersion`
- `nodes`
  - `nodeKey`
  - `type`
  - `serial`
  - `displayText`
  - `traceKind`
  - `allocated`
  - `retired`
  - `online`
- `series`
  - `nodeKey`
  - `samples`
- `samples`
  - `tick`
  - `online`
  - `active`
  - `inputPower`
  - `outputPower`

#### 4. 网络协议与客户端落盘

新增 `P2` 录制协议：

- 录制 GUI 打开包
- 录制会话状态查询包
- 录制开始包
- 录制结束包
- 录制 bundle 分块下发包
- 通用反馈包

传输策略：

- 录制结果按 `gzip + 分块` 方式传输
- 客户端收到完整结果后再一次性落盘
- 成功落盘后按 `kind=recording&name=...` 打开本地网页

#### 5. 网页端查看模式

网页端继续保留 `P1` 的本地资产仓预览基础，但对 `recording` 资产增加专用查看模式：

- 读取 `manifest`
- 展示节点列表
- 选中节点后展示样本表格
- 展示 markers
- 继续保留原始文本预览作为兜底

第一版不接图表库，不做复杂时间轴，只保证可读、可定位、可切换节点。

### 影响范围

- 状态面板客户端界面
- 新增录制 GUI
- 状态面板网络协议
- 服务端录制会话服务与录制 DTO
- 客户端本地 recording 资产写入
- 本地网页打开入口
- `webapp/src/**` 录制结果查看模式

### 语义对齐说明

- 新增命名与文案统一使用 `triggerSource/core`
- 本轮不新增任何 `triggerSource -> core` 真值写入路径
- 状态面板工具 NBT 仍只保存轻量订阅上下文，不保存录制结果
- 录制 bundle 属于客户端本地网页资产，不属于世界真值
- 本轮不引入 `com.makomi.api.v1.*`
- 兼容层保持“读当前订阅，写新的本地 recording bundle”
- 残余风险：
  1. 玩家断线后的活动录制先按运行时会话清理处理，不做恢复
  2. 大录制结果需要稳定的分块重组与本地落盘校验
  3. 第一版网页查看偏结果浏览，不包含复杂图表分析能力

## 预期结果

完成后，项目会得到一个最小可用的 `P2` 录制闭环：

- 状态面板中的录制入口不再是占位按钮，而是独立录制 GUI
- 服务端能基于当前订阅真正启动和停止录制会话
- 录制结果能导出为本地 `recordings/*.json.gz` 资产
- 网页端能直接查看刚录制完成的 recording bundle

这使得“游戏内负责录制控制，网页端负责录制结果主查看”的主架构在 `P2` 就能真实落地。
