# 为attach replay接入过滤器持久化判定

生成时间：2026-04-10 11:16:30
文件名：2026-04-10_111630_为attach_replay接入过滤器持久化判定.md

## 任务背景
当前 `triggerSource/core` 的实时派发已经会经过 send/receive 过滤器判定，但进入存档时的 attach replay 仍然直接发布“节点附着重放”事件，没有在发事件前重新读取 `PlacedLinkFilterSavedData` 的持久化真值。这样一来，只要过滤器注册稍晚于 replay，理论上就可能把本应被持久化过滤器拦截的重放错误地下发出去。

## 方案详情

### 现状分析
- attach replay 的入口位于 `LinkNodeLifecycleDispatchEvents`，当前会直接根据链接关系重放来源或目标上线事件。
- 通用发布器 `InternalDispatchDeltaRuleSupport.publishLinkAttached(...)` 不只被 attach replay 使用，也会被正常建链流程复用；如果把 replay 过滤逻辑塞进通用发布器，会把“启动恢复补判”误扩散到实时路径。
- `PlacedLinkFilterSavedData` 已经持久化了 send/receive 过滤器的真值，这份数据能作为 replay 时的最终判定依据，不需要同步等待过滤器 block entity 注册完成。
- `neighborSignalStrength` 在本轮方案中允许暂时不新鲜；后续由过滤器变化事件与既有补采样方案兜底。

### 技术方案
1. 在 `LinkDispatchFilterService` 增加基于 `PlacedLinkFilterSavedData` 的 replay 判定入口，直接接受 `triggerSource/core` 的维度、坐标、序列号和重放信号强度，避免依赖已加载 block entity。
2. 调整 `LinkNodeLifecycleDispatchEvents` 的 target attach replay：
   - 先沿用既有“哪些同步来源具备 replay 资格”的筛选；
   - 再逐个来源用持久化过滤真值补判；
   - 只有放行的 `triggerSource -> core` 组合才继续发布 replay 事件。
3. 调整 `LinkNodeLifecycleDispatchEvents` 的 source attach replay：
   - 先解析一次来源当前重放强度；
   - 再逐个目标 core 用持久化过滤真值补判；
   - 只对通过补判的目标发布 replay 事件。
4. 补充自动化测试，覆盖“无过滤器放行、send 过滤器拦截、receive 过滤器拦截、双侧均放行”四类边界。

### 影响范围
- `src/main/java/com/makomi/data/LinkDispatchFilterService.java`
- `src/main/java/com/makomi/data/LinkNodeLifecycleDispatchEvents.java`
- `src/test/java/com/makomi/data/LinkDispatchFilterServiceTest.java`
- `docs_dev/reviews/` 下本轮审查文档

### 语义对齐说明
- 命名统一保持 `triggerSource/core`，不新增旧术语输出。
- 判定方向只允许 `triggerSource -> core`，不会引入反向 replay 写入。
- 与 `LinkNodeType.TRIGGER_SOURCE/CORE` 的映射保持不变。
- 兼容层仍是“读旧写新”原则，本轮不新增任何旧术语持久化字段。
- 残余风险：`neighborSignalStrength` 可能不是最新值，但该问题已接受由后续过滤器变化事件兜底，本轮不在 attach replay 中额外同步补采样。

## 原子步骤清单

### 步骤 1：补充 replay 过滤判定入口
- **操作对象**：`LinkDispatchFilterService`
- **具体动作**：抽出基于 `PlacedLinkFilterSavedData` 的 send/receive 持久化真值判定，并封装成 replay 专用入口
- **预期结果**：attach replay 可在不依赖过滤器实例注册的前提下直接做最终放行判断
- **关键里程碑**：是

### 步骤 2：接入 target attach replay
- **操作对象**：`LinkNodeLifecycleDispatchEvents`
- **具体动作**：在 target attach replay 发布前，对每个来源按持久化 send/receive 过滤真值补判
- **预期结果**：core 上线补发时不会把已被过滤器拦截的来源误重放
- **关键里程碑**：是

### 步骤 3：接入 source attach replay
- **操作对象**：`LinkNodeLifecycleDispatchEvents`
- **具体动作**：在 source attach replay 发布前，对每个目标按持久化 send/receive 过滤真值补判
- **预期结果**：triggerSource 上线补发时不会把已被过滤器拦截的目标误重放
- **关键里程碑**：是

### 步骤 4：补测试与审查
- **操作对象**：过滤器相关测试、审查文档
- **具体动作**：新增 replay 判定测试，随后执行自动化测试并编写五段式审查文档
- **预期结果**：本轮修复具备回归覆盖和可追溯审查记录
- **关键里程碑**：是

## 预期结果
attach replay 在发事件前会直接以 `PlacedLinkFilterSavedData` 为准重查 send/receive 过滤器真值，只向真正应放行的 `triggerSource -> core` 组合发布重放事件；方案不阻塞启动、不复制过滤器快照到节点实体，并把“邻居阈值可能暂不新鲜”的问题留给后续过滤器变化事件处理。
