# sync批内重算延后原型验证

生成时间：2026-05-03 14:15:27
文件名：2026-05-03_141527_sync批内重算延后原型验证.md

## 任务背景

当前 `p15_sync_1024_to_1` 在 `triggerSource -> core` 的 `sync` 高 fan-in 压力下，热点集中在目标端批内重复执行 `recomputeSyncTruthFromConcurrentBuckets`、`mergeLatestSyncTruthFromBuckets` 与 `recomputeAuthorityFromConcurrentBuckets`。用户要求先做一个最小原型，只验证“把批内 `sync` 重算延后到批末”能否明显降低 `p15` 开销，并与 `p18_sync_1024_to_1024` 做对比。

## 方案详情

### 现状分析

- 当前 loaded direct `sync` 在 `crosschunk.directBatching=all_direct` 下会进入 `CoreDispatchBatchScheduler`。
- 但目标端 `applyDispatchBatch` 处理 `SYNC_SIGNAL` 时，`applySyncDeltaMutation` 与 `applyTriggerSource*InvalidationMutation` 仍会在批内每条 entry 后立刻重算 `sync truth` 与 `authority`。
- `finalizeStructuredBatchMutation` 在批末又会额外再做一次统一重算，导致单目标高 fan-in 下出现明显的重复全量 merge。
- `toggle/pulse` 路径带有更强的时序语义与基准态依赖，不适合在本轮原型里一起改动。

### 技术方案

- 仅修改 `ActivatableTargetDispatchSupport`。
- 对批内 `SYNC_SIGNAL`、`SOURCE_INVALIDATION`、`TRIGGER_SOURCE_CHUNK_UNLOAD_INVALIDATION`、`TRIGGER_SOURCE_INVALIDATION` 这几条 `sync` 相关 mutation：
  - 保留优先级校验与 bucket 更新；
  - 不再在每条 entry 后立刻调用 `owner.recomputeSyncTruthFromConcurrentBuckets()` 与 `owner.recomputeAuthorityFromConcurrentBuckets(...)`；
  - 改为只在累计器中记录“本批是否触发了 sync 相关结构变更”。
- `finalizeStructuredBatchMutation` 根据累计器状态，在批末统一执行一次 `sync truth`、`pulse truth`、`toggle truth`、`authority` 与 `derived state` 提交。
- `ACTIVATION`（`toggle/pulse`）批路径保持原状，避免本轮原型影响 `toggle` 基准态与 `pulse` 生命周期语义。

## 原子步骤清单

### 步骤 1：收敛 sync 批路径重算时机
- **操作对象**：`ActivatableTargetDispatchSupport`
- **具体动作**：让批内 `sync` 与 `triggerSource` 失效 mutation 只改 bucket 和累计器，不在每条 entry 后立刻重算 truth/authority
- **预期结果**：单批 `sync` 只在批末统一重算一次
- **关键里程碑**：是

### 步骤 2：保持 activation 语义不变
- **操作对象**：`ActivatableTargetDispatchSupport`
- **具体动作**：不改 `ACTIVATION` 批路径的时序处理，仅扩展累计器区分是否发生了 sync 结构变更
- **预期结果**：最小化对 `toggle/pulse` 的行为风险
- **关键里程碑**：是

### 步骤 3：构建并跑 p15/p18 定向性能验证
- **操作对象**：Gradle 与 bench suite

- **预期结果**：获得优化前后的 `MSPT` 与热点对比
- **关键里程碑**：是

## 预期结果

在不改变 `triggerSource/core` 方向语义和 `toggle/pulse` 批内时序语义的前提下，验证“仅将批内 `sync` 重算延后到批末”是否能显著降低 `p15_sync_1024_to_1` 的目标端重复全量 merge 开销，并明确该优化对 `p18_sync_1024_to_1024` 的影响幅度。
