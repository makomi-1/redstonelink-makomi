# 频道批量保存与聚合收起修复

生成时间：2026-04-19 09:56:49
文件名：2026-04-19_095649_频道批量保存与聚合收起修复.md

## 任务背景

当前频道模式存在两个联动问题。其一，批量频道修改保存时即使等待较久仍持续返回“保存过于频繁，请稍后再试”，分析表明服务端会把多条 `SetNodeChannel` 分别展开为真实 `triggerSource -> core` relink 计划并直接累加成本，导致单次请求本身可能永远超过 `LINK_RW` 限流桶容量。其二，频道模式“应用到草稿”后，新增成员所在聚合块无法收起，同时节点出现绿色叠加；分析表明绿色叠加是草稿差异高亮，而聚合块会把草稿差异成员误当作必须展开的成员。

## 方案详情

### 现状分析

- `GraphWriteService` 当前逐条处理 `SetNodeChannel`，并将每条操作准备出的 relink 成本直接累加。
- `LinkChannelEditingService` 当前只提供“单节点 override”推导能力，缺少按整批最终频道状态一次性去重计算 relink 计划的能力。
- 前端 `GraphViewer` 会把 `draftDiff.changedNodeKeys` 直接并入 `forcedVisibleNodeKeys`。
- `canvas.tsx` 中频道聚合块把“成员在 forcedVisible 集合里”视为展开条件，从而把草稿差异预览误提升为展开状态。

### 技术方案

- 在服务端引入“整批频道覆盖写入”准备语义：先汇总同批 `SetNodeChannel` 的最终节点频道配置，再按整批最终状态一次性推导受影响的 `triggerSource` 与去重后的 relink 计划。
- 保存应用阶段改为先写整批频道配置，再执行去重后的真实 relink，限流成本按去重后的最终计划计算。
- 前端拆分“强制可见节点集合”和“聚合自动展开节点集合”两套口径，使草稿差异节点仍可见、仍保留绿色高亮，但不再强制把频道聚合块自动顶为展开。

## 原子步骤清单

### 步骤 1：重构服务端频道批量准备语义
- **操作对象**：`GraphWriteService.java`、`LinkChannelEditingService.java`、`LinkSavedDataChannelSupport.java`
- **具体动作**：把多条 `SetNodeChannel` 汇总为一份最终频道覆盖集，并一次性计算受影响 `triggerSource` 与去重后的 relink 计划
- **预期结果**：频道保存不再按单节点重复展开和重复计费
- **关键里程碑**：是

### 步骤 2：对齐服务端应用与限流成本
- **操作对象**：同上
- **具体动作**：保存时先写整批频道配置，再应用去重后的 relink 计划；限流成本改为使用整批最终计划成本
- **预期结果**：频道模式保存结果与整批最终状态一致
- **关键里程碑**：是

### 步骤 3：修复前端频道聚合收起口径
- **操作对象**：`GraphViewer.tsx`、`canvas.tsx`
- **具体动作**：将草稿差异节点从“自动展开依据”中拆出，仅保留其可见和高亮效果
- **预期结果**：应用到草稿后的新增成员可收起，绿色叠加仅表示草稿差异
- **关键里程碑**：是

### 步骤 4：验证与审查
- **操作对象**：相关测试、构建、审查文档
- **具体动作**：执行类型检查、前端构建、Gradle 全量测试，并补审查文档
- **预期结果**：形成完整验证证据与风险说明
- **关键里程碑**：是

## 预期结果

频道模式批量修改保存会按整批最终状态一次性去重计算真实 relink，避免“等多久都过于频繁”的假限流；同时，频道聚合块在应用到草稿后仍保留绿色草稿差异高亮，但用户可以真实收起新增成员。
