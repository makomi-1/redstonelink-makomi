# 修复sync跨tick覆盖语义

生成时间：2026-04-24 13:29:19
文件名：2026-04-24_132919_修复sync跨tick覆盖语义.md

## 任务背景

当前 `core` 目标端的 `sync` 运行态虽然已经具备 `TimeKey` 仲裁框架，但 `sync` 类内真值仍按跨所有 tick 的全局最大强度聚合。结果是：当更晚 tick 到来一个更低强度的 `sync` 时，旧 tick 的更高强度仍会继续作为最终输出，无法体现“later sync 覆盖 earlier sync”的目标语义。

用户本轮明确确认的目标语义为：
- 更晚 tick 的 `sync` 应淘汰更早 tick 的 `sync`
- 同一 tick 内多个 `sync` 来源仍按强度 `max` 聚合
- 最新 tick 的 `sync` 被移除后，不回露旧 tick 的 `sync`

## 方案详情

### 现状分析

- `ActivatableTargetArbitrationComponent` 已能按 `TimeKey` 维护 `authorityTimeKey`，并拒绝更早 tick 的事件覆盖当前主导结果。
- 但 `ActivatableTargetConcurrentBucketComponent.recomputeSyncTruthFromConcurrentBuckets()` 当前会遍历所有 `sync` bucket，并把各来源强度做全局 `Math.max` 合并。
- `ActivatableTargetBlockEntity.resolveDerivedOutputPowerFromTruth()` 又直接读取 `syncSignalMaxStrength()` 作为 `SYNC` 最终输出，因此实际效果仍是“跨 tick 全局 max”。
- 当前存档已保留 `SyncConcurrentEntries`，因此不必新增新的持久化结构，只需调整“如何从现有 bucket 重建真值”的口径。

### 技术方案

- 保留现有 `syncConcurrentBuckets` / `runtimeSimulatedSyncConcurrentBuckets` 的结构与存档格式。
- 将 `sync` 真值重算口径从“遍历所有 tick bucket 合并”改为：
  - 仅选取最新 `TimeKey` 的 `sync` bucket 作为当前有效帧
  - 若持久 bucket 与运行态模拟 bucket 的最新 `TimeKey` 相同，则只合并这个同 tick 帧
  - 若两侧最新 `TimeKey` 不同，则只采用更晚的那一帧
- 当更晚 tick 的 `sync` 写入时，主动清理更早 tick 的 `sync` bucket`，避免后续删除最新帧后又回露旧帧。
- 保持同一 tick 内来源级 `max` 聚合与 `maxSources` 统计逻辑不变，只改变“参与聚合的是哪一帧”。
- 补充单测，锁定 later lower-strength sync 覆盖 earlier higher-strength sync、同 tick 仍取 `max`、最新帧删除不回露旧帧、存档恢复保持新语义。

## 原子步骤清单

### 步骤 1：收口sync真值重算口径
- **操作对象**：`ActivatableTargetConcurrentBucketComponent`
- **具体动作**：新增“只基于最新 `TimeKey` sync 帧重建真值”的辅助逻辑，保留同 tick 内 `max` 聚合
- **预期结果**：更晚 tick 的较低强度 `sync` 能覆盖更早 tick 的较高强度 `sync`
- **关键里程碑**：是

- **操作对象**：`ActivatableTargetConcurrentBucketComponent`、`ActivatableTargetDispatchSupport`
- **具体动作**：在写入更晚 tick 的 `sync` 时清理更早 tick bucket，避免最新帧移除后回露旧帧
- **预期结果**：`sync` 的跨 tick 行为严格保持“later 覆盖 earlier”
- **关键里程碑**：是

- **关键里程碑**：否

- **关键里程碑**：是

## 预期结果

`core` 对 `sync` 的处理将从“跨所有 tick 全局 max”收口为“同 tick 内 max、跨 tick 最新帧覆盖”。这样更晚 tick 的低强度 `sync` 可以正确覆盖更早 tick 的高强度 `sync`，且删除最新帧后不会回露旧 tick 结果。
