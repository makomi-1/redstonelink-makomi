# 新增边 replay 过滤补发修复

生成时间：2026-04-15 16:05:32
文件名：2026-04-15_160532_新增边replay过滤补发修复.md

## 任务背景
游戏内实测确认：当 `triggerSource` 已有可 replay 的 `sync` 真值时，后续新增 `triggerSource -> core` 边会立即触发一次 attach replay；但这条 replay 当前没有经过已放置 `send/receive` 过滤器的持久化真值判定，导致被过滤器拦截的新增边仍可能收到一次错误补发。

## 方案详情

### 现状分析
- `LinkSetExecutionService.applyPreparedReplace(...)` 在新增边后会调用 `InternalDispatchDeltaEvents.publishLinkAttached(...)`。
- `InternalDispatchDeltaRuleSupport.publishLinkAttached(...)` 当前会直接解析 replay 强度并发布 `SYNC_SIGNAL UPSERT`。
- `target chunk load replay` 与 `triggerSource attach replay` 两条 replay 路径已经在发布前通过 `LinkDispatchFilterService.allowsReplayByPersistedFilters(...)` 做了持久化过滤补判。
- 因此缺口只在“新增边即时 replay”这一路径上。

### 技术方案
- 在 `InternalDispatchDeltaRuleSupport.publishLinkAttached(...)` 的公共实现内补一层 attach replay 过滤判定。
- 对每个归一化后的 `triggerSource -> core` 配对，读取两端节点快照，并使用 `LinkDispatchFilterService.allowsReplayByPersistedFilters(...)` 判定是否允许 replay。
- 仅对判定通过的新增边发布 `publishSourceRebuildUpsertResolved(...)`；未通过的边直接跳过，不补发。
- 单目标入口复用同一公共实现，保证所有 attach replay 入口口径一致。

## 预期结果
- 新增边时的 `sync replay` 将同时受 `send` 与 `receive` 过滤器约束。
- 过滤器拦截的新增边不再收到错误补发。
- 普通实时 dispatch、删边失效、目标区块加载 replay 与 `triggerSource` attach replay 现有语义保持不变。

## 语义对齐说明
- 命名仅使用 `triggerSource/core`，不新增旧术语输出。
- 输入输出方向保持 `triggerSource -> core`，不允许反向写入。
- 兼容层不变，本次仅补 replay 发布条件，不改持久化结构。
- 与 `LinkNodeType.TRIGGER_SOURCE/CORE` 一一对应。
- 残余风险：`resolveReplaySyncStrength(...)` 仍依赖来源端当前可解析的 replay 强度；若运行态本身无法解析，则本次不会新增 replay，这属于既有语义，非本次修复范围。
