# 首批必跑二次收敛修复

生成时间：2026-03-24 16:48:56
文件名：2026-03-24_164856_首批必跑二次收敛修复.md

## 任务背景
首批必跑 suite 在上一轮修复后，已从多项命令/区块加载问题收敛到 3 个残留失败项：
- `F02 link_lifecycle_add_remove_set_clear`
- `F03 pulse_activate_sparse_zip`
- `F03 sync_triggerSource_custom_mixed_basic`

最新有效重跑结果表明，这 3 项已不再是同一类问题：
1. `F02` 为 bench 脚本读取游戏时间时的瞬时空响应问题；
2. `F03 pulse` 为功能矩阵中目标 serial 写死为 `1` 的配置错误；
3. `F03 custom` 为 trace 自动扩读策略过猛，导致多 serial 回读时命中命令限流。

## 方案详情

### 现状分析
- `tools/bench/run-bench.ps1` 的 `Get-ServerGameTime` 仅读取一次 `time query gametime`，没有对空响应或瞬时抖动做重试。
- `tools/bench/functional-matrix.json` 中 `pulse_activate_sparse_zip` 的 `pulse_targets_ticks` 断言仍硬编码 `serials: [1]`，与实际 `targets` 分配 serial 不一致。
- `tools/bench/run-bench.ps1` 的 `trace_read_tick_assert` 在检测到窗口可能被截断时，会将读取上限直接扩到 sampler capacity；在多 serial 连续断言场景下，这会明显放大每次读成本并触发命令频率限制。

### 技术方案
- 为 `Get-ServerGameTime` 增加有限次重试与短暂退避，只在多次失败后再抛出错误。
- 将 `pulse_activate_sparse_zip` 的断言对象改为引用 `targets`，避免依赖“序号恰好从 1 开始”的旧假设。
- 收敛 trace 自动扩读策略：
  - 仅在确实检测到起始窗口被裁掉时才扩读；
  - 扩读不再默认打满到 mount capacity，而是按缺口做有限补偿；
  - 扩读后若仍遇到频率限制，则保留原始失败结果，避免整批断言被单次过大读取拖垮。

### 影响范围
- `tools/bench/run-bench.ps1`
- `tools/bench/functional-matrix.json`

- **操作对象**：`tools/bench/run-bench.ps1`
- **具体动作**：为 `Get-ServerGameTime` 增加空响应/不可解析响应的有限次重试。
- **预期结果**：`F02` 不再因瞬时空返回提前失败。
- **关键里程碑**：是

- **预期结果**：`F03 pulse` 能读取到实际挂载的 core sampler。
- **关键里程碑**：是

### 步骤 3：收敛 trace 自动扩读
- **操作对象**：`tools/bench/run-bench.ps1`
- **具体动作**：调整 `trace_read_tick_assert` 的扩读上限计算和补读触发条件，避免多 serial 场景打满读取。
- **预期结果**：`F03 custom` 不再因 `Too many requests` 造成假失败。
- **关键里程碑**：是
