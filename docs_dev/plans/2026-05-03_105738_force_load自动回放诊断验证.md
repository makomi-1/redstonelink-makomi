# force_load自动回放诊断验证

生成时间：2026-05-03 10:57:38
文件名：2026-05-03_105738_force_load自动回放诊断验证.md

## 任务背景
用户要求先解释并验证 `force_load` 激活器在 `x51/x53` 两个 dedicated bench 用例中的失败根因。现有分析已将问题范围收缩到 `triggerSource/core` 语义下的 `force_load` 激活器专有自动回放路径：玩家 `TP` 拉起目标区块与 `resident` 拉起目标区块均可通过，只有 `force_load` 激活器在目标区块拉起后未恢复高态。本轮目标是在不先修改业务语义的前提下，增加最小化诊断日志，重跑 `x51/x53`，确认是否存在“提前 replay 抢跑，后续 target attach replay 被去重吞掉”的现象。

## 方案详情

### 现状分析
- `force_load` 激活器在条目 `upsert` 后会立即调用 `publishTriggerSourceCurrentOrPersistedSyncReplay(...)`，这是一条玩家 `TP` 与 `resident` 都不会走到的专有副作用路径。
- 目标 `core` 的常规恢复主链位于 `LinkNodeLifecycleDispatchEvents.tryReplayTargetChunkLoad(...)`，仅在目标节点真正 attach/ready 后触发。
- 内部事件发布去重使用 `DispatchDedupKey`，其键中包含 `source/target`、`syncSignalStrength` 与 `eventMeta(timeKey/seq)`，不是按“当前发布时刻”去重，而是按“事件身份”去重。
- 现有推断需要日志级证据支撑：确认 `force_load` 提前 replay 是否发生、其使用的 `eventMeta` 是否复用了 persisted snapshot、target attach replay 是否因此被去重拒绝。

### 技术方案
- 在 `InternalDispatchDeltaRuleSupport` 中为两类 replay 增加受 `crosschunk.diag.runtime.enabled` 控制的诊断日志：
  - `force_load` 激活器的提前 replay：记录来源、目标、走 live/persisted、强度与 `eventMeta`。
  - target attach replay：记录目标 attach 时的 replay 资格、snapshot 与 `eventMeta`。
- 在 `InternalDispatchDeltaPublishSupport` 中增加去重命中日志，记录被吞掉的 `DispatchDedupKey` 与事件关键字段。
- 保持日志实现最小化，不调整 `triggerSource/core` 方向语义，不引入 `com.makomi.api.v1.*` 依赖。
- 按游戏内回归测试构建同步规则，先 `remapJar`，再同步 dedicated server mod jar，然后只定向重跑 `x51/x53`。

### 影响范围
- 诊断日志代码：
  - `src/main/java/com/makomi/data/InternalDispatchDeltaRuleSupport.java`
  - `src/main/java/com/makomi/data/InternalDispatchDeltaPublishSupport.java`
  - `src/main/java/com/makomi/data/LinkNodeLifecycleDispatchEvents.java`
- 游戏内回归入口：
  - `tools/bench/run-regression-lifecycle-suite-build-sync.ps1`
  - 或 `tools/bench/run-bench-suite.ps1` + `CaseIds`
