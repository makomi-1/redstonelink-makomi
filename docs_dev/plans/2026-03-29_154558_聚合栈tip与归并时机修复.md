# 聚合栈tip与归并时机修复

生成时间：2026-03-29 15:45:58
文件名：2026-03-29_154558_聚合栈tip与归并时机修复.md

## 任务背景

第一层聚合栈已经支持基础聚合交互，但当前仍有两个体验问题：

- 聚合栈 tooltip 仍展示单件语义的栈顶序号和当前连接，信息噪声偏大
- 聚合栈单件出栈后，新单件没有同步当前连接信息

第二层菜单后处理自动归并已经覆盖 `shift` 快移与批量合成后的散栈折叠，但当前时机过宽：

- 玩家手动拆分聚合栈后，下一拍会被第二层服务端后处理立即重新合并

本轮目标是在不引入新的 mixin 的前提下，修正上述两个问题。

## 方案详情

### 现状分析

- 聚合栈 tooltip 逻辑位于 `LinkerItem.appendHoverText(...)` 与 `PairableBlockItem.appendHoverText(...)`，当前无论是否聚合都会先输出单件语义的序号和当前连接。
- 单件出栈路径位于 `PairableItemAggregateClickSupport`；新单件会通过 `LinkItemData.copySingleSerialStack(...)` 或 `LinkItemData.setSerialGroup(...)` 生成，但聚合序号组写入时会清空 `KEY_LINKS`，导致新单件没有当前连接快照。
- 第二层自动归并当前只有“`menu != null` 且 `carried` 为空”这一层保护，不区分 `shift`/批量合成 与 玩家手动拆分/放一，因此时机过宽。

### 技术方案

- tooltip 改为按聚合态分支：
  - 聚合态只显示聚合数量、聚合序号列表和聚合限制提示
  - 非聚合态继续显示单件序号、当前连接与原有操作提示
- 为单件出栈增加“当前连接快照同步”：
  - 在服务端根据新单件的 `serial + LinkNodeType` 调用现有 `NodeSnapshotQueryService.queryItemSnapshotLinks(...)`
  - 将查询结果继续写入现有 `KEY_LINKS`
  - 客户端侧不做业务判定，依赖服务端同步结果回写
- 第二层增加“手动布局保持”：
  - 第一层明确属于“手动拆分/右键放一”的操作成功后，登记玩家当前菜单分区为手动布局
  - 第二层在玩家光标重新归空后，会先记录当前布局；只要布局未再变化，就持续跳过自动归并
  - 一旦同分区同物品布局后续再次变化，就恢复第二层自动归并
  - 非手动路径如 `shift` 快移、`shift` 合成仍继续自动归并

## 原子步骤清单

### 步骤 1：调整聚合栈 tooltip 分支
- **操作对象**：`LinkerItem`、`PairableBlockItem`
- **具体动作**：按是否聚合拆分 tooltip 输出逻辑
- **预期结果**：聚合栈不再展示单件序号和当前连接
- **关键里程碑**：是

### 步骤 2：补齐单件出栈连接快照
- **操作对象**：`LinkItemData`、`PairableItemAggregateClickSupport`
- **具体动作**：在单件拆出/放一后同步当前连接快照
- **预期结果**：新单件可继续展示当前连接信息
- **关键里程碑**：是

### 步骤 3：修正第二层自动归并时机
- **操作对象**：`PairableItemAggregateMenuNormalizationService`
- **具体动作**：加入手动布局保持判断
- **预期结果**：手动拆分不会被下一拍立刻合回，布局变化后再恢复自动归并
- **关键里程碑**：是

### 步骤 4：补充回归测试并验证
- **操作对象**：相关测试类
- **具体动作**：补充 tooltip/连接同步/归并时机测试并执行全量回归
- **预期结果**：修复结果具备自动化保护
- **关键里程碑**：否

## 预期结果

- 聚合栈 tooltip 只保留聚合语义信息，不再混入单件序号和当前连接。
- 单件从聚合栈拆出后，会同步获得当前连接快照。
- 第二层自动归并仍覆盖 `shift` 快移与批量合成，但不会把玩家刚手动拆开的聚合栈立刻重新合并。

## 语义对齐说明

- 本方案不新增 `triggerSource/core` 之外的领域术语输出。
- 本方案不涉及方向写入，不改变 `LinkNodeType` 与 `triggerSource/core` 的映射关系。
- 本方案只修复聚合交互显示、单件出栈快照同步与第二层归并时机，不改变命令链路、配对 GUI 和持久化结构。
- 残余风险：第二层“手动布局保持”属于非 mixin 的策略性判断，并非原版 `doClick(...)` 内部点击类型的精确复刻。
