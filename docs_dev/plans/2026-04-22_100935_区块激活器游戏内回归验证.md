# 区块激活器游戏内回归验证

生成时间：2026-04-22 10:09:35
文件名：2026-04-22_100935_区块激活器游戏内回归验证.md

## 任务背景
当前“区块激活器”已经完成数据层、运行态查询、方块实体生命周期、GUI 与基础单元测试，但还缺少 dedicated server 级别的真实游戏内回归用例，无法证明其在区块卸载、跨区块加载与常驻保持场景下的实际生效链路。

本轮目标是在现有 `tools/bench` dedicated functional 体系中补充区块激活器专项回归，并把它接入既有生命周期/完整回归入口。额外约束为：
- 每个区块激活器只作用于 `3` 个 `triggerSource`
- 用例布局必须避开出生点常驻加载区块影响，不能把 spawn chunk 常驻误判为区块激活器效果

## 方案详情

### 现状分析
- 仓库已有成熟的 `tools/bench` dedicated functional 回归框架，支持 `setblock`、`data merge block`、`forceload add/remove`、`node get`、输入驱动与 suite 编排。
- 现有 `x02/x09/x10/x14/x19` 已验证 resident、forceLoad、离线/重载、目标/来源卸载等基础跨区块语义，可直接复用其布局、断言与节奏。
- `node get triggerSource/core` 已能稳定输出 `online/active` 等字段，足以作为区块激活器 force_load/resident 实效验证口径。

### 技术方案
1. 新增一个“区块激活器 force_load” functional case：
   - 在远离出生点的 chunk 放置 `3` 个 `sync_emitter`、`3` 个跨区块目标 `core`，并放置 1 个 `link_chunk_activator`
   - 用 `data merge block` 直接写入区块激活器方块实体配置，使其节点集恰好包含那 `3` 个 `triggerSource`
   - 用邻接红石块使区块激活器处于激活态，然后卸载激活器自身 chunk 与目标 chunk
   - 在 `forceLoad.mode=whitelist` 下驱动来源输入，验证目标 `core` 仍会因区块激活器贡献被自动加载并激活
2. 新增一个“区块激活器 resident” functional case：
   - 在远离出生点的 chunk 放置 `3` 个 `sync_emitter` 与 1 个 `link_chunk_activator`
   - 区块激活器配置为 `resident` 模式并激活
   - 移除来源 chunk 的外部 `forceload` 后，验证这 `3` 个 `triggerSource` 仍保持 `online=true`
   - 再重新加载激活器所在 chunk，撤销区块激活器激活态，验证来源最终回到 `online=false`
3. 把这两个 case 注册到 `functional-matrix.json`，并接入 `regression-lifecycle.json` 与 `regression-full.json`
4. 按项目规则执行验证：
   - 先跑 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`
   - 再基于当前工作区构建运行 jar，并同步 dedicated server jar
   - 最后只跑新增 case 的 dedicated build-sync 回归，作为本轮游戏内验证证据
