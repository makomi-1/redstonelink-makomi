# 配置层 RedstoneLinkConfig 拆分一期

生成时间：2026-03-24 22:22:45
文件名：2026-03-24_222245_配置层RedstoneLinkConfig拆分一期.md

## 任务背景

当前代码组织优化已经完成命令层第一阶段拆分，下一步按既定顺序推进配置层与抽象基类中的 1k+ 文件治理。  
结合现有计划与草稿，配置层应先于抽象基类执行，以降低一次性重构风险，并复用现有配置解析测试作为回归护栏。

## 方案详情

### 现状分析

`src/main/java/com/makomi/config/RedstoneLinkConfig.java` 当前约 1727 行，同时承担以下职责：

- 配置加载与热重载入口
- 主配置解析
- 跨区块配置解析
- 解析辅助函数
- 默认配置模板拼装
- 配置快照结构定义
- 大量静态 accessor

这使得文件职责过重，后续继续补充配置项、注释和测试时成本偏高。

### 技术方案

本轮采用“对外门面不变、内部职责拆分”的低风险方案：

1. 保留 `RedstoneLinkConfig` 作为唯一对外入口，现有 `xxx()` accessor 和 load/reload 流程不改。
2. 将主配置解析逻辑拆出到独立 parser 类。
3. 将跨区块配置解析及相关 preset/type-set 解析拆出到独立 parser 类。
4. 将默认配置模板文本拆出到独立 template 类。
5. 保留 `RedstoneLinkConfig.parse(Properties)` 与 `parseCrossChunk(Properties)` 私有桥接入口，兼容现有反射测试。
6. 本轮不处理 `ActivatableTargetBlockEntity`，避免把配置重构和运行态重构混在同一批次。

### 技术取舍

- 选择先拆配置层而不是抽象基类：
  配置解析行为边界更清晰，测试护栏更成熟，重构风险更低。
- 选择保留 facade 而不是直接调整调用面：
  可把影响限制在 `com.makomi.config` 包内部，避免引入无关回归。
- 选择先保留快照结构在 `RedstoneLinkConfig`：
  降低本轮 public/internal 类型扩散风险，为后续二次整理保留空间。

### 影响范围

- `src/main/java/com/makomi/config/RedstoneLinkConfig.java`
- 新增同包 support/template/parser 类
- `src/test/java/com/makomi/config/*` 相关配置测试仅做兼容性回归，不预期行为修改
