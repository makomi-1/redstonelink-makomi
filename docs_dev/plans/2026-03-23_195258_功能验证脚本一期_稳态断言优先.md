# 功能验证脚本一期_稳态断言优先

生成时间：2026-03-23 19:52:58
文件名：2026-03-23_195258_功能验证脚本一期_稳态断言优先.md

## 任务背景

当前仓库已有 `tools/bench/run-bench.ps1` 与性能压测矩阵，能够完成放置节点、建链、驱动激活与结果落盘，但还没有一套面向“输入器 + 激活命令 + 采集器”的自动功能验证脚本。

本轮目标不是重做一套新框架，而是复用现有 bench 骨架，新增一条“功能验证模式”执行路径，用来验证：

1. `input start` 对 `triggerSource/core` 的稳定驱动是否符合预期
2. `node activate` 的 `pulse/toggle` 行为是否符合预期
3. `node trace latest` 挂载后的阶段状态是否符合预期
4. `s/p/t` 在不同序号分布下的理论结果与设计结果是否一致

本轮暂不把 `trace read` 作为主断言面，不做逐 tick 波形证明；该能力保留到第二阶段增强。

## 方案详情

### 现状分析

- `tools/bench/run-bench.ps1` 当前只有 `RunCase`，驱动模型偏向性能 case，核心循环仍是基于本地睡眠的 schedule。
- `node trace latest` 已支持批量序号，适合做当前快照读取；`node trace read` 仍是单序号接口，更适合作为补证而不是多节点主断言。
- `NodeStateTraceService.mount(...)` 会在挂载时立即写入一条当前快照，因此若直接做“采集后 n tick 内逐 tick 对比”，需要先处理基线样本裁剪问题。
- `InputEndpointKind` 目前只覆盖 `TRIGGER_SOURCE_INPUT` 与 `CORE_SYNC_DIRECT`，因此 `sync` 类验证适合走输入器，`pulse/toggle` 第一版仍应走 `activate`。

### 技术方案

1. 复用现有 bench 脚本骨架
   - 保留现有 `Action=RunCase`
   - 新增 `Action=RunFunctionalCase`
   - 不污染现有性能矩阵与 spark 流程

2. 为功能验证新增 phase runner
   - 不再把功能 case 建模成单一 `drive.totalTicks + steps`
   - 改为按阶段顺序执行，阶段类型至少包括：
     - `trace_mount`
     - `input_start_square`
     - `input_start_custom`
     - `input_clear`
     - `activate_batch`
     - `wait_ticks`
     - `trace_latest_assert`
     - `node_runtime_assert`

3. 第一阶段断言以“阶段稳态”优先
   - 主断言面使用 `node trace latest`
   - 断言字段聚焦：
     - `active`
     - `input`
     - `output`
     - `configuredMode`
     - `effectiveMode`
     - `resolvedStrength`
   - `trace read` 本轮不做主路径，仅预留为第二阶段逐 tick 对比增强项

4. 新增独立功能矩阵
   - 文件：`tools/bench/functional-matrix.json`
   - 与 `tools/bench/matrix.json` 分离
   - 首批落 4~5 个最小可验证 case，覆盖：
     - `sync` 输入器 + 范围序号
     - `sync` 输入器 + 斜杠序号
     - `pulse` 批量激活
     - `toggle` 双次翻转
     - `toggle` fan-in 奇偶归并

5. 结果输出扩展为“功能验证报告”
   - 在 JSON 里新增：
     - `phases`
     - `checks`
     - `passed`
     - `failedChecks`
     - `artifacts`
   - 让功能验证产物与性能产物可并存，但可清晰区分

### 技术取舍

- 选择复用 `run-bench.ps1`，是因为现有放置、建链、RCON、结果落盘都已可用，重写测试脚手架收益低于维护成本。
- 第一阶段不直接上 `trace read` 逐 tick 主断言，是因为当前 `read` 为单序号接口，且挂载即写基线快照，直接强上逐 tick 证明会明显放大脚本复杂度与 flaky 风险。
- 保留第二阶段增强空间：待功能验证脚本稳定后，再决定是否补 `trace read` 批量化、服务端 tick 栅栏与逐 tick 波形断言。
