# core批提交与异步目标级调度接入

生成时间：2026-03-31 21:07:08
文件名：2026-03-31_210708_core批提交与异步目标级调度接入.md

## 任务背景

当前 `triggerSource -> core` 的 SYNC / invalidation 相关链路，虽然生命周期侧已经改成“节点事件发布 + tick 消费”，但在目标端仍然是逐条 delta 立即写入、逐条重算、逐条对外生效。这会带来两个问题：

1. 同一时间粒度内多来源命中同一 `core` 时，虽然最终结果通常正确，但中间态可能被服务端逻辑观察到。
2. crosschunk release、target attach replay 等异步链路会重复查找目标实体、重复重算真值，存在额外性能开销。

本轮只实现已确认方案中的第 1 级与第 2 级：

1. 给 `core` 增加批提交能力。
2. 新增只覆盖异步链路的目标级批调度层。

本轮明确不做：

1. 不接入 `ACTIVATION` / `toggle` / `pulse`。
2. 不修改 direct 在线立即投影语义。
3. 不引入对外 API 调整。

## 方案详情

### 现状分析

1. 生命周期 replay 与 crosschunk release 最终都会落到 `ActivatableTargetBlockEntity.applyDispatchDelta(...)`，而该入口当前是每条 delta 后立即重算一次。
2. 目标端已经存在结果写回去重与 fanout 去重缓存，但它们发生在“单条 delta 已经完成重算”之后，不能替代批次入口压缩。
3. crosschunk queue 已经有离线 pending 的 key 级 upsert 去重，但这只能减少离线累积，不能让同一 `core` 的多条异步变更在目标侧合并为一次提交。

### 技术方案

1. 在 `ActivatableTargetBlockEntity` 中新增 `applyDispatchBatch(...)` 能力。
2. 批次内仅允许 `SYNC_SIGNAL`、`TRIGGER_SOURCE_INVALIDATION`、`TRIGGER_SOURCE_CHUNK_UNLOAD_INVALIDATION`。
3. 批次执行策略为：
   - 逐条把规约后的变更写入来源桶；
   - 批末统一执行一次真值重算、仲裁重算与派生状态写回；
   - 避免单条 delta 重复触发 `applyDerivedStateFromTruth()`。
4. 新增服务端级 `core` 批调度器，负责：
   - 以 `dimension + coreType + coreSerial + blockPos + flushTick` 聚合；
   - 以 `triggerSource + deltaKind` 为键做窗口内去重；
   - 将生命周期 replay、crosschunk release 等异步链路统一导入批次调度；
   - 在 tick 末按预算 flush。
5. direct 在线路径保持不变，确保本轮语义变化仅限异步链路。

### 影响范围

1. `src/main/java/com/makomi/block/entity/ActivatableTargetBlockEntity.java`
2. `src/main/java/com/makomi/data/CrossChunkDispatchRuntimeSupport.java`
3. `src/main/java/com/makomi/data/LinkNodeLifecycleDispatchEvents.java`
4. 新增 `src/main/java/com/makomi/data/*Batch*` 调度器相关类
5. 可能涉及异步 delta 发布/投影辅助类的小范围接线调整

## 原子步骤清单

### 步骤 1：补齐 core 端批提交入口
- **操作对象**：`ActivatableTargetBlockEntity`
- **具体动作**：新增批提交数据模型与 `applyDispatchBatch(...)`，抽离 SYNC / invalidation 的“仅更新桶”和“批末统一重算”路径
- **预期结果**：同一批内多条异步变更只触发一次最终重算
- **关键里程碑**：是

### 步骤 2：实现目标级批调度器
- **操作对象**：新增调度器类
- **具体动作**：实现 enqueue、窗口内去重规约、按 `core` flush、服务端生命周期清理
- **预期结果**：异步链路拥有统一的目标级缓冲/提交层
- **关键里程碑**：是

### 步骤 3：接入 crosschunk release
- **操作对象**：`CrossChunkDispatchRuntimeSupport`
- **具体动作**：将 ready pending 从“逐条 apply”改为“按目标 enqueue -> 批 flush”
- **预期结果**：queue release 进入统一批调度层
- **关键里程碑**：是

### 步骤 4：接入生命周期 replay
- **操作对象**：`LinkNodeLifecycleDispatchEvents` 及必要发布路径
- **具体动作**：让 target attach replay / source attach sync replay 的最终投影走异步批提交入口
- **预期结果**：生命周期 replay 与 queue release 使用同一批提交模型
- **关键里程碑**：否

### 步骤 5：验证与回归
- **操作对象**：本地编译 / 相关测试 / 必要 bench 用例
- **具体动作**：验证新增批调度器能正确合并异步 SYNC / invalidation，且 direct 在线路径不受影响
- **预期结果**：确认 1+2 级改动可运行且无明显回归
- **关键里程碑**：是

## 预期结果

1. 异步 SYNC / invalidation 链路实现“一个 `core` 一次批提交”。
2. 同一时间粒度内的异步多来源变更在目标端只重算一次、只生效一次。
3. direct 在线路径与 `ACTIVATION` 语义保持原状，为后续更大范围接入保留低风险演进路径。
