# scheduler两阶段flush防重入修复

生成时间：2026-04-03 10:35:22
文件名：2026-04-03_103522_scheduler两阶段flush防重入修复.md

## 任务背景
工作区客户端日志显示集成服在 `CoreDispatchBatchScheduler.flushServerBatches(...)` 内抛出 `ConcurrentModificationException`。已确认根因不是业务语义错误，而是 scheduler 在遍历 `pendingByTarget` 时，下游 `core.applyDispatchBatch(...)` 触发邻居扇出，进一步回流到 `enqueueLoadedTargetDispatch(...)`，导致同一张 map 在 flush 过程中被重入修改。

## 方案详情

### 现状分析
当前实现把“遍历到期 bucket”和“立即 apply 到目标实体”放在同一轮 map 迭代中执行。这样一旦 apply 下游再入队，就会直接修改当前正在迭代的 `pendingByTarget`，与 `window=0` late-arrival 补 flush 路径叠加时更容易触发并发修改异常。

### 技术方案
保留现有批语义，不改 direct dispatch / late-arrival 的设计口径，只把 flush 改成两阶段：
1. 第一阶段仅在 scheduler 内遍历 `pendingByTarget`，把本轮到期 bucket 从 accumulator 摘出到本地 flush plan。
2. accumulator 摘空后立即从 map 移除并回收到对象池。
3. 第二阶段脱离 map 迭代，再统一执行 flush plan 的 `applyDispatchBatch(...)`。

这样可以保持当前设计语义不变，只消除“flush 中重入 enqueue 修改同一 map”的结构性风险。

### 影响范围
- `src/main/java/com/makomi/data/CoreDispatchBatchScheduler.java`
- `src/test/java/com/makomi/data/CoreDispatchBatchSchedulerTest.java`

## 原子步骤清单

### 步骤 1：改造 scheduler flush 相位
- **操作对象**：`CoreDispatchBatchScheduler`
- **具体动作**：新增本地 flush plan 抽象，把 accumulator 的到期 bucket 先摘出，再脱离 `pendingByTarget` 迭代后统一 apply
- **预期结果**：flush 期间下游重入 enqueue 不再修改正在迭代的 map
- **关键里程碑**：是

### 步骤 2：补回归测试
- **操作对象**：`CoreDispatchBatchSchedulerTest`
- **具体动作**：补足两阶段 flush 的结构性回归验证，覆盖“到期 bucket 已从 accumulator 脱离后再 apply”的关键行为
- **预期结果**：自动化测试能锁住本次修复点
- **关键里程碑**：是

- **预期结果**：验证本地回归门禁与最小游戏内回环均不再触发该异常
- **关键里程碑**：是
