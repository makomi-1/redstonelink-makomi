# x22混合逐tick窗口对齐修复

生成时间：2026-04-02 18:48:33
文件名：2026-04-02_184833_x22混合逐tick窗口对齐修复.md

## 任务背景

`x22` mixed 逐 tick 专项当前在 `window=1/2` 下失败，现象是 target `sync` 段依旧在 `jobStartTick+1` 附近出现，与 `window=0` 基本一致。初步怀疑是 `crosschunk.dispatch.batchWindowTicks` 未被 suite 成功覆盖；但对照 `x21` 成功案例、suite summary、bench 结果与运行时单测后，更大的可能是 `x22` 当前断言仍直接锚定 `input start` 的 `jobStartTick`，缺少像 `x21` 那样的 source 参考相位，导致 source 起点偏移与 core 相对 source 的固定延迟被混在一起，无法准确判断 mixed 场景是否真的违反固定窗口语义。

## 方案详情

### 现状分析

1. `x22` suite summary 已记录 `parameters.dispatchBatchWindowTicks=1/2`，同时 `serverConfigOverrides.crosschunk.dispatch.batchWindowTicks=1/2` 也已写入运行结果，因此“suite 完全未覆盖配置”缺少直接证据。
2. `x21` 在同一 bench/suite 注入链路下已成功验证 `window=1/2`，说明 bench 参数展开、suite 配置覆盖与运行时配置解析主链路是可工作的。
3. `CoreDispatchBatchScheduler` 现有单测已覆盖 `dueTick` 分桶、非零窗口到期 flush 与 `window=0` late-arrival 补 flush，说明调度器基础语义已有保护。
4. `x22` 的 `trace_read_tick_assert` 目前只对 target 做绝对锚点断言，没有 source 侧 matched start tick 参考，无法像 `x21` 那样直接验证“core 相对 triggerSource 延迟是否等于窗口值”。

### 技术方案

本轮优先修 bench 口径，而不是先改运行时：

1. 为 `trace_read_tick_assert` 增加 matched start tick 汇总与参考相位对齐能力，让它能像 `trace_sync_latency_collect` 一样基于 source 已匹配窗口对齐 target。
2. 为 `x22` 补 source 侧逐 tick phase：
   - `sync` 复用现有 `sync_custom`；
   - `pulse/toggle` 补充 custom 序列模板；
   - target 侧则改为基于 source phase 做 reference 对齐。
3. 保留 `x22` 现有分段断言结构，只修正“如何找到每一段真实起点”的口径，避免一次性重写 mixed 模板或运行时逻辑。
4. 若 bench 口径补齐后 `x22` 仍失败，则说明 mixed 单核仲裁/派发路径仍可能存在运行时问题；届时再依据新的 source/reference 证据最小化修运行时。
