# 同区块SYNC延迟批量采集与专项验证

生成时间：2026-04-01 15:36:47

## 任务背景

当前进入第 9 级后，重点不再是继续调优 crosschunk，而是补齐“传播模型的延迟测试”能力。用户已经明确缩小范围：

- 只做同区块场景；
- 只做 `SYNC`；
- 优先补齐批量延迟采集能力；
- 目标是验证高并发下的传播延迟，并判断最低处理窗口要开到多大；
- 暂不做 crosschunk `replay/force-load`；
- 暂不做 `toggle/pulse`。

现有 `node trace` 能记录结构化状态轨迹，但读取是“单 serial 查询”，不适合直接对 `>=4096` 有效连接做游戏内批量延迟分析。因此本轮需要在现有 bench 体系内补一个只在 benchmark 模式下可用的批量分析入口，把 trace 读取与延迟判定放到服务端一次性完成。

## 方案详情

### 现状分析

- `NodeStateTraceService` 已经具备挂载 trace ring buffer 的能力，适合继续复用。
- 公开的 `node trace read` 路径偏向人工排查，不适合对 1024+ serial 做批量 RCON 轮询。
- bench 侧已有 `mountRef`、`anchorRef`、波形元数据与 functional phase 框架，可直接承接新的批量延迟收集阶段。
- 已有同区块高并发布局可复用，例如 `1024 -> 1024` 的 `banded16`，其有效连接数已满足“>=4096 有效信号（连接）”要求。

### 技术方案

1. 在 `/redstonelink bench` 下新增 benchmark-only 的 trace 批量延迟分析命令。
2. 服务端基于已挂载的 trace buffer 批量扫描指定 `core` 集合，对照输入波形元数据做 `SYNC` 延迟判定。
3. bench PowerShell 新增 `trace_sync_latency_collect` phase，调用上述命令并把结果写回 functional result JSON。
4. 只新增同区块 `SYNC` 延迟专项 case，分别覆盖单次突发和连续方波两类负载。
5. 第一轮只验证 `window=0/1/2` 的处理窗口结论，不引入新的公开命令语义。

### 影响范围

- `src/main/java/com/makomi/command/bench/BenchCommandRegistry.java`
- `src/main/java/com/makomi/data/NodeStateTraceService.java`
- `tools/bench/lib/Bench.FunctionalTrace.ps1`
- `tools/bench/templates/functional/phases.json`
- `tools/bench/functional-matrix.json`
- 新增同区块 `SYNC` 延迟功能 case 文件

### 技术取舍

- 采用 bench 内部命令而不是扩展公开 `node trace` 命令，原因是本轮目标是大规模压测采样，不应把高开销批量分析能力暴露为常规运维接口。
- 采用“服务端一次性分析 + bench 拉聚合结果”的方式，而不是 4096 次 `trace read` RCON 调用，原因是后者会把测量噪声放大到无法判断真实处理窗口。
- 只先支持 `SYNC`，避免在第一轮把 `toggle/pulse` 的判定规则混入实现，先把采集链路跑通。

### 预期结果

- 可以在游戏内 bench 中直接对同区块高并发 `SYNC` 传播做批量延迟采集。
- functional result JSON 中新增统一的延迟统计结果，可用于后续脚本化汇总。
- 能够基于 `window=0/1/2` 的同一区块高并发专项，判断最低可接受处理窗口。

## 原子步骤清单

### 步骤 1：补齐 bench 内部批量延迟分析命令
- **操作对象**：`BenchCommandRegistry`、相关 trace 支撑代码
- **具体动作**：新增 benchmark-only 子命令，接收挂载引用、目标集合和波形参数，并返回批量延迟统计结果。
- **预期结果**：游戏内 bench 可通过单次命令获取整批 `core` 的 `SYNC` 延迟分析数据。
- **关键里程碑**：是

### 步骤 2：实现服务端SYNC延迟批量分析
- **操作对象**：`NodeStateTraceService` 及其协作代码
- **具体动作**：在挂载 trace buffer 上实现按 serial 批量扫描、按波形对齐的 `SYNC` 延迟判定与聚合统计。
- **预期结果**：同区块高并发目标的延迟分析在服务端完成，不依赖海量单点 RCON 读取。
- **关键里程碑**：是

### 步骤 3：接入 bench functional phase
- **操作对象**：`Bench.FunctionalTrace.ps1`、`phases.json`
- **具体动作**：新增 `trace_sync_latency_collect` phase，复用已有 mount/anchor/waveform 元数据，写入结果 JSON。
- **预期结果**：functional case 可声明式启用延迟批量采集。
- **关键里程碑**：是

### 步骤 4：新增同区块SYNC延迟专项用例
- **操作对象**：`tools/bench/cases/functional/**`、`functional-matrix.json`
- **具体动作**：新增连续方波与单次突发两个同区块 `SYNC` 延迟 case，并注册矩阵。
- **预期结果**：可以直接跑专项测试观察高并发延迟与窗口需求。
- **关键里程碑**：是

### 步骤 5：执行验证
- **操作对象**：Gradle 全标签测试与定向功能 case
- **具体动作**：先执行 `.\gradlew.bat test testIntegration testClient testSlow --no-daemon`，再跑新增专项做窗口对比。
- **预期结果**：确认功能不回退，并拿到第一轮同区块高并发延迟数据。
- **关键里程碑**：是

## 预期结果

项目将新增一条仅供 bench 使用的高并发延迟采集链路，能够在不改公开语义的前提下，对同区块 `SYNC` 的大规模传播延迟做批量分析，并直接为“窗口最小应开多大”提供实测依据。

## 语义对齐说明

- 命名校验：方案与后续新增文案统一使用 `triggerSource/core`，不引入新的旧术语输出。
- 方向校验：采样与分析仍然只围绕 `triggerSource -> core`，不新增反向链路。
- 映射校验：不修改 `LinkNodeType.TRIGGER_SOURCE/CORE` 的既有映射关系。
- 兼容层校验：本轮不扩公开 API，只新增 benchmark-only 内部命令；旧术语仅保留已有输入兼容，不新增写回。
- 残余风险：若 trace 缓冲窗口长度不足以覆盖高并发长波形采样，可能出现样本不足；实现时需要把“不足样本”显式写入统计结果，避免误判为零延迟。
