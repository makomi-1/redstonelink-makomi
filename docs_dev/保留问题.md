### send 过滤器隐藏拦截态与重进重演仅做性能观察
- 风险描述：
1. 当单 `triggerSource -> core` 拓扑旁接 `send filter`，并用 `nodeSetMode=blocklist + signalThresholdSource=neighbor_max_input + signalMode=upper_bound` 拦截同一 `triggerSource` 时，可能出现过滤器外显、拦截状态与 reload 后表现不一致的设计空白边界。
2. 当前该现象不按功能缺陷处理，但仍需要持续确认其不会引入异常热点、MSPT 抖动、spark health 恶化或其它不可接受的性能副作用。
3. 特别是“持久输入”“2 tick 周期方波输入”“重进持久输入世界”三种路径，需要长期保持可重复采样。
- 规避方案：
1. 持续使用 `p27` 三个 performance case 与 `send-filter-hidden-intercept-perf.json` suite 做专项回归，验收只看 spark 性能采集是否异常。
2. 分析时统一按 `docs/使用说明.md` 中 spark 章节的机读入口取数，不以过滤器亮灭或 core 外显直接判定本轮结论。

### core 配对迁移后的显式命令兼容残留
- 风险描述：
1. 本轮会把 `core` 配对 GUI/网络提交链路迁移到新实现，并把真实写入统一收口为 `triggerSource -> core`。
2. 但若命令层仍保留显式兼容入口 `link set core ...`，则旧方向语义不会在仓库中彻底消失，后续维护时仍可能有人绕过新实现，继续沿用旧视角命令。
3. 因此本轮能收口的是“界面/协议层”，不是“仓库内全部显式兼容入口”。
- 规避方案：
1. 新增实现、测试、文档统一只使用 `triggerSource/core` 与 `triggerSource -> core` 正向语义，不再新增任何基于 `core` 作为真实来源的提交路径。
2. 若后续需要彻底收口旧方向语义，再单独立项清理显式兼容命令 `link set core ...`，并同步处理命令帮助、测试与使用说明。

### QuickLink 上行边界与 core 配对旧方向语义
- 风险描述：
1. 当前 `QuickLink` 上行链路仍主要信任客户端提供的坐标，服务端缺少与近外显同等级的距离和节点身份校验；若恶意客户端伪造请求，只要目标区块已加载，就可能对远处或错误节点触发采集/应用逻辑。
2. 当前 `CorePairingScreen` 与 `PairingNetwork.openCorePairing(...)` 仍沿用“`core` 作为 sourceType”的旧模型；若在未重设语义边界前直接把配对界面改成结构化 `C2S` 写入协议，只会把旧方向语义继续固化到协议层。
- 规避方案：
1. 先独立完成 `QuickLink` 服务端节点定位校验加固，优先复用近外显已有的“维度、区块、距离、节点身份一致”边界模型。
2. 配对协议重构采用“先抽共享写入服务，再迁移 triggerSource 侧结构化 `C2S`”的顺序，不直接复制当前命令字符串路径。
3. `core` 侧单独定义为兼容视图或按 `triggerSource -> core` 新语义重设计后，再决定是否接入新的写入协议。

### trace 采样相位与 pulse 可见宽度偏差
- 风险描述：
1. 当前 bench `node trace read` 的逐 tick 口径里，`sync` 与 `toggle` 主要表现为“观测平移”：以 `input start` 为锚点时，source/target 常从 `jobStartTick + 1` 才看到首个匹配样本。这是 `END_SERVER_TICK` 采样相位带来的可见性偏差，不等于运行时真实生效整体晚了 1 tick。
2. `pulse` 除了同样存在首拍观测平移外，还常见“配置 4 tick、trace 只观测到 3 个高样本”。根因是触发 tick 的采样已经结束，而到期 tick 会先走 scheduled tick 回落，导致首尾边界 tick 不一定都进入当前 `END_SERVER_TICK` trace 窗口。
3. 因此若后续直接调整 `NodeStateTraceService` 的采样相位，虽然可能把 `sync/toggle/pulse` 的 bench 可见序列改得更“直觉”，但会同步改写现有 `trace_read_tick_assert` 的首拍口径与 `pulse` 高样本宽度，影响当前 functional 回归基线。
- 规避方案：
1. 当前阶段先把这条差异视为“观测口径问题”而不是运行时功能错误；逐 tick bench 继续按现有口径维护：`sync/toggle` 主要验证相对窗口与模式切换，`pulse` 维持“默认 4 tick 配置、trace 常见 3 高样本”的断言基线。
2. 若需要验证 pulse 真实有效期或仲裁真值，优先看运行时单测、内部结构真值或专门拉长 `server.pulseDurationTicks` 的专项，而不是直接把 trace 高样本数当成运行时真值长度。
3. 只有在后续明确接受“一次 bench 口径迁移 + 全量回归重标定”的前提下，再考虑调整 trace 采样顺序；在那之前，不把这条观测偏差当作当前 mixed/pulse 运行时缺陷继续修实现。

- 风险描述：
1. 当前 `x22` 更可能是逐 tick bench 口径缺少 source 参考相位，而不是 `crosschunk.dispatch.batchWindowTicks` 完全未覆盖；但在本轮 bench 对齐完成前，仍不能彻底排除 mixed 单核运行时实现存在额外问题。
2. 若 bench 口径补齐后 `window=1/2` 仍失败，则说明 mixed 场景的 `triggerSource -> core` 固定延迟语义可能与 `x21` 不一致，需要继续沿运行时派发与仲裁链路排查。
- 规避方案：
1. 本轮先按 `x21` 成功模式为 `x22` 补 source 逐 tick 参考与 relative 对齐，先消除锚点偏移噪声。
2. 回归时同时保留全标签测试与 x22 定向专项；若仍失败，再依据新增 source/reference 证据最小化修运行时，而不是继续盲猜配置覆盖链路。

##  非正常路径退役不会立即补号

### 近外显最终 IO 轮询方案不适合直接放大到多节点/多玩家
- 风险描述：
1. 当前近外显最终 IO 采用“客户端按准星命中节点懒请求 + 250ms 节流轮询 + 500ms 本地缓存”的模式，在“一次只盯一个节点”的使用前提下足够轻量。
2. 若后续扩展为“同时显示多个节点 I/O”或“多个玩家同时长时间盯住节点”，该方案的请求频率会随“显示节点数 × 玩家数”线性放大，服务端探针与网络回包压力也会同步增长。
3. 现阶段这不属于功能错误，但属于可扩展性边界；若不提前收敛，后续状态面板或大范围外显功能容易直接踩到性能上限。
- 规避方案：
1. 当前阶段继续按“近外显一次只盯一个节点”的产品边界验收，不将现有轮询链路直接复用到多节点并发显示场景。
2. 后续若需要多节点或更高频的 I/O 展示，优先评估“订阅式推送”或“复用已有方块实体同步”方案，避免继续按轮询请求数线性放大。

### triggerSource 真实下线与后续退役/解绑可能重复发布 hard invalidation（冗余设计）
- 风险描述：
1. 当前 `triggerSource` 在方块移除触发 `unregisterNode(...)` 时，会先发布一次“其它失效”事件；若后续又进入待退役确认或显式解绑路径，可能再次发布同源同目标的 hard invalidation。
2. 这类重复发布通常不会造成状态错误：目标侧清理是按来源贡献剔除后重算，跨区块持久队列也会按同 key 覆盖，因此结果保持幂等。
3. 现阶段问题主要体现在冗余事件、冗余重算与冗余入队覆盖，属于性能与实现收敛度问题，不属于语义错误。
- 规避方案：
1. 当前按“冗余设计保留”处理，验收口径以最终状态正确、无残留贡献为准。
2. 后续如需收敛，可在“离线 hard invalidation”与“最终退役/解绑 hard invalidation”之间增加来源态短路，避免第二次重复发布。

### 跨区块全局配置已从 relay 改为 queue，旧键不会自动迁移
- 风险描述：
1. 全局持久派发队列配置已从 `crosschunk.relay.enabled` / `crosschunk.relayExpireTicks` 改为 `crosschunk.queue.enabled` / `crosschunk.queue.defaultTtlTicks`。
2. 本次实现未保留旧键兼容读取，升级后若配置文件仍使用旧键，将回退到新默认值。
3. 对旧服或长期保留旧配置模板的环境，可能出现“以为沿用旧配置，实际已按默认值运行”的误判。
- 规避方案：
1. 升级时手动同步配置键名，重点检查持久队列总开关与通用 TTL。
2. 使用说明与默认配置模板已统一切换到 `queue` 术语，后续排障以新键名为准。

### 1:900 同步场景下来源点位于区块边界的性能波动
- 风险描述：
1. 在同一 1:900 连接规模下，仅改变同步来源附近点位（白/黑羊毛）即可出现约 2~3ms 的开销差异。
2. 该差异与来源点是否落在区块边界附近有关，容易受区块局部拓扑与原版邻居更新链路影响。
3. 现阶段无法保证“同规模必同耗时”，压测结果存在点位敏感性。
- 规避方案：
1. 暂按“保留问题”处理，性能对比时固定来源坐标、固定区块加载状态并多轮取中位数。
2. 后续如需彻底收敛，再补充“边界点位专项基准”与“来源点位标准化”测试工装。

### sync 来源先激活后下线时，目标迟加载可能“先亮后灭”
- 风险描述：
1. 当 sync 来源先产生 `SYNC_SIGNAL + UPSERT` 后很快下线，且目标区块尚未加载，队列中会先后存在旧的同步写入与后续失效剔除事件。
2. 在 `crosschunk.dispatch.maxPerTick` 较小或队列积压时，目标区块加载后可能先处理到旧 UPSERT，短暂点亮后再被 `TRIGGER_SOURCE_INVALIDATION + REMOVE` 回退熄灭。
3. 最终状态通常可收敛正确，但观测层存在瞬态闪烁窗口。
- 规避方案：
1. 当前阶段按“最终一致”验收；时序敏感场景可提高 `crosschunk.dispatch.maxPerTick`，缩短可见窗口。
2. 后续可补“失效优先短路”策略：当同源同目标已命中失效事件时，跳过历史同步写入回放，消除瞬态双到。

### plain 模式历史物品 NBT 快照残留风险
- 风险描述：
1. 在 `server.currentLinksPrivacy.mode=plain` 期间写入到物品 NBT 的“当前连接快照”会随物品流转而保留。
2. 后续切回 `masked/hidden` 时，历史物品快照不会自动全量重写，可能出现旧明文残留窗口。
- 规避方案：
1. 服务端默认值改为 `masked`，降低首次部署时的误暴露概率。
2. 若曾启用 `plain`，切换模式后需通过重写流程（重新同步/覆盖快照）清理历史物品 NBT。

### 顶面核心红石粉 ACTIVE 抖动（已知行为，非错误）
- 风险描述：
1. 顶面核心红石粉在激活切换时，F3 观察到的 `active` 可能出现一次短暂波动（先旧值后新值）。
2. 当前 `ACTIVE` 客户端同步节流窗口，导致观测层出现瞬时延迟。
3. 该现象不影响最终激活态一致性，不影响红石强度计算结果。
- 规避方案：
1. 当前阶段按“性能优先 + 最终一致”保留现状，并明确该现象属于已知行为，不判定为错误。
2. 若后续需要“首个边沿零抖动”体验，可改为首个边沿立即写回 `ACTIVE`，窗口内后续变化再节流。

### 持久化键与网络协议 ID 已硬切，旧版本不兼容
- 风险描述：
1. 当前已硬切到新契约（持久化键 `sourceSerial/targetSerials`、协议 ID `open_triggersource_pairing`），旧版本存档与旧端联机不再兼容。
2. 若后续需要回滚到旧版本，可能出现旧端无法识别新数据/新协议的问题。
- 规避方案：
1. 当前项目按“仅内部调用、单环境同版本”约束运行，统一使用同一版本客户端与服务端。
2. 如未来存在外部分发需求，再补“双读写 + 双协议 + 迁移回归”的兼容层。

### 命令激活跨区块提示缺失（无玩家上下文）
- 风险描述：
1. `activate triggersource` 属于命令触发路径，当前无玩家上下文时不会投递跨区块接管提示。
2. 与玩家交互触发（按钮/拉杆/遥控器）的提示行为不一致，可能造成“是否生效”的误判。
- 规避方案：
1. 当前阶段保留现状，命令激活验收以目标状态变化与结果汇总为准。
2. 后续可补充服务端提示投递策略（执行者回执、附近玩家广播或可配置日志）。

### 命令层解析结果二次包装可读性问题
- 风险描述：
1. `ModCommands.parseTargetSerials` 会把 `SerialParseUtil.TargetParseResult` 再包装为本地 `TargetParseResult`，阅读时容易被误解为重复构造或冗余逻辑。
2. 当后续字段扩展时，若两处 record 未同步更新，存在维护遗漏风险。
- 规避方案：
1. 当前阶段保留现状（命令层模型隔离）。
2. 后续可评估是否统一直接使用 `SerialParseUtil.TargetParseResult`，或在命令层补充明确注释说明“隔离映射”的意图。

### 跨区块通信无距离上限
- 风险描述：
1. 当前跨区块链路不按距离裁剪，远距离或跨维目标也可直接联动，误配置时影响面更大。
2. 当目标集合过大时，强加载/中继接管压力会随触发范围放大。
- 规避方案：
1. 现阶段通过白名单/预设与 `server.maxTargetsPerSetLinks` 控制联动范围。
2. 后续如需增强可控性，可补充“通信距离上限”配置与超限提示。

2. 后续如需统一体验，可补充“无玩家上下文提示投递策略”（附近玩家广播或可配置服务端日志）。
